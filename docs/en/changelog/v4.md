## [4.31.1] - 2026-08-25

Cross-device pending-delete queue gains a lease + heartbeat model, and queued conversations are hidden from the DeepSeek sidebar on every device.

### Added

- **Lease timestamps on the sync queue** (`utils/temporary-chat-constants.js`, `content/temporary-chat-pending-store.js`): Entries under `dss-pending-deletes-sync` are now `{ chatUuid, attemptCount, lastActiveAt }`, where `lastActiveAt` is an epoch-ms lease stamp. New constants `LEASE_TTL_MS = 600000` (10 minutes) and `HEARTBEAT_INTERVAL_MS = 60000` (1 minute) — the TTL is deliberately generous so it absorbs `chrome.storage.sync` propagation delay, background-tab timer throttling, and cross-device clock skew. The store gains `refreshLease(chatUuid)`, `releaseLease(chatUuid)` (zeroes `lastActiveAt`), and the pure predicate `isLeaseExpired(entry, now)`: expired when `lastActiveAt` is not a finite number or `now - lastActiveAt > LEASE_TTL_MS`, with a value exactly at the TTL still live. Every read-modify-write over the queue is serialized through a promise-chain mutex, so concurrent messages from multiple tabs cannot interleave `get`/`set` and lose an update.
- **`content/temporary-chat-heartbeat.js` (new)**: Publishes `{ start, stop }`. While a tab tracks a temporary conversation it sends `{type: 'DSS_HEARTBEAT', uuid}` immediately and then every `HEARTBEAT_INTERVAL_MS`; the service-worker route calls `refreshLease`. It starts from `trackUuid()` and from the restore-from-`sessionStorage` path, and stops when tracking ends or listeners detach. Binding it to the content-script/tab lifecycle is the design: a crashed or force-killed tab stops renewing and the lease expires on its own, with no device identifier required.
- **`content/temporary-chat-sidebar-hide.js` (new)**: Publishes `{ init, stop }`, bootstrapped from `content/content-script.js`. Keeps an in-memory uuid set seeded via `DSS_GET_PENDING_UUIDS` and refreshed by `DSS_PENDING_UUIDS_CHANGED` pushes; `background/service-worker.js` broadcasts the queue's uuids to tabs on every sync-queue change. Evaluation is per date-group container: when every anchor inside it is queued the whole container is hidden so its date label goes with it, and when at least one anchor is not queued only the individual queued anchors are hidden (a single-anchor group whose only anchor is queued counts as fully queued). Hiding applies the `ds-` prefixed class `ds-temp-chat-hidden` with an injected `display: none !important` rule and never removes nodes; each application clears the class everywhere and re-derives it, so a group reappears and an individual anchor unhides once its entry leaves the queue. A `MutationObserver` on the sidebar wrapper coalesces bursts into one application per animation frame.
- **Four new message types** routed through `background/pending-store-routes.js`: `DSS_HEARTBEAT`, `DSS_RELEASE_LEASE`, `DSS_GET_PENDING_UUIDS`, `DSS_PENDING_UUIDS_CHANGED`.
- **Two new selectors in `content/ds-selectors.js`**: `SIDEBAR_DATE_GROUP_SELECTOR` (the obfuscated date-group container class) and `SIDEBAR_CHAT_LINK_SELECTOR` (anchors located by their `/a/chat/s/` href). Should a DeepSeek markup change break the group selector, the feature degrades to individual-anchor hiding, which finds anchors by href independently of obfuscated classes.

### Changed

- **Remediation is lease-gated on every path** (`background/service-worker.js`): `remediatePendingDeletes()` takes no argument and deletes only lease-expired entries. `chrome.runtime.onStartup`, the `dss-delete-retry` alarm, and the sync `chrome.storage.onChanged` listener all apply that same gate, so a conversation in active use on any device is protected — the previous guard was a device-local open-uuid set that other devices could not see, which let a second device signed into the same Chrome account delete a conversation the first device was still using.
- **Fast-restart recovery**: On `onStartup`, each locally-open uuid that is also queued has its lease released first, then the local open set is cleared, then remediation runs — so a conversation this device had open is deleted immediately on restart rather than waiting out the TTL.
- **Explicit lease release on immediate-delete failure**: When the leave flow's Fiber delete fails and the API fallback exhausts its retries, the coordinator sends `DSS_RELEASE_LEASE`, zeroing the lease so any device can take over instantly.

## [4.19.1] - 2026-08-08

Scroll step size changed to **per-step measured-then-derived**, replacing the fixed 0.9× viewport height.

### Changed

- **Adaptive step size replaces fixed step size** (`content/harvest.js`, `content/harvest.policy.js`, `content/harvest.dom.js`): `HARVEST_SCROLL_STEP_FACTOR` (0.9) removed from `harvest.js`; step size now derived from `_measureMountedBottomOffset()` measurement + `HarvestPolicy.computeScrollStep()`.
  - **Measured facts** (two real conversations, different scroll positions): The virtual list consistently mounts **18 nodes** regardless of message height; the mount window does not extend upward (overscan is 0 px) and extends downward 3406–4244 px (container `clientHeight` 928, viewport height 988).   - **Derivation rule**: `round(mountedBottomOffset × 0.7)`, lower bound `round(viewportHeight × 0.25)`; falls back to `round(viewportHeight × 0.9)` (the old fixed behavior) when measurement is unavailable; `throw`s when `viewportHeight` is invalid (callers always have `innerHeight`; inability to measure means the caller is broken — deliberately asymmetric with the "page redesign" degradation scenario for unavailable measurements).
  - **Why the change was necessary**: The mount window is determined by **item count** rather than height, so a fixed pixel step size is a bet on message length — in a stretch of all-short messages, 18 nodes span a much smaller height, and the fixed step overshoots content that was never mounted. The scan is one-directional and never backtracks; those messages are permanently lost. On the test samples, step size increased from 889 px to 3620/3034 px, roughly 3.4–4.1× fewer steps.
  - **Rejected: key gap detection**. Unless new evidence shows numbers are dense, this will not be revisited.
  - **The 0.25 lower bound is a deliberately marked corner**: Below this value, the measurement is more likely inaccurate than real (18 nodes spanning less than a quarter viewport means ~11 px per message); rather than letting scrolling crawl in tiny increments across tens of thousands of pixels, a bounded, still-progressing step size is preferred.

  - **Budget was consumed by idle waiting, not loading**: Each downward scroll step requires `await _waitForDomStability()`, whose minimum cost is `HARVEST_STABLE_TICKS`(3) × `HARVEST_STABLE_INTERVAL`(150 ms) = 450 ms, **paid even when the step has no new content**. Total scrollable distance is thus hard-limited to ~120000 ÷ 450 ≈ 266 steps × 0.9 viewport heights ≈ **240 viewport heights**, regardless of actual conversation length — conversations exceeding this are structurally impossible to export completely. This is also why "export is slow" and "export aborts" are not two problems: time is spent waiting rather than loading; they are two faces of the same defect.
  - **Changed to progress-based criteria**: `HARVEST_TOTAL_TIMEOUT` and its check completely removed, **not replaced with a larger value, not replaced with a configurable value, not replaced in any form**. The only time-based stop condition is `HARVEST_STALL_TIMEOUT_MS` (20000 ms) of **consecutive** no-progress, returning `reason: 'stalled'`. "Progress" is defined as captured message count increasing **or** `scrollHeight` changing in any direction — the virtual list can shrink; treating shrinkage as stall would abort healthy execution.
- **Incomplete warning now reports the actual cause** (`content/content-script.export.js`): Previously the footer always hardcoded `scroll-harvest timed out before reaching the end.`, but `harvest.js` has five early exit types (`stalled`/`scroll_interrupted`/`cancelled`/`no_container`/`no_messages`) plus one reason propagated from `GoToTop.scrollToTopAndWait()`, all sharing that same sentence — every non-timeout abort was lying about its cause, misleading subsequent debugging. Changed to `> ⚠️ Export may be incomplete (<N> messages captured): <clause>.`, where `<N>` is actual captured count and `<clause>` is produced by `HarvestPolicy.describeIncompleteReason(reason)` per actual reason; unknown reasons' fallback clause includes the raw string verbatim so unmapped codes don't vanish.
- **Incomplete warning now visible on the page** (`content/harvest.toast.js`, `content/content-script.export.js`): Relying solely on a footer line is effectively invisible — in the reported case it was at **line 12209** of a 12209-line file; the user's actual experience was "no indication at all, just downloaded". Added `showHarvestToastIncomplete(capturedCount, reasonText)` with warning styling (`.dss-harvest-toast--incomplete`, amber border and background) clearly distinct from the progress toast, manually dismissable, auto-dismissed after `HARVEST_INCOMPLETE_TOAST_AUTO_DISMISS_MS` (10000 ms) — deliberately longer than a typical toast's 3 seconds because this message is important. Footer and toast share **the same** clause string (`describeIncompleteReason` called only once per export), structurally impossible for the two to say different things.
  - **Export is not blocked by incompleteness**: `downloadMarkdown()` still executes unconditionally, with no confirmation dialog and no `isComplete` gate. The user retaining a partial file while being clearly informed is better than discarding already-captured data.

### Added

- **Export cancel functionality** (`content/harvest.js`, `content/harvest.toast.js`): Both progress toast phases (scroll-to-top, capture) provide a cancel button. `harvestAllMessages()` creates a native `AbortController` internally with a lifetime of exactly one export, **introducing no module-level mutable state** (`coding-guidelines` §7); `() => abortController.abort()` is handed to the toast as the cancel callback; `abortController.signal.aborted` is fed into every step's observation. After cancel, returns **the already-captured portion** rather than an empty array — partial data is still the user's data.
  - Cancel triggers at most once: the button is immediately disabled and changes to "Cancelling…" because actual stopping occurs at the next capture step boundary, and the user needs immediate feedback that the click registered. State is not stored in module-level variables; the button's own `disabled` attribute is the single source of truth with the cancel callback attached to the button element, following the file's existing "DOM as state source" convention.
  - The capture phase toast redraws the count every step, so button creation and `addEventListener` execute only inside `if (!cancelBtn)`: redraws neither restore a pressed button to clickable nor stack duplicate listeners.
  - The `.dss-harvest-toast` container is `pointer-events: none` (deliberately letting clicks pass through to the page), so the button must individually specify `pointer-events: auto`; otherwise the cancel button is purely decorative. The button has keyboard accessibility and accessible labels.

Note: harvest toast strings come from `utils/i18n.locales.js`, not `_locales/*/messages.json`.

### Changed

- **`harvest.js` split out `harvest.policy.js`** (430 → 446 lines + 140 lines): Extracted the pure decision logic of "should we keep scrolling or stop, and why" — `createInitialState()`, `decideNextStep()`, `describeIncompleteReason()`, mounted on `window.DSstudio.HarvestPolicy`; registered in `manifest.json` before `harvest.js`.
  - **The split simultaneously solved two problems**. `harvest.js` was already at 430 lines, approaching the §8 450-line threshold; but the real motivation was **that logic was previously untestable** — stop decisions were entangled with DOM scrolling, `MutationObserver`, and `Date.now()` in the same async loop; verifying "stops after 20 consecutive seconds of no progress" required building an entire virtual list with fake timers. Extracted as pure functions, the clock is injected as a `nowMs` parameter; 29 tests need no fixtures or fake timers. The logic most in need of testing is precisely the logic that most needed to leave the file.
  - `harvest.policy.js` maintains zero DOM, zero `chrome.*`, zero timers, zero clock reads. **Reading `Date.now()` once in there for convenience would push this logic right back to untestable.**
  - Decision priority (earlier wins): `isAtBottomConfirmed` → `complete`; `isAborted` → `cancelled`; `isScrollJumpDetected` → `scroll_interrupted`; progress → continue and reset last-progress time; consecutive no-progress reaching 20000 ms (boundary inclusive) → `stalled`; otherwise continue **without** resetting last-progress time, allowing consecutive no-progress to accumulate. Bottom-reached wins over cancel deliberately: if the end has been reached, the export is complete; reporting it as cancelled would understate what the user actually got.
- **`HARVEST_STABLE_INTERVAL` reduced from 150 ms to 100 ms**; per-step minimum reduced from 450 ms to 300 ms (~1.5×). **`HARVEST_STABLE_TICKS` deliberately kept at 3, must not be reduced**: If stability waiting converges early, it will scroll past a segment before new content has rendered; the scan is one-directional and never backtracks, so those messages are permanently lost. Completeness takes priority over speed here — this is the user's explicit tradeoff.
- **Layout metrics read once per round** (`content/harvest.js`): `scrollTop`/`clientHeight`/`scrollHeight` were previously read multiple times within the loop (including inside `_isAtBottom()`); each read can force a layout reflow. Changed to read into local variables at the start of each round and reuse within that round. Deliberately **not** cached across rounds — after scrolling, these values are supposed to change.
- **`HARVEST_SCROLL_STEP_FACTOR` (0.9) and `HARVEST_STEP_TIMEOUT` (8000 ms) unchanged**: Step size was calibrated against actual pages; not blindly adjusted.

### Deliberately Not Done

- **Two `_waitForDomStability()` calls not merged**: They appear to cause waiting twice per step and could save half the time; testing confirmed they are on **mutually exclusive branches** — one is inside the `if (isAtBottomNow)` bottom confirmation block, the other is reached only after `scrollBy()` (i.e., when `isAtBottomNow` is false). A single iteration only takes one path. The acceleration hypothesis was withdrawn accordingly. **Looks like duplication but isn't — do not "optimize" this.**
- **Two layers of "`HarvestPolicy` absent" handling deliberately inconsistent**: `harvest.js` directly `throw`s (it cannot function without decision logic, and it's a hard dependency loaded from the same manifest; absence means the manifest is broken — fail loudly). `content-script.export.js` falls back to a generic but diagnosable description and downloads anyway (it can still hand the user their data). ## [4.18.1] - 2026-08-07

Fixed three in-page prompt dropdown defects: entry expand jitter, width stuck at 200px cap, and pinned default not showing when navigating to a new conversation within the page.

### Fixed

- **Entry expand jitter** (`content/preset-overlay.controller.js`): Previously `mountTo()` appended `wrapperEl` to the title row **without any inline `left`/`width`**; then immediately called `startSettle('initial-settle')`; the settle loop's first `reposition()` landed on the next animation frame, so the browser inevitably painted one frame of "unpositioned, unsized" default geometry — the jump between that frame and the first measurement result looked like an expand animation. **There has never been any CSS transition here** — `preset-overlay.styles.js` only sets position/transform/z-index; the only transition in `preset-dropdown.css` is on `.dss-preset-arrow` (open/close arrow rotation). The fix had to be sequential rather than masking: extracted the measurement and application logic from `reposition()`'s `scheduleFrame` callback into `_applyPlacementSync()`; `mountTo()` now calls it synchronously once after `appendChild`, within the same task, before starting the settle loop. **Deliberately not adding `opacity`/`visibility` fade-in** — that would only hide the problem. The settle loop constants (`maxFrames: 7200`, `stableK: 120`, `epsilon: 1`) and frame counts are all unchanged because the DeepSeek host page's layout genuinely moves during loading. `reposition()` and `_applyPlacementSync()` share the same implementation; there is no second layout path.
- **Width fits the widest option** (`content/preset-dropdown.width.js`, `content/preset-dropdown.position.js`): `getNaturalWidth()` measured only the visible label on the trigger — i.e., the **currently selected item (or placeholder)** width — and never iterated all options; that value was then clamped by `Math.min(naturalWidth, maxWidth)` at 200, so longer names were permanently stuck at the cap. Changed to use all option names plus the placeholder as the candidate set; each is temporarily written into the real label to read `scrollWidth` (thus using the label's own computed font for measurement), restored in `finally`. A new pure function `pickNaturalWidth()` takes the maximum plus `arrowWidth`/left-right padding/`gap`, with `minWidth` (80) as lower bound. **`pickNaturalWidth()` deliberately sets no upper bound**: clamping to available horizontal space remains `computePlacement()`'s responsibility (`maxWidth` 200; gap mode additionally clamps to measured spacing); keeping the two concerns separate prevents them from tangling again.
  - **Source of the regression**: Before v4.2.x, this control was a native `<select>` (`min-width: 80px; max-width: 200px`, no `width`); fitting the widest `<option>` was native browser behavior. `d560729` replaced it with a custom combobox and lost the native fitting; the rewritten measurement only read the current label from the first version. `052eeff3`'s replacement of the off-screen probe with `scrollWidth` was an equivalent rewrite and not the cause of this defect.
  - **Caching is a necessary condition, not an optimization**: `getNaturalWidth()` is on the settle loop's per-frame layout path (up to 7200 frames); per-frame remeasurement would mean changing label text N times per frame and forcing N reflows. The measurer therefore caches results **per dropdown instance** (not module-level mutable state) and invalidates only when input actually changes: `setOptions()` (options data rebuilt) and `updateLocale()` (placeholder text changed), one invalidation point each. The label's `overflow: hidden`/`white-space: nowrap` remain as-is; names exceeding 200px are still truncated with ellipsis.
- **Navigating to a new conversation within the page now shows the pinned default** (`content/preset-id.resolver.js`, `content/preset-overlay.controller.js`, `content/content-script.js`): `findAndMount()` originally used a hardcoded ternary `currentChatUuid ? (chatPresetMap[currentChatUuid] || '') : ''` to determine the id to render; the `else` branch was literal empty string and completely ignored `pendingPresetId` and `pinnedPresetId` — which was the only scenario the pin feature targeted. When the user opened a new conversation within the page, React replaced the title row, `findAndMount()` immediately rebuilt the dropdown, and **deterministically** overwrote the value `handleChatChange()` had just pushed via `updateActiveId()` (this is not a race — regardless of which observer runs first, that ternary always produces `''`). The reason a page refresh worked correctly is that `initSettings()` starts rendering with the persisted `activePresetId` and the title row is not replaced; the reason sending the first message worked is that by then there's a UUID and the ternary takes the correct branch.
  - **Decision extracted into pure function** `resolveOverlayPresetId({ chatUuid, chatPresetMap, pendingPresetId, pinnedPresetId, presets })`: When `chatUuid` is a non-empty string, it only looks up from `chatPresetMap`; `pendingPresetId`/`pinnedPresetId` can never influence the result — "existing conversations' prompt groups are never changed by defaults" is now a contract rather than scattered guards. Without a chat id, pending id is **three-valued**: a still-existing non-empty id wins; empty string `''` means the user explicitly chose blank and **must not** fall back to the pinned default; `null`/`undefined` means no selection yet, and only then does the pinned default apply (likewise only when that group still exists). On any path, an invalidated id (group was deleted) degrades to `''`.
  - **Controller does not duplicate the logic**: `pendingPresetId` obtained via `content-script.js`'s new optional `ctx.getPendingPresetId()` getter (degrades to `undefined` when missing, which is exactly the correct "no selection yet" semantic, so existing test ctx mocks are unaffected); `pinnedPresetId` and the presets array come from the `getSettings()` call `findAndMount()` was already making — **no second storage read added**. `render()` and `start()`'s `activeId` are passed in by callers and don't make their own determination, so no parallel ternary needs changing.
- **Explicitly selecting blank prompt no longer overridden by pinned default** (`content/preset-overlay.controller.js:201`, `content/content-script.js:320`): The three-valued semantics above were destroyed by `|| null` before reaching the resolver — `'' || null` equals `null`, collapsing "user explicitly chose blank" into "no selection yet"; on the next rebuild, the pinned default overwrote it again. Both sites changed to `??`: `''` survives as `''`, `undefined`/`null` still normalize to `null`. **The resolver itself was not touched at all**, and no compensating logic was added to `findAndMount()` — the defect is at the collapse point, fix at the collapse point.
  - The other 6 `pendingPresetId` assignment sites in `content/content-script.js` were audited and **all kept as-is**: initial value, no-pinned-preset branch, clearing after binding resolution, `__resetState` are all semantically correct `null`; `:186` only entered when `pinnedPreset` is truthy so must be non-empty string; `__setState` assigns as-is by design. Also found the same-shape `|| null` at `popup/popup.preset-manager.js:115`, but its only caller `popup/popup.js:231-232` already does a truthy check on that value; `''` and `null` produce the same final result; it is not on this defect's causal path and was **deliberately not changed**.

### Fixed

## [4.11.19] - 2026-07-26

Fixed prompt group ordering reverting to "whichever groups happen to be locally cached" when timestamps tie.

### Fixed

- **User-visible: Prompt group order jumps back to the old arrangement on next popup open after drag-reordering.** `mergePresets()` (`utils/storage-manager.presets.js:187-192`) originally only adopted the corresponding side's `order` array when the timestamp was **strictly newer**; on tie, `chosen` stayed `undefined` and fell back to the merge `Map`'s insertion order. That insertion order was "locally-cached prompt groups first, rest in cloud order" — so the result was determined by **which prompt group objects happened to be in `chrome.storage.local`**, not by the saved order array. Any locally cached group floated to the top.
  - **Tie is the norm, not an edge case.** A single `_set()` writes to `chrome.storage.sync` first (`utils/storage-manager.js:332`), then mirrors **the same object** to `chrome.storage.local` (`:358`). `orderUpdatedAt` travels with the object into both areas, so after any successful save the two sides are necessarily bit-identical. Confirmed against the user's live dump: both sides had `orderUpdatedAt: 1785070411839`.
  - **Fix**: On tie, adopt the cloud side's `order`. The effective condition collapsed to "only use local order when `baseTs > incTs`; all other cases use cloud".
  - **Why cloud over local**: Tie means no way to determine which is newer; cloud winning is **self-converging** — all devices eventually land on the same array. Local winning would let two devices each permanently keep their own order, because the read path never writes merge decisions back to cloud (`_get()` only writes back to `local`, see `utils/storage-manager.js:284-290`, and that write-back only triggers when cloud wins). Protecting "local is genuinely newer" is the `dsLocalAuth` re-push queue's job, not the tie-break rule's.
  - **Self-perpetuating cycle**: This defect was self-sustaining. `resolveSyncConflict()` overwrites the timestamp with `Math.max(localTs, syncTs, Date.now())` (`utils/storage-manager.sync.js:96-100`); a single `mergedMeta` written to both areas makes the timestamp immediately tie again, and the next open takes the same fallback path.
  - **Why it triggers on every open**: `_detectSyncConflict()` (`utils/storage-manager.sync.js:31-59`) returns `'auto'` due to incomplete local cache alone (the live machine had only 3 objects cached out of 11 indexed groups), making `hasAnyDivergence = true`. `retrySync()` then calls `resolveSyncConflict()`. This overly sensitive detection was **deliberately not fixed here** — it is a separate issue; after fixing the tie branch, even if the merge runs frequently, it no longer reorders.
  - **Root cause investigation history**: This symptom had two prior hypotheses disproven; a third hypothesis (`retrySync()` blindly pushing `dsPresetOrderMeta`, fixed in 4.11.18) was confirmed as a real defect via adversarial verification but **was not the cause of this symptom** — the user's live dump showed `dsLocalAuth` didn't contain that key at all, meaning nothing was parked and the push loop never executed. Lesson: steps the plan document self-marked as INFERENCE (does the symptom actually take that path) must not be acted on without runtime evidence.

## [4.11.18] - 2026-07-26

Fixed cross-device sync: prompt group order rolling back, and groups deleted on one device resurrecting on another. Both are victims of the same defect.

### Fixed

- **User-visible: Drag-reordering prompt groups on device A syncs but jumps back to the old order on next open; prompt groups deleted on device A reappear on device B.** Root cause in `retrySync()`'s pending-push loop (`utils/storage-manager.sync.js:199-240`). The loop walks `dsLocalAuth` keys that "last failed to write to cloud" and pushes local values up. It has "compare-before-push" guards for `PRESET_INDEX` and `dsPreset_*` content keys, but **`PRESET_ORDER_META` and `PRESET_TOMBSTONES` have none** — `shouldPush` stays at the default `true`, falling into unconditional push where stale local values blindly overwrite newer cloud values.
  - **Why `dsPresetOrderMeta` was missed**: The existing guard condition is `key.startsWith('dsPreset_')`, **with trailing underscore**. `'dsPresetOrderMeta'` has `O` at position 8 instead of `_`, so `startsWith` is false — it matches neither the `PRESET_INDEX` branch nor the `dsPreset_*` branch. This is a string prefix near-collision, extremely easy to misjudge by eye.
  - **Tombstones have different semantics from other keys — not "newer side wins wholesale"**. Tombstones are an object keyed by prompt group id `{ [id]: { ts, deleted } }`. Two devices can each delete **different** groups while offline; replacing cloud with local wholesale silently resurrects the other device's deletions. Fixed as **per-id union**: ids present only on one side are kept; ids on both sides take the newer `ts`; an empty local set must not clear the cloud set.
  - **Reused existing helper without writing new merge logic**: Directly calls `_mergeTombstones()` (`utils/storage-manager.presets.js:41-47`), the same function `resolveSyncConflict()` already uses.
  - **`>=` not `>`**: The new guard for `PRESET_ORDER_META` uses the same comparison operator as the existing `PRESET_INDEX` branch in the same loop. A key's presence in the push path is itself evidence of "local has an action not yet delivered to cloud", so pushing on timestamp equality is correct. This decision is directionally opposite to the read path (`_get()` uses cloud-wins on tie) — deliberate, documented for future unified review.
  - **Adversarial verification**: Two competing hypotheses were disproven before confirming this root cause. A third-version hypothesis was reviewed by a verifier explicitly instructed to "attempt to disprove; if you cannot positively confirm, default to disproved"; it judged CONFIRMED and additionally discovered `PRESET_TOMBSTONES` shares the same defect — order rollback and deletion non-propagation thus converge into a single fix rather than two independent problems.
  - **Deliberately not addressed here**: `dsPresetOrderMeta` internally stores a duplicate `order` array copy alongside `dsPresetIndex`, constituting duplicate truth; the two are written by two independent `_set()` calls in `savePromptPresets()` (`utils/storage-manager.presets.js:233`, `:236`) and can independently fail and decouple. Removing `.order` is structural cleanup rather than a bug fix; deliberately deferred until the live-machine verification of this fix succeeds, to avoid mixing two variables.
