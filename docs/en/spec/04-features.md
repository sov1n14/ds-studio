## 3. Markdown Export

- **Trigger**: The user clicks the "Export Current Page Conversation as Markdown" button in the extension popup menu.
- **Scope**: Exports **all** message turns from the current chat session on `chat.deepseek.com`, including messages not rendered in the viewport due to the virtualized list.
- **Scroll-and-Harvest Process** (v2.6.0, extended in v2.6.1, further updated in v2.6.2, termination condition rewritten in v4.19.0):
  1. **Anti-Auto-Scroll Suppression** (v2.6.1): Before capture begins, `window.DSstudio.PreventAutoScroll.enable()` activates the MAIN-world scroll interception patch, silently suppressing DeepSeek's native "auto-scroll to latest message" behavior. Once enabled, the user can continue normal conversation (typing and sending messages) during capture without interfering with the harvest process; after capture completes, `.disable()` restores native behavior — but if the user has enabled the "Prevent Auto-Scroll" persistent toggle (v4.12.0), that `.disable()` is a no-op, and protection continues after export ends.
  2. **Progress Indicator** (v2.6.2 two-phase update): The toast uses `pointer-events: none` and **does not block** mouse events, allowing the user full page interaction during capture (replacing v2.6.0's full-screen blocking overlay). Text is split into two phases:
     - **Scroll-to-Top Phase**: The toast displays "Scrolling to the top of the conversation…" without showing a capture count, to avoid misleading the user.
     - **Capture Phase**: The toast displays "Capturing full conversation… {count} messages captured" (count updates dynamically with capture progress), with a persistent warning line below: "⚠ Do not scroll the conversation history to avoid capture failure", reminding the user that manual scrolling during capture **is not** suppressed and may cause capture failure.
     - **Cancel Button** (v4.19.0): Both phases of the toast include a cancel button. After clicking, at most one cancellation is triggered (the button is immediately disabled and changes to "Cancelling…"); the actual stop occurs at the next capture step boundary, hence the immediate feedback to let the user know the click registered. Since the toast container is `pointer-events: none`, the button must individually specify `pointer-events: auto` to be clickable. The capture phase toast redraws the count on each step; redraws **must not** re-enable an already-clicked button, nor re-attach event listeners.
  3. **Scroll to Top**: Calls `GoToTop.scrollToTopAndWait()` to anchor the virtual list at position 0, ensuring capture starts from the first message.
  4. **Incremental Scroll Capture**: Scrolls the page progressively from top to bottom, waiting for the virtual list to render new nodes after each scroll, continuously collecting message nodes appearing in the DOM. Deduplication uses the `data-virtual-list-item-key` numeric attribute assigned by DeepSeek's virtual list renderer as the key (`Map<number, Element>`), with a "do not overwrite if exists" strategy; the final output is sorted by ascending key.

     **Adaptive Step Size** (v4.19.1): The step size is no longer a fixed viewport height ratio but is **derived from real-time measurement each step**. Measurements from two real conversations show that the virtual list always mounts **18 nodes** (regardless of message height), with the mount window not extending upward (overscan of 0) and extending downward 3406–4244px. Since the deepest point of already-captured content is the bottom edge of the lowest mounted node, the next step's new viewport top only needs to not exceed that point to avoid missing content; `_measureMountedBottomOffset()` measures that distance, and `HarvestPolicy.computeScrollStep()` takes 70% of it as the step size, with a floor of 25% of viewport height and a fallback to 90% of viewport height (i.e., the fixed behavior prior to v4.19.1) when measurement fails.

     **Why This Change Was Necessary**: The mount window is determined **by item count**, not by height, so a fixed pixel step size is a bet on message length — in a segment of all short messages, 18 nodes span much less height, and a fixed step would scroll past content that was never mounted, and since scanning is one-directional without backtracking, those messages are permanently lost. Switching to real-time measurement causes step size to automatically scale up to 3–4 viewports for long-message segments and automatically shrink for short ones — the coefficient is no longer an assertion about the page but a consequence of it. On measured samples, the step size increased from 889px to 3620px/3034px, reducing step count by approximately 3.4–4.1×.

     **Rejected Approach**: Using `data-virtual-list-item-key` sequence gaps as a completeness proof was considered and abandoned after measurement — sample one's `distinctDiffs` was `[1, 3]` (naturally occurring holes), while sample two was fully contiguous. Since gaps occur naturally, they cannot prove missed captures. Unless new evidence shows that numbering is dense, do not revisit this idea.
  5. **External Scroll Interruption Safety Net** (introduced in v2.6.1, fixed in v2.6.2): The capture loop continuously monitors scroll position. If a large jump not initiated by the capture loop itself is detected (e.g., the suppression patch is bypassed, or the user force-scrolls with the mouse wheel), capture is immediately aborted with `scroll_interrupted` reason, and the already-collected partial content is exported; an incomplete warning footer is appended at the end of the Markdown file. This ensures the user is explicitly aware the result is incomplete. Starting from v4.19.0, the footer was changed to `> ⚠️ Export may be incomplete (<N> messages captured): <clause>.`, where `<N>` is the actual number of captured messages and `<clause>` is generated by `HarvestPolicy.describeIncompleteReason(reason)` based on the **actual** reason — prior to this, all interruption reasons (including manual scroll interruption) were uniformly written as `scroll-harvest timed out before reaching the end`, effectively misreporting the cause. v2.6.2 fix: Previously, after each DOM stability wait ended, `_expectedScrollTop` was erroneously reset to the current scroll position, masking external scroll jumps that occurred during the wait period, preventing the safety net from triggering correctly; after removing that reset, the safety net now reliably detects and responds to external scroll interruptions.
  6. **Sorting and Assembly**: After capture completes, messages are sorted by key to build the final ordered message array, ensuring output order matches conversation order.
  7. **Scroll Position Restoration**: Regardless of whether capture succeeds, times out, or is interrupted, the user's original scroll position is unconditionally restored.
  8. **Termination Condition: Stall Detection, No Total Time Limit** (v4.19.0 rewrite): The loop itself no longer holds the stop decision; each step assembles observations and submits them to `window.DSstudio.HarvestPolicy.decideNextStep()` for adjudication and obeys the result. **No total duration cap is set** — as long as progress continues (captured count increases, or `scrollHeight` changes in either direction), the run is never cut short no matter how long it takes; the only time-based stop condition is **20 consecutive seconds** (`HARVEST_STALL_TIMEOUT_MS`) with no progress at all, classified as `stalled`.

     **Rationale for Change**: Prior to v4.19.0, a `HARVEST_TOTAL_TIMEOUT` of 120000ms hard cap was in place, silently truncating long conversations — in a real case, capture stopped at 500 messages and lost all recent messages, leaving only a single buried warning line at the end of the file. That budget was exhausted by "idle waiting" rather than "loading": each step's DOM stability wait has a minimum cost of `HARVEST_STABLE_TICKS`(3) × `HARVEST_STABLE_INTERVAL`(150ms) = 450ms, paid even when that step has no new content, so the total scrollable distance was hard-limited to approximately 120000 ÷ 450 ≈ 266 steps × 0.9 viewport height ≈ 240 viewport heights, regardless of actual conversation length. **"Export interrupted" and "export too slow" are two sides of the same defect**, hence fixed together.

     **Performance Trade-off**: `HARVEST_STABLE_INTERVAL` was reduced from 150ms to 100ms, lowering the per-step floor from 450ms to 300ms; however, `HARVEST_STABLE_TICKS` is intentionally kept at 3 and **must not be reduced**. Rationale: if stability wait converges early, it would scroll past a segment before new content has rendered, and since scanning is one-directional without backtracking, those messages would be permanently lost. Completeness takes priority over speed here.

  9. **Partial Export Never Blocks**: Any early stop (`stalled`, `cancelled`, `scroll_interrupted`) still exports collected content, and simultaneously emits two signals: an accurate cause-specific warning footer at the end of the file, and a prominent warning toast on the page (`showHarvestToastIncomplete`, auto-dismissed after 10 seconds). This ensures the user always gets a file rather than a silent failure, and never mistakes the export as complete. The in-page toast is necessary because the file-end warning alone is effectively invisible in practice — in a real case, the warning line landed on line 12209 of a 12209-line file.
- **Output Format**: A valid Markdown (`.md`) file containing:
  - A title line (`# DeepSeek Chat Export`).
  - An export timestamp.
  - Each conversation turn separated by a horizontal rule (`---`).
  - User messages under an `## User` heading.
  - AI responses under a `## DeepSeek` heading.
- **Thinking Process Handling**: If present, the AI's thinking process is rendered as a blockquote (`> `) under a `> **Thinking Process:**` heading. Internal links within the thinking process are always preserved.
- **Reference Link Handling**: Citation links (e.g., `[link-1]`) are extracted from `.ds-markdown-cite` elements; when enabled, they are rendered in `[[link-N]](url)` format.
- **HTML-to-Markdown Conversion**: The exporter must correctly convert headings, tables, blockquotes, ordered/unordered lists, code blocks (including `<div class="md-code-block">` → `<pre><span>` extraction), inline formatting, and links.
- **File Name**: `deepseek-chat-YYYYMMDD-HHmmss.md` (timestamp at the moment of export).

## 16. Quote Reply

- **Trigger Scope**: Only triggers when the user selects text within `div.ds-virtual-list-visible-items` (the AI reply virtual list). Both `anchorNode` and `focusNode` must be within this container; cross-container selections are always ignored. Empty selections or whitespace-only selections do not trigger.
- **Floating Button**: After selection completes (`selectionchange`, 250ms debounce), a `.dss-quote-btn` floating button is displayed above the first line of the selection, containing a quotation mark SVG icon and a "Quote Reply" text label.
- **Positioning Rules**: The button defaults to 16px above the first line of the selection, horizontally centered; left/right boundaries are clamped to a minimum of 10px; if `top < 10`, it flips to 8px below the selection; the button auto-hides when the selection scrolls completely out of the viewport.
- **Injection Format**: After clicking the button, the selected text is appended to the `<textarea>` in Markdown blockquote format (each line prefixed with `> `):
  - textarea is empty → directly fills in `> selected content` (no extra blank lines).
  - textarea has content → original content + `\n` (if no trailing newline) + `> selected content`.
  - Multi-line selection → each line individually prefixed with `> `, joined with `\n`.
- **React-Compatible Writing**: Uses `Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype, 'value').set` to write the value, then dispatches `input` (`bubbles: true`) followed by `change` (`bubbles: true`) events in sequence.
- **Dismiss Conditions**: The button auto-hides under any of the following: (1) selection cleared or collapsed, (2) selection nodes leave the container, (3) selection scrolls completely out of viewport, (4) window resize (recalculates positioning; hides if out of bounds), (5) clicking outside the button.
- **IME Protection**: `keyup` events are skipped when `e.isComposing === true`, preventing accidental triggers during Chinese character composition.
- **Virtual List Snapshot**: `_selectedText` is snapshot at the end of the debounce; the button `click` uses the snapshot value rather than the live selection, preventing the selection from being invalidated by DeepSeek's virtual list re-rendering.

## 19. System Time Injection

- **Toggle Location**: The `#showSystemTimeToggle` checkbox in the popup menu's "Features" card, the first item in that card (moved from the Export card in v4.32.2).
- **Storage Key**: `dsShowSystemTime` (boolean, default `false`).
- **Injection Format**: When enabled, the current system time is inserted at the beginning of each message in the format `Current Time: yyyy/mm/dd hh:mm:ss (UTC±hh:mm)` (24-hour, zero-padded, with local timezone offset), placed before the `<system-reminder>` block (if present) or the `<user-input>` block. Example: `Current Time: 2026/06/14 20:19:32 (UTC+08:00)`.
- **Duplicate Injection Handling**: The injection logic regenerates the timestamp each time and prepends it to the message start (no deduplication check). If the text input area already contains an old timestamp, it is replaced by the new one.
- **Master Switch Awareness**: When the master switch (`isEnabled`) is off, this toggle is disabled (via the `disabled` attribute).
- **Attachment/Image-Only Sends (v4.21.1)**: When the text input area is empty but the send button is not disabled (attachments or images only), the timestamp is still inserted — this is part of the prompt injection logic (see [Prompt System Specification §2](01-prompt-system.md#2-prompt-injection-logic)), with the timestamp format and insertion position unchanged; it simply no longer requires text in the input area to trigger.

## 20. Censor Reply Restore

- **Purpose**: DeepSeek's official systems may replace the original model reply with messages like "I'm temporarily unable to answer this question" (content moderation/censorship). This feature restores the original assistant reply from SSE stream data and displays it in the UI.
- **Stream Interception**: Via `censor-xhr-hook.js` (injected into the page's main world), monkey-patches `XMLHttpRequest.prototype.send` to intercept SSE responses from two endpoints listed in `INTERCEPTED_ENDPOINTS` (matched by `getMatchedEndpoint()` pure function): `/api/v0/chat/completion` and `/api/v0/chat/edit_message` — re-generation after editing an existing user message goes through `edit_message`, whose SSE format and request field names (`chat_session_id`, `prompt`) are identical to `completion`; the extra `message_id` in the request is the ID of the edited user message, deliberately ignored — the reply ID is always taken from the SSE stream's `response.message_id`. When the request is sent, `chat_session_id` and `prompt` are also parsed; the interception log identifies the matched endpoint. When the response completes, a `DSS_FRAGMENT_COMPLETE` event is delivered to the extension's content script via `window.postMessage`.
- **Censorship Detection**: `SseParser.parseLine()` (`content/sse-parser.js`) parses the `CONTENT_FILTER` status from SSE data lines. This parser was originally a private method `_parseSseEvent()` of `censor-reply-restore.js`; after extraction into a standalone module, the original method briefly remained as dead code and was deleted in v4.11.3. DOM-level detection: `_isCensored()` checks whether the 2nd and 5th buttons in the assistant message toolbar are both disabled (censorship signature). Button selection is compatible with both old and new design systems: first queries `.ds-icon-button` (old), then falls back to `[role="button"].ds-button.ds-button--icon` (new); disabled determination is "`ds-icon-button--disabled` class and `aria-disabled="true"` (old)" or "`ds-button--disabled` class (new, some disabled buttons lack the `aria-disabled` attribute)". `_getToolbarGroup()` primary selector is `.ds-flex._965abe9`, with a fallback that uses the same merged selector to find a `.ds-flex` containing 5 or more buttons.
- **Storage Records**: `_saveFragment()` saves censored messages to `chrome.storage.local` (key `restored_messages`), containing `message_id`, `fragments`, `thinking_elapsed_secs`, `chat_session_id`, `prompt_key` (normalized user prompt). The record key is session-scoped: `_recordKey(sessionId, messageId)` produces `"<session>::<message_id>"` (with `nosession` prefix when session is null), because `message_id` is a per-conversation sequence number that necessarily collides across conversations — all reads and writes (save, injection lookup, storage matching) consistently use this composite key. A maximum of 200 records are retained (`_evictOldest()`).
- **Real-Time Restoration**: After the SSE event completes, `_onFragmentComplete()` pushes the `message_id` onto `_pendingQueue`; `_tryRestoreMessage()` queries and injects the original content when the corresponding element appears in the DOM.
- **message_id Resolution Order**: `_getMessageIdFromElement()` checks in order: `_keyToMessageId` (runtime cache) → `_resolveMessageIdFromStorage()` (matches storage records using URL session id + normalized prompt_key; writes back to `_keyToMessageId` on hit; already-claimed message_ids are skipped) → `_pendingQueue.shift()` (last resort only), preventing the queue ID from an in-flight XHR from being incorrectly assigned to an older unrestored message. Each successful resolution logs the source path (`map` / `storage` / `queue`) with the `[DV:CensorRestore]` prefix.
- **Queue Synchronous Cleanup**: When resolution succeeds via the map or storage path, all entries with the same messageId are synchronously removed from `_pendingQueue` (with logging). Queue entries would originally only be consumed by the queue fallback path's `.shift()`; if an element resolves via another path, residual entries would be blindly applied to the next "element appearing before fragment" censored message, causing same-conversation content misalignment.
- **Queue Fallback Validation**: Before consuming from `_pendingQueue`, the queue head is peeked at: if the element can obtain a prompt key via `_getPrecedingUserPromptKey()`, and the candidate messageId's storage record exists with a mismatching `prompt_key`, consumption is refused (with logging) and null is returned, allowing that element's own fragment to arrive and be correctly injected via rescan; only when the element cannot obtain a prompt key (DOM variant) or the candidate has no storage record does the original blind consumption behavior remain.
- **Session Strict Matching**: When either the record's `chat_session_id` or the current URL's session id is null, storage matching never succeeds (`_resolveMessageIdFromStorage()` returns null, `_tryRestoreFromStoredRecords()` returns immediately), preventing two conversations that have not yet obtained their session ids from mismatching via `null === null`.
- **SPA Conversation Switch Cleanup**: `_checkSessionChange()` checks at the entry points of `_tryRestoreMessage()`, `_onFragmentComplete()`, and `_tryRestoreFromStoredRecords()` whether the URL session has changed. `data-virtual-list-item-key` is an index reused per conversation, so when switching conversations (non-null → different non-null, or non-null → null), `_keyToMessageId` and `_pendingQueue` must be cleared and `_storedRecordsApplied` must be reset to prevent residual mappings from injecting content from the previous conversation into the new one; null → non-null (new conversation just obtained its session id) only updates `_currentSessionId` and preserves the queue, because the first message's fragment may have already been enqueued before the URL update.
- **Refresh Restoration**: Chat history is typically rendered by React after the content script has started, so refresh restoration is ensured by two paths:
  - Startup path: `enable()` → `applyToExisting()` calls `_tryRestoreFromStoredRecords()` once (no effect if DOM has not yet rendered at that point).
  - Observer fallback path: When the MutationObserver detects a censored message and `_getMessageIdFromElement()` finds no ID, `_tryRestoreMessage()` triggers `_tryRestoreFromStoredRecords()` for a full match; the `_storedRecordsApplied` flag prevents redundant scans, and the flag is reset on each `_onFragmentComplete()`.
- **Storage Record Matching Flow** (`_tryRestoreFromStoredRecords()`, with `[DV:CensorRestore]` diagnostic logs at each decision point):
  1. Parse `chat_session_id` from the URL.
  2. Collect unrestored, censored assistant messages in the DOM.
  3. Obtain each assistant message's preceding user prompt as an anchor via `_getPrecedingUserPromptKey()`.
  4. Group records by `chat_session_id` + `prompt_key`; within each group, pair by ascending `message_id` order.
  5. Positional pairing occurs only within the same prompt group, preventing cross-conversation content misalignment.
- **Content Injection**: `_injectRestoredContent()` hides the original censored content (`.dss-censored-hidden`) and inserts the restored HTML, containing:
  - **RESPONSE** fragments: The original Markdown is rendered to HTML via `_renderMarkdown()`, with a "⚠ Content Restored" badge appended.
  - **THINK** fragments: If a thinking process exists, `_buildThinkBlock()` rebuilds a collapsible thinking block displaying the thinking time.
- **Old Key Migration**: `_loadRestoredMessages()` detects old-style bare message_id keys not containing `::` during loading, re-keys them using the record's embedded `chat_session_id` (null → `nosession::`, which by strict matching rules never matches, naturally expiring through LRU), and writes them back to storage in a single batch.

## 21. Temporary Conversation

- **Purpose**: When enabled, conversations **newly created from the homepage** by the user are marked as temporary; upon leaving a temporary conversation, the extension automatically calls `POST https://chat.deepseek.com/api/v0/chat_session/delete` (body `{ "chat_session_id": "<uuid>" }`) to delete it, achieving "no history" ad-hoc questioning.
- **Temporary Conversation Determination (Only Newly Created Conversations Are Deleted)**: Whether a conversation is temporary is authoritatively determined by whether a new-conversation API (`/api/v0/chat_session/create`) request was observed. Opening a history conversation from the list calls `/api/v0/chat/history_messages` and is **never marked, never deleted**. Minimal risk principle: if no create request is observed, the conversation is treated as historical.
- **Overall Gating (Default Off)**: The behavior of marking new conversations is controlled by the homepage toggle, which defaults to off. However, if a "tracked temporary conversation" already exists, even if the toggle is turned off, leaving that conversation still deletes it (the mark follows the conversation lifecycle); only when there is no tracked conversation and the toggle is off does the system fully detach listeners.
- **Shared Contract** (`utils/temporary-chat-constants.js`, loaded first to ensure global constants are ready):
  - `DSS_TEMP_CHAT_STORAGE_KEY = 'dss-temporary-chat-enabled'`: `chrome.storage.local` key (v4.9.0 migrated from sessionStorage to chrome.storage.local), value `true`/`false`.
  - `DSS_TEMP_CHAT_CHANGED_EVENT = 'dss-temporary-chat-changed'`
  - `DSS_TEMP_CHAT_UUID_KEY = 'dss-temporary-chat-uuid'`: sessionStorage key.
  - `DSS_CHAT_CREATE_MESSAGE_TYPE = 'DSS_CHAT_CREATE_DETECTED'`
  - `DSS_CHAT_CREATE_ENDPOINT = '/api/v0/chat_session/create'`
  - `DSS_CHAT_COMPLETION_MESSAGE_TYPE`: completion API endpoint for matching
  - `DSS_FIBER_DELETE_MESSAGE_TYPE` / `DSS_FIBER_DELETE_RESULT_TYPE`: Fiber deletion related
  - `DSS_PENDING_DELETES_SYNC_KEY`: cross-device pending-delete queue sync key
  - `DSS_LAST_AUTH_TOKEN_KEY`: local auth token storage key (`chrome.storage.local` only)
  - `DSS_OPEN_TEMP_UUIDS_KEY`: local set of open conversation UUIDs
  - `DSS_SCHEDULE_DELETE_RETRY_MESSAGE_TYPE`: Service Worker scheduled retry message
  - `DSS_MSG_TRACK_FOR_DELETION = 'DSS_TRACK_FOR_DELETION'` (payload `{uuid}`): registers as pending-delete and adds to the local open set
  - `DSS_MSG_REMOVE_PENDING_DELETE = 'DSS_REMOVE_PENDING_DELETE'` (payload `{uuid}`): removes from the cross-device pending-delete queue
  - `DSS_MSG_REMOVE_OPEN_UUID = 'DSS_REMOVE_OPEN_UUID'` (payload `{uuid}`): removes from the local open UUID set
  - `DSS_MSG_SET_LAST_AUTH_TOKEN = 'DSS_SET_LAST_AUTH_TOKEN'` (payload `{token}`): updates the local most-recent valid bearer token cache
  - `DSS_MSG_HEARTBEAT = 'DSS_HEARTBEAT'` (payload `{uuid}`): renews the lease for that conversation
  - `DSS_MSG_RELEASE_LEASE = 'DSS_RELEASE_LEASE'` (payload `{uuid}`): zeroes the lease timestamp, allowing any device to take over immediately
  - `DSS_MSG_GET_PENDING_UUIDS = 'DSS_GET_PENDING_UUIDS'`: requests the current list of UUIDs in the pending-delete queue from the background
  - `DSS_MSG_PENDING_UUIDS_CHANGED = 'DSS_PENDING_UUIDS_CHANGED'` (payload `{uuids}`): pushed by the background to all tabs when the queue changes
  - `LEASE_TTL_MS = 600000` (10 minutes): lease time-to-live
  - `HEARTBEAT_INTERVAL_MS = 60000` (1 minute): heartbeat renewal interval
  - Constants are explicitly mounted on globalThis via `Object.assign(globalThis, DSS_TEMP_CHAT_CONSTANTS)`: a classic script's top-level `const` does not become a globalThis property, and when consumed via `importScripts` in the service worker, `globalThis[name]` must be used for resolution.
- **Toggle UI** (`content/temporary-chat-toggle.js` + `.css`): Displayed only when `pathname === '/'` (homepage). Text 14px / weight 500, off state `#f9fafb`, on state `#679efe`; toggle track on state `#4d6bfe`. Style selectors are all prefixed with `.dss-temp-chat-*` for isolation.
  - **SPA Injection/Removal**: The Navigation API `navigate` event (supplemented by `popstate` and `MutationObserver`) re-evaluates on each navigation: when `pathname === '/'`, waits for `div.aaff8b8f` to appear then injects 38px below it (deduplicated by id); when `pathname !== '/'`, removes the toggle row. Removal only deletes the DOM element, **does not change the enabled flag** (that flag is held by `TemporaryChatEnabledFlag` in `chrome.storage.local`); on re-injection, the visual state is restored from the persisted flag. The flag is broadcast-synced to every tab via the background and cached in memory, so `readEnabledFlag()` can be synchronous.
  - **Diagnostic Logs**: Outputs `[DV:TempChatToggle]` prefixed logs at decision points including init / navigation / anchor query / injection / removal / observer disconnect detection, for investigating "toggle occasionally not appearing, only appearing after refresh" in real browsers.
- **Creation Detection and Auth Capture** (`content/censor-xhr-hook.js`, main world):
  - Reuses interception of `setRequestHeader('authorization', ...)`, broadcasting via `window.postMessage({ type: 'DSS_AUTH_CAPTURED', authorization })`; `temporary-chat-delete.js` consumes and caches the token only when needed.
  - Also detects requests whose URL contains `/api/v0/chat_session/create` (intercepting both `XMLHttpRequest.prototype.open` and wrapping `window.fetch`), broadcasting `DSS_CHAT_CREATE_DETECTED` on match.
- **Marking and Deletion Logic** (`content/temporary-chat-delete.js`):
  - `deleteChatSession(chatUuid, { keepalive })`: guard clause returns without sending if token or chatUuid is missing; uses `fetch` POST with authorization and x-client-* headers.
  - **Marking**: When `DSS_CHAT_CREATE_DETECTED` is received and the toggle is on, sets pending; when the Navigation API `navigate` lands on `/a/chat/s/<uuid>`, writes that UUID to `DSS_TEMP_CHAT_UUID_KEY` as the tracked target and clears pending.
  - **Delete on Leave**: The `navigate` event calculates the `fromUuid` before leaving and the destination URL; when "not a reload", "not navigating to the same conversation", `fromUuid` matches the tracked temporary UUID, and the token has been captured, it deletes and clears the tracked UUID.
  - **Same URL / Refresh Does Not Delete (Bug Fix)**: When `navigationType === 'reload'` or the destination URL equals the current URL (including pressing the current conversation URL in the address bar), deletion is skipped and a suppression flag blocks subsequent `beforeunload` deletion; F5 / Ctrl+R / Cmd+R keyboard detection serves as a second layer of insurance.
  - **Navigating to Same Conversation Does Not Delete (Bug Fix, v4.9.1)**: `handleNavigationEvent` extracts `destUuid` from the destination URL's `/a/chat/s/{uuid}`, using `isSameConversation = destUuid === _trackedTemporaryUuid` as the guard. As long as the destination is the same tracked conversation (even if only the query string or hash differs, such as `?model=v3`, `#msg-42`), deletion is skipped, replacing the previous fragile check that only compared full URL string equality; `extractUuidFromUrl` is correspondingly extended to accept an optional full URL parameter. This guard does not affect existing behavior for "navigating to another page still deletes" and "closing the tab still deletes."
  - `beforeunload`: Covers closing the tab/browser and full-page navigation; when the current UUID equals the tracked UUID, is not suppressed, and has a token, deletes with `keepalive: true`.
- **Lifecycle**: Listeners remain mounted when either "toggle is on" or "a tracked temporary UUID exists"; marking new conversations occurs only when the toggle is on; deleting already-tracked conversations is unaffected by the toggle being off; listeners are detached only when the tracked target is cleared and the toggle is off.
- **Independence**: This feature is not linked to the popup menu's top-right master switch and is independently controlled by its own homepage toggle.
- **Two-Layer Deletion Architecture (v4.9.0)**:
  - **Layer 1 (Real-Time Path, Content Script)**: SPA navigation continues to use Fiber/API deletion; `beforeunload` (closing tab/browser) switches to direct `fetch(keepalive: true)`, eliminating IPC race conditions by no longer going through the Service Worker. Items are removed from the pending-delete queue only upon successful deletion (API explicitly returns success).
  - **Layer 2 (Remediation Path, Service Worker, Triggered Only on `onStartup`)**: Extends the existing `chrome.runtime.onStartup` listener (originally for cloud preset sync) to read the shared pending-delete queue and retry deletions one by one using the local `dss-last-auth-token`; items are removed only upon confirmed success; failures increment `attemptCount` and are retained for the next remediation.
  - **Cross-Device Single Source of Truth**: The pending-delete queue (`dss-pending-deletes-sync`) exists only in `chrome.storage.sync`, with no local-only copy; any device logged into the same Chrome account can use its own `dss-last-auth-token` to remediate any item in the queue, regardless of which device marked it.
  - **Sync-Change Safeguard**: `chrome.storage.onChanged` (sync area) triggers a remediation scan, mitigating the race condition where `chrome.storage.sync` may not have completed cloud hydration at `onStartup` cold start; the scan only deletes items whose leases have expired (see "Leases and Heartbeats" below), so conversations in active use are protected on any device.
  - **Open Conversation Guard Storage Layout (v4.15.1)**: Each open UUID occupies its own `chrome.storage.local` key (prefix `dss-open-temp-uuid:`); adding writes only its own key, removing deletes only its own key. The old version stored the entire list in a single array key `dss-open-temp-uuids` and rewrote the whole thing on each add/remove; any context reading a stale snapshot would lose other tabs' entries, causing active conversations to lose guard protection and be deleted by scans. The new version has no read-modify-write and therefore no such loss. The old array key is converted to read-only and union-merged during reads (conversations alive at upgrade time retain their guard); `clearOpenUuids()` also clears it.
  - **Privacy Boundary**: `authToken` exists only in `chrome.storage.local` (`dss-last-auth-token`), never synced via `chrome.storage.sync`; the shared queue contains only non-sensitive `chatUuid`, `attemptCount`, and lease timestamp `lastActiveAt`.
  - **Storage Responsibility Belongs to the Service Worker**: `background/pending-store.js` is no longer in the `manifest.json` `content_scripts` list and is loaded only by `background/service-worker.js` via `importScripts`, so `TemporaryChatPendingStore` (and all its `chrome.storage.*` calls) exists only in the worker context. The content layer uses the four message types above for writes and no longer directly touches `chrome.storage` (`chrome-extension-coding-guidelines` §1 layer boundary).
    - **Background Routing** (`background/pending-store-routes.js`): `install()` is called at the service worker top level (ensuring it survives worker restarts) and registers a single `chrome.runtime.onMessage` listener containing a `type` → store operation lookup table. Unknown types return `false` without responding, allowing other listeners in the worker to still handle them; known types return `true` and respond with `{ ok: true }` or `{ ok: false, error }` after awaiting completion. Missing dependencies (store layer or constants not loaded first) throw at resolution time, naming the file that should be loaded.
    - **Senders**: `temporary-chat-delete.tracking.js` sends `DSS_TRACK_FOR_DELETION`; `temporary-chat-delete.coordinator.js` sends two removal messages; `temporary-chat-delete.handlers.js` sends `DSS_SET_LAST_AUTH_TOKEN`.

- **Cross-Device Leases and Heartbeats (v4.31.1)**: The pending-delete queue is stored in `chrome.storage.sync` and propagates to other devices under the same Chrome account. To make the fact that "this conversation is currently in use" visible to all devices, queue items carry a lease timestamp.
  - **Queue Item Structure**: `{ chatUuid, attemptCount, lastActiveAt }`, where `lastActiveAt` is the lease timestamp in epoch milliseconds. `LEASE_TTL_MS` is set to a generous 10 minutes to absorb `chrome.storage.sync` propagation delay, background tab timer throttling, and cross-device clock skew in one margin.
  - **Store Layer API** (`background/pending-store.js`): `refreshLease(chatUuid)` renews the lease, `releaseLease(chatUuid)` zeroes `lastActiveAt`, and the pure function `isLeaseExpired(entry, now)` determines expiry — expired when `lastActiveAt` is not a finite number, or `now - lastActiveAt > LEASE_TTL_MS`; exactly equal to TTL is still valid. All read-modify-write operations on the queue are serialized via a promise-chain mutex gate, so multiple tabs sending messages simultaneously never interleave get/set and lose updates.
  - **Remediation Scans Are Always Lease-Gated** (`background/service-worker.js`): `remediatePendingDeletes()` no longer accepts parameters and only deletes items whose leases have expired; the three paths — `chrome.runtime.onStartup`, `dss-delete-retry` scheduled alarm, and sync-area `chrome.storage.onChanged` — all apply the same gate.
  - **Heartbeats** (`content/temporary-chat-heartbeat.js`, exports `{ start, stop }`): A tab tracking a temporary conversation immediately sends one `{type: 'DSS_HEARTBEAT', uuid}`, then sends one every `HEARTBEAT_INTERVAL_MS` thereafter; the service worker route calls `refreshLease` on receipt. Heartbeats start on `trackUuid()` and on the sessionStorage restoration path, and stop on tracking end or listener detachment. Because heartbeats are bound to the content script / tab lifecycle, they naturally stop when a tab crashes or is forcefully terminated, and the lease expires accordingly, requiring no device identifier.
  - **Fast Restart Recovery**: At `onStartup`, leases for each UUID in the local open set that are still in the queue are released first, then the local open set is cleared, and finally the remediation scan runs — conversations that were open on this device before shutdown are thus deleted immediately upon restart.
  - **Explicit Lease Release**: When the real-time deletion in the leave flow completely fails (Fiber deletion fails and API fallback retries are exhausted), the coordinator sends `DSS_RELEASE_LEASE` to zero the lease, allowing any device to take over immediately rather than waiting for TTL expiry.
- **Sidebar Hiding of Pending-Delete Conversations (v4.31.1)**: Conversations in the pending-delete queue are hidden in the DeepSeek sidebar on all devices, including the currently open one on the marking device — this is a deliberate product decision: in a real-time conversation context, switching to a temporary conversation being torn down serves no purpose.
  - **Data Source**: `background/service-worker.js` broadcasts queue UUIDs to all tabs on each sync queue change; `content/temporary-chat-sidebar-hide.js` (exports `{ init, stop }`, started by `content/content-script.js`) maintains an in-memory UUID set, initially fetched via `DSS_GET_PENDING_UUIDS` and subsequently updated by `DSS_PENDING_UUIDS_CHANGED` pushes.
  - **Group Collapse Rules**: The sidebar groups conversation anchors by date, with each group container containing one date label and one or more row anchors. Determination is per-container — when all anchors within a container are in the queue, the entire container is hidden and the date label disappears; as long as any anchor is not in the queue, only the individual pending-delete anchors are hidden. A group containing a single anchor treats that anchor being in the queue as all pending-delete.
  - **Hide Method**: Applies a `ds-` prefixed `ds-temp-chat-hidden` class paired with an injected `display: none !important` rule; nodes are always retained on the page. Each application first clears the class entirely then re-derives, so items leaving the queue cause groups to reappear and individual anchors to become visible again.
  - **Update Timing**: A `MutationObserver` is mounted on the sidebar container, coalescing dense changes to one application per animation frame.
  - **Selectors** (`content/ds-selectors.js`): `SIDEBAR_DATE_GROUP_SELECTOR` is the obfuscated class for date group containers; `SIDEBAR_CHAT_LINK_SELECTOR` locates anchors by `/a/chat/s/` href. If a DeepSeek update causes the group selector to mismatch, the feature degrades to per-anchor hiding — that path finds anchors by href and is unaffected by obfuscated class changes.
- **Known Limitations**:
  - `chrome.storage.sync` propagation delay (typically a few seconds) causes conversations to remain briefly visible on other devices until the queue arrives and they are hidden.
  - When Chrome sync is logged out or paused, cleanup degrades to single-device mode: the marking device still deletes its own conversations; other devices do not receive the queue and therefore no erroneous deletions occur.

## 23. Settings Read/Write via Messages (content → background)

General settings are likewise not read directly from storage by the content layer. Type constants are centralized in `utils/settings-message-constants.js`, published via `globalThis.DSS_SETTINGS_MSG` with three types: `GET_SETTINGS` / `SET_SETTINGS` / `SETTINGS_CHANGED`; both the content script and service worker load the same file, so neither side hardcodes strings.

- **Background Routing** (`background/settings-routes.js`, `install()` likewise called at the top level):
  - `DSS_GET_SETTINGS` (`{ keys: string[] }`): Reads specified keys from `chrome.storage.local`, filling missing ones with `StorageManager.DEFAULTS`; `dsWebSearchToggle` is corrected via the shared `normalizeWebsearchToggle()` before responding with `{ ok: true, values }`. Returns `{ ok: false, error }` if keys is not an array or is empty.
  - `DSS_SET_SETTINGS` (`{ values: object }`): Writes to `chrome.storage.local`; rejects if values is not an object, is an array, or has no keys.
  - **Change Broadcast**: The same `install()` registers `chrome.storage.onChanged`; when a monitored key changes, it forwards `{ type: DSS_SETTINGS_CHANGED, area, changes }` as-is to all `*://chat.deepseek.com/*` tabs. The monitored scope is: any `StorageManager.KEYS` value in the `local` area, plus `dss-temporary-chat-enabled`, and `dsPreset_` / `chatPresetMap_` prefixed keys regardless of area. Individual tab send failures are ignored without affecting other tabs.
- **Content-Side Shared Pipeline** (`content/feature-toggle.js`): `registerFeatureToggle({ ownKey, onEnable, onDisable })` registers a feature, requesting `isEnabled` and the feature's own key from the background; the effective condition is "master switch !== `false` and own key !== `false`" (not stored is treated as on). All features share a single `chrome.runtime.onMessage` listener, attached only on the first registration; callbacks are only invoked when the effective state truly transitions, and a single callback error does not interrupt other features. If the initial read fails, `masterValue` is pinned to `false`, keeping the feature dormant rather than enabling it with unknown settings. The returned `unregister()` is safe to call repeatedly. Features currently registered with `ownKey: null` (following master switch only) include `content/go-top.js` and `content/quote-reply.js`.
- **Temporary Conversation Enabled Flag** (`content/temporary-chat-enabled-flag.js`): Since its toggle is independent of the master switch, it directly uses the same message set without going through `registerFeatureToggle` — `initFromStorage()` fetches `dss-temporary-chat-enabled` via `DSS_GET_SETTINGS`, `write()` persists via `DSS_SET_SETTINGS` (updating the in-memory cache first so callers can read the new value before await returns), and `startSync()` converges on `DSS_SETTINGS_CHANGED` and notifies subscribers. Only boolean `true` is treated as enabled; truthy strings like `'true'` are always treated as disabled.
