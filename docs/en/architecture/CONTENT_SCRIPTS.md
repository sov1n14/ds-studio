> **Settings Access Boundary**: Feature modules' settings reads and writes are always relayed through the background — `DSS_GET_SETTINGS`/`DSS_SET_SETTINGS` sent to `background/settings-routes.js`, which broadcasts changes back to all DeepSeek tabs via `DSS_SETTINGS_CHANGED`; message type constants are centralized in `utils/settings-message-constants.js`. Toggle-type features are uniformly registered with `registerFeatureToggle({ ownKey, onEnable, onDisable })` from `content/feature-toggle.js`, effective when "master switch `isEnabled !== false` AND own key `!== false`" — **an unsaved own key is treated as enabled**. The temporary conversation's pending-delete queue follows the same pattern: the content side sends `DSS_TRACK_FOR_DELETION`/`DSS_REMOVE_PENDING_DELETE`/`DSS_REMOVE_OPEN_UUID`/`DSS_SET_LAST_AUTH_TOKEN`, delegated by `background/pending-store-routes.js` to the `TemporaryChatPendingStore` held by the service worker.
>

> **v4.11.9 Split**: `harvest.js` → `harvest.js` (entry, scroll-and-harvest engine) + `harvest.toast.js` (progress notification UI). The original file was 502 lines, exceeding `coding-guidelines` §8's 450-line proactive split threshold, and simultaneously carried two concerns: "harvest engine" and "toast UI"; after splitting, 426 lines + 102 lines, behavior unchanged.
>
> This uses the **pure-function method package** convention (same as `content-script.js`, `preset-overlay.controller.js`), different from the `this`-binding `Object.assign` method packages described above: `harvest.toast.js` is mounted on `globalThis.__DS_Harvest_toast`, and the entry file retrieves it via `globalThis.__DS_Harvest_toast || require('./harvest.toast.js')`, compatible with both browser and Node/vitest loading paths. In `manifest.json`, `harvest.toast.js` is ordered before `harvest.js`.

> **v4.19.0 Split**: `harvest.js` → `harvest.js` (entry, scroll-and-harvest engine, 446 lines) + `harvest.policy.js` (pure decision logic, 140 lines). What was extracted is the "should we continue scrolling or stop, and why" judgment: `createInitialState()`, `decideNextStep()`, `describeIncompleteReason()`. See the Harvest Policy Module section in [EXPORT.md](EXPORT.md).
>
> This split simultaneously addressed two issues — it was not splitting for splitting's sake. At that point `harvest.js` had reached 430 lines, approaching §8's 450-line threshold; the real motivation was that **the logic was originally untestable** — the stop decision was entangled with DOM scrolling, `MutationObserver`, and `Date.now()` inside the same async loop, and verifying "stop after 20 consecutive seconds of no progress" required building an entire virtual list with fake timers. After extracting as pure functions, the clock is injected via a `nowMs` parameter with zero DOM dependency, and 29 tests need no fixtures or fake timers. **The logic most in need of testing is exactly the logic that most needed to leave that file.**
>
> `harvest.policy.js` must maintain zero DOM, zero `chrome.*`, zero timers, zero clock reads. Adding a single `Date.now()` call for convenience would push this logic back to an untestable state. The namespace uses `window.DSstudio.HarvestPolicy` (following the `window.DSstudio.Harvest` convention); in `manifest.json` it is ordered before `harvest.js`.
>
> **v4.19.1 Split**: `harvest.js` → `harvest.js` (entry, harvest orchestration, 446 → 303 lines) + `harvest.dom.js` (DOM probing and measurement, 224 lines). What was moved out is the single concern of "reading or observing the page": `_findHarvestScrollContainer`, `_harvestVisibleMessages`, `_waitForDomStability`, `_isAtBottom`, the new `_measureMountedBottomOffset`, and the selectors and stability constants used only by them. Loop orchestration, policy wiring, toast calls, `PreventAutoScroll` lifecycle, and `harvestAllMessages()` itself remain in the entry file.
>
> The split was triggered by the adaptive stride feature needing measurement code, while `harvest.js` was already at 446 lines — adding more would exceed §8's 450-line threshold, so the split came before the addition. Uses the v4.11.9 **pure-function method package** convention (same as `harvest.toast.js`): the new file is wrapped in an IIFE, mounted on `root.__DS_Harvest_dom`, so it has **zero top-level identifiers** and cannot collide with other content scripts; the entry file retrieves it via `globalThis.__DS_Harvest_dom || require('./harvest.dom.js')`, compatible with both browser and Node/vitest.
>
> **Key constraint: the entry file re-exports every moved function under its original name**, with every `module.exports` key preserved. `test/unit/harvest.spec.js`'s 58 tests destructure-call these internal functions directly from the `harvest.js` module interface; re-exporting means those 58 tests need zero changes — which reduces the splitting risk to near zero. This is the reason this convention was chosen over directly changing call sites.
>
> Note that the two layers' handling of "`HarvestPolicy` absence" is **intentionally inconsistent**: `harvest.js` throws directly (the module cannot function without decision logic, and since it's a hard dependency loaded by the same manifest, absence means the manifest is broken — it should fail loudly); `content-script.export.js` falls back to a generic description and downloads anyway (it can still deliver the user's data). **Do not unify these two for consistency's sake.**

> **v4.11.15 Split**: `content-script.js` was originally 491 lines, exceeding `coding-guidelines` §8's 450-line threshold, while simultaneously carrying two concerns: "chat state" and "prompt injection". The latter was extracted to `prompt-injector.controller.js` (179 lines), reducing the entry file to 360 lines.
>
> The choice to extract "prompt injection" rather than "chat state" was because `test/unit/storage-manager.sync-now.spec.js` uses regex matching against the **source text literal** of `content-script.js` to capture its `initSettings` block; chat-state functions all surround `initSettings`, and moving them would break that assertion. Extracting the injection side leaves `initSettings` in place — zero risk.
>
> The new file uses the `createPromptInjector(ctx)` factory convention (same as `preset-overlay.controller.js`), accessing module state from the entry file via getter/setter closures; `isInjecting` is the only variable written by the new file, passed in as a paired getter + setter. All 16 `module.exports` keys are preserved, and the `content-script.*.spec.js` full series' default import usage remains unchanged.

> **v4.11.13 Shared Selectors**: `content/ds-selectors.js` is the sole DeepSeek DOM selector source for all content scripts, wrapped in an IIFE, exporting only constant strings (zero logic, zero side effects). Consumers include `go-top.js`, `harvest.dom.js`, `censor-reply-restore.*.js`, `content-script.export.js`, `prompt-injector.*.js`, `preset-overlay.*.js`, etc. Content is divided into three categories: semantic `ds-*` classes (`MESSAGE_SELECTOR`, `MARKDOWN_SELECTOR`, `THINK_CONTENT_SELECTOR`, `VISIBLE_ITEMS_SELECTOR`, `VIRTUAL_ITEM_KEY_ATTR`, etc.), obfuscated hash classes (`ASSISTANT_MESSAGE_SELECTOR`, `USER_CONTENT_SELECTOR`, `SCROLL_ROOT_SELECTOR`, `THINK_BLOCK_SELECTOR`, `CHAT_HEADER_SELECTOR`, `CONTENT_COLUMN_SELECTOR`, `FLOATING_BUTTON_BAR_SELECTOR`, etc.), and send-button structure (`SEND_BUTTON_ROLE_SELECTOR`, `SEND_BUTTON_ICON_SELECTOR`, `EDIT_SEND_BUTTON_VARIANT_CLASSES`, `BUTTON_DISABLED_CLASS`, etc.).
>
> The initial three constants explain why this file exists — `VIRTUAL_LIST_SELECTOR` (`.ds-virtual-list-items._6f2c522`), `VIRTUAL_LIST_FALLBACK` (`[class*="ds-virtual-list-items"]`), `SCROLL_AREA_CLASS` (`ds-scroll-area`). Previously the first two had identical literal values duplicated in `go-top.js` and `harvest.js`, while the third was hardcoded as inline strings in both `go-top.locate.js` and `harvest.js`, with the synchronization mechanism being nothing more than a comment. DeepSeek is a React application with hashed class names — when a version change breaks one copy, the other doesn't get fixed along with it, and the failure symptoms on both sides don't point to the real cause (go-top falls back to `document.scrollingElement`, the button appears clickable but scrolling doesn't work; harvest hits the `no_container` guard and export fails outright).
>
> The namespace uses `window.DSstudio.Selectors` (the convention for cross-module shared utilities, same as `prevent-auto-scroll-bridge.js`'s `window.DSstudio.PreventAutoScroll`), not the `globalThis.__DS_*` method package convention — the latter is for single-module multi-file splits sharing `this` bindings, which is a different nature.
>
> **v4.11.17 Fix (important convention)**: The initial version had `harvest.js` and `go-top.js` each declare `const __DSSelectors = ...` at the top level to obtain the shared constants. Both declared the same name at the **true top level**. `manifest.json`'s `content_scripts` are all loaded as classic scripts sharing the same global scope in the isolated world, so the second script (`go-top.js`) threw `SyntaxError: Identifier '__DSSelectors' has already been declared` and the entire script failed to execute — the "go to top" button never appeared. This has been fixed with unique identifiers for each; currently `go-top.js` declares `__DSSelectorsGoTop` at the top level, while the harvest side obtains the shared constants inside `harvest.dom.js`'s IIFE (declarations inside an IIFE don't enter the global scope and thus don't participate in collisions).
>
> This class of defect **cannot be structurally caught by unit tests** — under vitest each file is an independent module with its own scope, so collisions cannot be reproduced (all 1746 tests were green at the time). The gating mechanism is now provided by `test/unit/content-script-global-collisions.spec.js`: it uses the `manifest.json` list as the source of truth, statically scans each content script's top-level declarations, and fails if any two scripts share a name (declarations inside IIFEs are excluded, so `__DSSelectors` inside `go-top.locate.js` is unaffected). **Before adding any `const`/`let`/`var`/`function` at the top level of a content script not wrapped in an IIFE, first verify the name is unique across all content scripts.**
>
> **Deliberately not done**: `_findScrollContainer()` (go-top) and `_findHarvestScrollContainer()` (harvest) — the two walk-up functions — **remain independent** and have not been merged. Their strategy sets are not a subset relationship (go-top has 4 strategies including anchor starting point and sidebar guard; harvest has only 2 with no anchor concept), and their caching semantics differ (go-top caches on `this._scrollContainer` and deliberately does not cache the document fallback; harvest does not cache at all). Taking the union would silently disable two strategies in harvest, creating false consistency; taking the intersection would strip go-top's sidebar guard. Shared selectors and shared walk-up logic are two separable concerns — the former is safe, the latter is not.
