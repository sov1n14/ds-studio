> **Settings Access Boundary**: Feature modules' settings reads and writes are always relayed through the background — `DSS_GET_SETTINGS`/`DSS_SET_SETTINGS` sent to `background/settings-routes.js`, which broadcasts changes back to all DeepSeek tabs via `DSS_SETTINGS_CHANGED`; message type constants are centralized in `utils/message-constants.js`. Toggle-type features are uniformly registered with `registerFeatureToggle({ ownKey, onEnable, onDisable })` from `content/feature-toggle.js`, effective when "master switch `isEnabled !== false` AND own key `!== false`" — **an unsaved own key is treated as enabled**. The temporary conversation's pending-delete queue follows the same pattern: the content side sends `DSS_TRACK_FOR_DELETION`/`DSS_REMOVE_PENDING_DELETE`/`DSS_REMOVE_OPEN_UUID`/`DSS_SET_LAST_AUTH_TOKEN`, delegated by `background/pending-store-routes.js` to the `TemporaryChatPendingStore` held by the service worker.
>
> **Entry file + method packages** (v4.0.0): The following large content scripts use an "entry file + method packages" structure: method packages mount on `globalThis.__DS_*` and are merged by the entry file via `Object.assign`, with load order enforced in `manifest.json` as method packages before entry files. `harvest.js` (scroll-and-harvest engine) is likewise loaded via the `content_scripts` list in `manifest.json`:
>
> - `content-script.js` → `content-script.js` (entry/wiring layer, holds the sole body `MutationObserver`) + `content-script.export.js` (Markdown export) + `prompt-injector.controller.js` (prompt injection, v4.11.15) + `prompt-injector.send-button.js` (send button detection and interception) + `chat-binding-controller.js` (chat binding state machine, holds all mutable state)<!-- overlay consists of preset-overlay.controller.js/preset-overlay.resolvers.js/preset-overlay.styles.js, see ARCHITECTURE.md directory tree -->
> - `go-top.js` → `go-top.js` (entry) + `go-top.locate.js` (DOM query helpers, wrapper container location and visibility evaluation, incorporates scroll container location strategy and anchor detection) + `go-top.render.combined.js` (button construction, SVG icon, injection strategy, stack offset calculation, wrapper container observer and mode switching) + `go-top.scroll.js` (scroll animation engine) + `go-top.observers.js` (DOM mutation monitoring, scroll listeners, and route detection) + `go-top.lifecycle.js` (route change handling, enable/disable, DOM readiness polling, and lifecycle management)
> - `censor-reply-restore.js` → `censor-reply-restore.js` (entry) + `censor-reply-restore.keymap.js` (key ↔ messageId bidirectional mapping table) + `censor-reply-restore.markdown.js` (Markdown rendering) + `censor-reply-restore.dom.resolve.js` (messageId resolution, incorporates fragment extraction) + `censor-reply-restore.dom.inject.js` (restored content injection) + `censor-reply-restore.dom.scan.js` (full scan restore from storage records) + `censor-reply-restore.thinkblock.js` (thinking block widget, v4.11.12) + `censor-reply-restore.storage.js` (persistence) + `censor-reply-restore.detection.js` (censorship detection, toolbar location, preceding user prompt retrieval) + `censor-reply-restore.observer.js` (MutationObserver start/stop and DOM scan)
> - `mobile-sidebar-swipe.js` → `mobile-sidebar-swipe.js` (entry) + `mobile-sidebar-swipe.button.js` (sidebar toggle button discovery and DOM readiness polling) + `mobile-sidebar-swipe.gesture.js` (touch gesture handler) + `mobile-sidebar-swipe.bind.js` (touch event binding and unbinding) + `mobile-sidebar-swipe.lifecycle.js` (lifecycle methods)

> **Harvest toast module** (v4.11.9): `harvest.js` (entry, scroll-and-harvest engine) + `harvest.toast.js` (progress notification UI). Each file carries a single concern ("harvest engine" and "toast UI"), keeping `harvest.js` under `coding-guidelines` §8's 450-line proactive JS split threshold.
>
> This uses the **pure-function method package** convention (same as `content-script.js`, `preset-overlay.controller.js`), different from the `this`-binding `Object.assign` method packages described above: `harvest.toast.js` is mounted on `globalThis.__DS_Harvest_toast`, and the entry file retrieves it via `globalThis.__DS_Harvest_toast || require('./harvest.toast.js')`, compatible with both browser and Node/vitest loading paths. In `manifest.json`, `harvest.toast.js` is ordered before `harvest.js`.

> **Harvest decision module** (v4.19.0): `harvest.js` (entry, scroll-and-harvest engine) + `harvest.policy.js` (pure decision logic). `harvest.policy.js` owns the "should we continue scrolling or stop, and why" judgment: `createInitialState()`, `decideNextStep()`, `describeIncompleteReason()`, `computeScrollStep()`. See the Harvest Policy Module section in [EXPORT.md](EXPORT.md).
>
> The decision logic is a separate pure module so that it is testable: entangled with DOM scrolling, `MutationObserver`, and `Date.now()` inside one async loop, verifying "stop after 20 consecutive seconds of no progress" would require building an entire virtual list with fake timers; as pure functions, the clock is injected via a `nowMs` parameter with zero DOM dependency, and the tests need no fixtures or fake timers. **The logic most in need of testing is exactly the logic that most needs to live outside that file.**
>
> `harvest.policy.js` must maintain zero DOM, zero `chrome.*`, zero timers, zero clock reads. Adding a single `Date.now()` call for convenience would push this logic back to an untestable state. The namespace uses `window.DSstudio.HarvestPolicy` (following the `window.DSstudio.Harvest` convention); in `manifest.json` it is ordered before `harvest.js`.
>
> **Harvest DOM module** (v4.19.1): `harvest.js` (entry, harvest orchestration) + `harvest.dom.js` (DOM probing and measurement). `harvest.dom.js` carries the single concern of "reading or observing the page": `_findHarvestScrollContainer`, `_harvestVisibleMessages`, `_waitForDomStability`, `_isAtBottom`, `_measureMountedBottomOffset`, and the selectors and stability constants used only by them. Loop orchestration, policy wiring, toast calls, `PreventAutoScroll` lifecycle, and `harvestAllMessages()` itself live in the entry file.
>
> DOM measurement code (including the measurements adaptive stride needs) lives in `harvest.dom.js`, keeping `harvest.js` under §8's 450-line threshold. Uses the same **pure-function method package** convention as `harvest.toast.js`: `harvest.dom.js` is wrapped in an IIFE, mounted on `root.__DS_Harvest_dom`, so it has **zero top-level identifiers** and cannot collide with other content scripts; the entry file retrieves it via `globalThis.__DS_Harvest_dom || require('./harvest.dom.js')`, compatible with both browser and Node/vitest.
>
> **Key constraint: the entry file's `module.exports` re-exports `_findHarvestScrollContainer`, `_harvestVisibleMessages`, `_waitForDomStability`, and `_isAtBottom` under their original names**. `test/unit/harvest.spec.js` destructure-calls these internal functions directly from the `harvest.js` module interface; re-exporting keeps those tests independent of which file each function lives in.
>
> Note that the two layers' handling of "`HarvestPolicy` absence" is **intentionally inconsistent**: `harvest.js` throws directly (the module cannot function without decision logic, and since it's a hard dependency loaded by the same manifest, absence means the manifest is broken — it should fail loudly); `content-script.export.js` falls back to a generic description and downloads anyway (it can still deliver the user's data). **Do not unify these two for consistency's sake.**

> **Prompt injection module** (v4.11.15): `content-script.js` carries settings initialization and wiring (`initSettings()`, settings-change handling), while prompt injection lives in `prompt-injector.controller.js`, keeping the entry file under `coding-guidelines` §8's 450-line threshold.
>
> `initSettings()` stays in `content-script.js`: `test/unit/storage-manager.sync-now.spec.js` uses regex matching against the **source text literal** of `content-script.js` to capture the `async function initSettings()` block and asserts that it calls `StorageManager.syncNow()`; moving that function would break the assertion.
>
> `prompt-injector.controller.js` uses the `createPromptInjector(ctx)` factory convention (same as `preset-overlay.controller.js`), reading and writing `ChatBinding` state via getter/setter closures; `isInjecting` is the only state written by the injection module, passed in as the paired `getIsInjecting`/`setIsInjecting`.

> **Shared Selectors** (v4.11.13): `content/ds-selectors.js` is the sole DeepSeek DOM selector source for all content scripts, wrapped in an IIFE, exporting only constant strings (zero logic, zero side effects). Consumers include `go-top.js`, `harvest.dom.js`, `censor-reply-restore.*.js`, `content-script.export.js`, `prompt-injector.*.js`, `preset-overlay.*.js`, etc. Content is divided into three categories: semantic `ds-*` classes (`MESSAGE_SELECTOR`, `MARKDOWN_SELECTOR`, `THINK_CONTENT_SELECTOR`, `VISIBLE_ITEMS_SELECTOR`, `VIRTUAL_ITEM_KEY_ATTR`, etc.), obfuscated hash classes (`ASSISTANT_MESSAGE_SELECTOR`, `USER_CONTENT_SELECTOR`, `SCROLL_ROOT_SELECTOR`, `THINK_BLOCK_SELECTOR`, `CHAT_HEADER_SELECTOR`, `CONTENT_COLUMN_SELECTOR`, `FLOATING_BUTTON_BAR_SELECTOR`, etc.), and send-button structure (`SEND_BUTTON_ROLE_SELECTOR`, `SEND_BUTTON_ICON_SELECTOR`, `EDIT_SEND_BUTTON_VARIANT_CLASSES`, `BUTTON_DISABLED_CLASS`, etc.).
>
> The three scroll-container constants explain why this file exists — `VIRTUAL_LIST_SELECTOR` (`.ds-virtual-list-items._6f2c522`), `VIRTUAL_LIST_FALLBACK` (`[class*="ds-virtual-list-items"]`), `SCROLL_AREA_CLASS` (`ds-scroll-area`) are used by both go-top (`go-top.js`, `go-top.locate.js`) and harvest (`harvest.dom.js`). DeepSeek is a React application with hashed class names — if each side held its own copy of the literals, fixing one copy after a site update would leave the other broken, and the failure symptoms on both sides don't point to the real cause (go-top falls back to `document.scrollingElement`, the button appears clickable but scrolling doesn't work; harvest hits the `no_container` guard and export fails outright). A single source means one fix covers both sides.
>
> The namespace uses `window.DSstudio.Selectors` (the convention for cross-module shared utilities, same as `prevent-auto-scroll-bridge.js`'s `window.DSstudio.PreventAutoScroll`), not the `globalThis.__DS_*` method package convention — the latter is for single-module multi-file splits sharing `this` bindings, which is a different nature.
>
> **Unique top-level identifiers (important convention, v4.11.17)**: `manifest.json`'s `content_scripts` are all loaded as classic scripts sharing the same global scope in the isolated world. When any two scripts declare the same name at the **true top level**, the later one throws `SyntaxError: Identifier '…' has already been declared` and the entire script fails to execute (for example, a collision in `go-top.js` means the "go to top" button never appears). Each identifier used to obtain the shared constants is therefore unique: `go-top.js` declares `__DSSelectorsGoTop` at the top level, while `go-top.locate.js`, `go-top.render.combined.js`, and `harvest.dom.js` obtain the shared constants inside an IIFE (declarations inside an IIFE don't enter the global scope and thus don't participate in collisions).
>
> This class of defect **cannot be structurally caught by unit tests** — under vitest each file is an independent module with its own scope, so collisions cannot be reproduced, and a fully green suite does not rule out a name collision. The gating mechanism is provided by `test/unit/content-script-global-collisions.spec.js`: it uses the `manifest.json` list as the source of truth, statically scans each content script's top-level declarations, and fails if any two scripts share a name (declarations inside IIFEs are excluded, so `__DSSelectors` inside `go-top.locate.js` is unaffected). **Before adding any `const`/`let`/`var`/`function` at the top level of a content script not wrapped in an IIFE, first verify the name is unique across all content scripts.**
>
> **Deliberately not done**: `_findScrollContainer()` (go-top) and `_findHarvestScrollContainer()` (harvest) — the two walk-up functions — **remain independent** and have not been merged. Their strategy sets are not a subset relationship (go-top has 4 strategies including anchor starting point and sidebar guard; harvest has only 2 with no anchor concept), and their caching semantics differ (go-top caches on `this._scrollContainer` and deliberately does not cache the document fallback; harvest does not cache at all). Taking the union would silently disable two strategies in harvest, creating false consistency; taking the intersection would strip go-top's sidebar guard. Shared selectors and shared walk-up logic are two separable concerns — the former is safe, the latter is not.
