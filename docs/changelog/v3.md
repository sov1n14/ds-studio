# v3.x 版本變更記錄

## [3.4.0] - 2026-06-13

### 新增

- **編輯框捲動定位** (`content/edit-message-cleanup.js`)：點擊編輯按鈕後，編輯框現在會捲動到視覺上位於固定標頭 `._2be88ba` 下方 16px 的位置（`requirement.md` 第 9 行）。由於 `.cc852ac5` 位於可捲動容器（`ds-virtual-list-items _6f2c522`）內，而 `._2be88ba` 為固定定位（不同的 z 圖層），對齊是透過調整容器的 `scrollTop` 達成，而非重新定位元素。新的純函式 `computeScrollDelta(editBoxTop, headerBottom, gap)` = `editBoxTop − (headerBottom + gap)`；輔助函式 `findScrollableAncestor(el)` 解析真正的捲動容器（從 `._6f2c522` 開始，最近一個 `scrollHeight > clientHeight` 的祖先，備援為 `._6f2c522` 本身）；套用函式 `applyEditScrollPosition(root)` 即時讀取 `getBoundingClientRect()` 幾何資訊並調整 `scrollTop`。在 `handleEditButtonClick` 中，於 `max-height` 與包裹清理步驟之後，放在 `requestAnimationFrame` 內執行。編輯框／標頭／捲動容器缺失時不做任何事。只調整一次，不監聽縮放或捲動。新增常數 `EDIT_SCROLL_GAP_PX`（`16`）。

### 變更（測試）

- **單元測試** (`test/unit/edit-message-cleanup.spec.js`)：新增 16 個測試（G 組），涵蓋 `EDIT_SCROLL_GAP_PX`、`computeScrollDelta`（正值／負值／零／小數差值、gap 參數）與 `applyEditScrollPosition`（`scrollTop` 精確增量、可捲動祖先的走訪與備援、元素缺失防護、`root` 為 `null` 時的備援）。該檔案共 78 個測試；完整測試套件共 985 個測試，全數通過。

### 變更（manifest）

- **`manifest.json`**：版本 3.3.0 → 3.4.0。

## [3.3.0] - 2026-06-13

### 變更

- **編輯訊息的 `max-height` 行為** (`content/edit-message-cleanup.js`)：點擊編輯後的版面調整，由「移除 `.cc852ac5` 與 `._646a522` 兩者的 `max-height`」改為分開處理。`.cc852ac5` 仍移除其 `max-height`（`style.maxHeight = 'none'`，所有符合的元素）。`._646a522` 的 `max-height` 現在改為「設定」成偵測當下計算一次的動態值：`window.innerHeight − height(._2be88ba) − height(._871cbca) − 32`px，三個高度皆即時讀取（`window.innerHeight`，以及第一個 `._2be88ba` 與第一個 `._871cbca` 的 `getBoundingClientRect().height`）。只要「任一」來源元素缺失，就完全略過 `._646a522` 的調整（`.cc852ac5` 的移除仍會執行）。只計算一次，不監聽縮放。重構：以 `applyMaxHeightAdjustments(root)` 加上純函式 `computeDynamicMaxHeight(windowHeight, sourceHeightA, sourceHeightB)` 取代 `removeMaxHeightConstraints`／`MAX_HEIGHT_SELECTORS`，並新增常數 `REMOVE_MAX_HEIGHT_SELECTOR`（`.cc852ac5`）、`DYNAMIC_MAX_HEIGHT_SELECTOR`（`._646a522`）、`HEIGHT_SOURCE_SELECTOR_A`（`._2be88ba`）、`HEIGHT_SOURCE_SELECTOR_B`（`._871cbca`）、`MAX_HEIGHT_OFFSET_PX`（`32`）。

### 移除

## [3.2.3] - 2026-06-13

### 修正

- **編輯訊息清理抓錯 textarea，導致兩項子功能都失效** (`content/edit-message-cleanup.js`)：透過主控台日誌確認，點擊編輯按鈕當下頁面上唯一的 textarea 是底部的主要輸入框，而 `findMessageContainer` 往上走到一個範圍過大、早已包含它的虛擬清單祖先（`_2bd7b35`），因此 `waitForTextareaInContainer` 同步解析到空的主要輸入框（值為 `""`），`<user-input>` 正規表示式從未比對成功，`.cc852ac5`／`._646a522` 也比對到 0 個元素（編輯介面尚未掛載）。修正：以基於快照、不依賴 class 的偵測器取代往上走訪祖先的策略。`handleEditButtonClick` 先對現有的 textarea 做快照，接著 `waitForNewTextarea(preExisting, onFound)` 監看 `document.body`，解析到第一個「不在」快照中的 textarea（真正的編輯框），並以次要的 `VALUE_WAIT_TIMEOUT_MS`（800ms）等待 React 延後填入值。`max-height` 移除改到這個（正確的）偵測時間點執行。移除 `findMessageContainer`／`waitForTextareaInContainer`；新增 `waitForNewTextarea`；`applyTextareaCleanup` 現在回傳布林值。

- **編輯訊息清理** (`content/edit-message-cleanup.js`，新檔案)：使用者點擊 DeepSeek 先前送出訊息的編輯按鈕時，編輯 textarea 會預先填入「完整」的注入 payload（`<system-prompt>...</system-prompt>` + `<user-input>\n...\n</user-input>` 包裹）。本模組會移除包裹，讓使用者只編輯自己的原始文字。單一的文件層級委派點擊監聽器透過 `e.target.closest('.d4910adc')`（混淆過的編輯按鈕 class）解析編輯按鈕。點擊編輯時會 (1) 將每個 `.cc852ac5` 與 `._646a522` 元素的內嵌樣式設為 `style.maxHeight = 'none'`，移除 `max-height` 限制（之後不還原）；(2) 定位非同步渲染的編輯 textarea：從按鈕往上走到外層的訊息容器（`findMessageContainer`），再以 `MutationObserver` 監看，硬性逾時為 2000ms（`DETECTION_TIMEOUT_MS`；textarea 已存在時走同步路徑）。找到後，若值符合 `/<user-input>\n([\s\S]*)\n<\/user-input>$/`，就透過原生的 `value` 設定器加上派送 `input`／`change` 事件，將 textarea 改寫為「只有」內部內容（與 `injectPrefix`／`quote-reply.js` 相同、能被 React 感知的技巧）。若「沒有」`<user-input>` 包裹，textarea 內容完全不動（明確要求）。監聽器註冊透過 `window` 防護確保冪等；每次點擊的 observer／逾時狀態保存在處理器閉包內（無模組層級的可變狀態）。供測試使用的匯出：`extractUserInput`、`removeMaxHeightConstraints`、`applyTextareaCleanup`、`findMessageContainer`、`waitForTextareaInContainer`、`handleEditButtonClick`，以及常數 `EDIT_BUTTON_CLASS`、`MAX_HEIGHT_SELECTORS`、`USER_INPUT_REGEX`、`DETECTION_TIMEOUT_MS`。

## [3.1.2] - 2026-06-08

### 修正

- **切換對話（SPA 路由變更）後 GoToTop 按鈕未出現** (`content/go-top.js`)：在 DeepSeek 單頁應用程式中切換對話時，「回到頂端」按鈕會默默地沒有出現，即使初次載入頁面時一切正常。根本原因：由 `MutationObserver` + `popstate` 監聽器觸發的 `_onRouteChange()`，只以延遲 100ms 的單次呼叫執行 `_injectButton()`（加上 `_reattachScrollListener()` 與 `_evaluateVisibility()`），沒有任何把關或重試。當 `.aaff8b8f`（輸入區包裹容器）或 `._0706cde`（原生「回到底部」按鈕）尚未掛載時，`_injectButton()` 不做任何事並回傳 `false`，之後也不會再嘗試。修正方式是讓路由變更回呼改經由 `_tryConnectDom()`，它會以輸入區是否就緒把關，並每 500ms 重試一次、最多 120 次（約 60 秒）。`_tryConnectDom()` 的成功分支完整涵蓋舊的三步驟（注入 → 重新連接捲動容器 → 重新啟動監聽器 → 評估可見性），因此沒有遺漏任何功能。
- **3.1.2 版保留 `[GoToTop-DEBUG]` 日誌供使用者驗證**：確認後已於 3.1.3 移除。

### 移除

- **無用程式碼** (`content/go-top.js`)：確認 `_reattachScrollListener()` 沒有任何呼叫者（其唯一的舊呼叫者已在 3.1.0 的修正中改由 `_tryConnectDom()` 成功分支取代）。已刪除該方法及其 JSDoc 註解區塊。

### 變更

- **單元測試** (`test/unit/go-top.spec.js`)：以 6 個新測試取代 1 個過時測試（該測試斷言舊的、以 `setTimeout` 為基礎的單次注入三步驟），驗證 `_onRouteChange()` 在路由變更時驅動有把關的 `_tryConnectDom()` 重試：包裹容器不存在 → 排定重試；包裹容器出現 → 注入成功；包裹容器已存在 → 立即注入；原生按鈕已存在 → 立即注入；重新注入前先清除舊按鈕。測試套件：47 個檔案共 893 個測試，全數通過。
- **`manifest.json`**：版本 3.1.1 → 3.1.2。

## [3.1.0] - 2026-06-08

### 修正

- **開啟既有對話時「回到頂端」按鈕渲染在錯誤位置** (`content/go-top.js`)：直接以網址開啟對話時，「回到頂端」按鈕經常以浮動 overlay 的形式渲染在錯誤位置，而重新整理頁面後卻能正確渲染，屬於競爭條件。根本原因：`_tryConnectDom()` 只要 `_getAnchor()`（第一則訊息）存在就注入按鈕，但底部輸入區包裹容器 `.aaff8b8f` 與原生「回到底部」按鈕 `._0706cde` 會稍晚才渲染。兩個錨點都還不存在時，`_injectButton()` 會落入固定定位備援（`_injectAsFallback()`／`dsw-gotop--fixed`），將按鈕附加到第一個 `.ds-theme` 元素，而那是一個 `ds-notification-container ds-theme` 通知 overlay，之後也沒有任何機制能救回。修正後重新把關注入，只有在 `.aaff8b8f` 或原生按鈕存在時才建立按鈕；重試上限由 20 提高到 120（`RETRY_INTERVAL` 維持 500 ms，總計約 60 s），放棄時完全「不」注入按鈕（移除舊的「超過上限後注入降級按鈕」分支）。刪除整條固定定位備援路徑：`_injectAsFallback()`、`dsw-gotop--fixed` CSS 規則，以及每個 `_injectionMode === 'fixed'` 分支；兩個錨點都不存在時，`_injectButton()` 現在不做任何事並回傳 `false`。

### 變更

- **「回到頂端」捲動改為切換式且保持可點擊** (`content/go-top.js`)：先前在捲動到頂端的動畫期間，按鈕會被停用（`aria-disabled="true"`）。現在全程保持啟用（`aria-disabled="false"`），捲動進行中再次點擊會讓捲動「停」在目前位置（以原因 `'stopped-by-user'` 結束進行中的捲動），而非被忽略。之後再點擊會開始新的捲動。路由變更中止（原因 `'aborted'`）維持不變。
- **單元測試** (`test/unit/go-top.spec.js`)：移除過時的 `_injectAsFallback` 測試組，以及固定定位備援／捲動期間停用的斷言；新增涵蓋新的注入把關（`.aaff8b8f` 或原生按鈕出現前不注入、重試 120 次後放棄且不產生按鈕、重試中途 `disable()` 取消、成功時重設重試計數）、`_injectButton` 中不使用備援的保證、永不加上 `dsw-gotop--fixed` 的不變條件，以及捲動切換（`aria-disabled` 維持 `false`；第二次點擊以 `'stopped-by-user'` 中止且不會重新開始）。測試套件：47 個檔案共 888 個測試，全數通過。

## [3.0.0] - 2026-06-07

### 新增

- **獨立的提示詞編輯視窗** (`popup/editor/editor.html|css|js`，新檔案)：提示詞內容編輯從 popup 移到獨立的 1280×720 視窗，透過 `chrome.windows.create({ type: 'popup' })` 開啟。查詢字串約定：`?target=global` 編輯全域預設提示詞；`?target=preset&id=<presetId>` 編輯該提示詞組的內容。視窗標題顯示「全域預設提示詞」或提示詞組名稱，並附上熟悉的「已儲存」儲存狀態指示。自動儲存能防範作業系統層級的視窗關閉：已修改旗標 + 輸入防抖動儲存（600 ms）+ `blur` + `visibilitychange` + `pagehide`，全部經由 `StorageManager`（`saveGlobalDefaultPrompt`／`saveOnePromptPreset`）處理。儲存提示詞組時還會廣播 `ACTIVE_PRESET_CHANGED`，讓已開啟的 DeepSeek 分頁立即更新。無效的目標與已刪除的提示詞組會呈現停用狀態。不需要新的權限。
- **全域提示詞注入開關** (`#globalPromptToggle`)：外觀與主開關相同的切換開關，靠右對齊於「Global Prompt」卡片（與上方的主開關垂直對齊）。新的儲存鍵 `globalPromptEnabled`（同步儲存，預設 `true`，既有使用者維持目前行為）。在 `content-script.js` 的 `buildInjectionPrefix()` 中把關：只有主開關與此開關「都」開啟時才注入全域預設提示詞；主開關透過既有 `injectPrefix()` 的提前返回保有最高優先權。已納入 JSON 備份匯出／匯入（`getSettings()`／`restoreSettings()`）。
- **共用訊息工具** (`utils/messaging.js`，新檔案)：從 `popup.js` 的分頁廣播邏輯（查詢使用中分頁、`chat.deepseek.com` 篩選、靜默吞掉錯誤）抽出 `broadcastActivePreset(presetId, presetContent)`，以 `window.DSVMessaging` 與有防護的 `module.exports` 公開，`popup.js` 與 `editor.js` 共用。

### 變更

- **popup 版面重構** (`popup/popup.html|css|js`)：移除兩個提示詞編輯 textarea（`#globalDefaultPrompt`、`#promptInput`）。「Global Prompt」卡片現在是單一列：左側為標籤 + 鉛筆按鈕（`#editGlobalPromptBtn`，`.icon-btn`，內嵌由右上往左下繪製的 SVG 鉛筆），右側為新的開關。「Prompt Group」控制項重新排列為［縮短的下拉選單（`max-width: 150px`）］［+ `#addPresetBtn`］［鉛筆 `#editPresetBtn`］；未選取提示詞組時提示詞組鉛筆按鈕會停用（取代舊的停用 textarea 行為），並為使用中的提示詞組開啟編輯視窗。「Backup & Restore」卡片從右欄移到左欄「Prompt Group」下方。編輯視窗每個目標只有一個實例：再次點擊會聚焦既有視窗（`chrome.windows.update`），只有在視窗已關閉時才重新建立。移除已過時的 `initColumnLayout()`、內容已修改旗標與 `saveCurrentPresetContent()`；`sendActivePresetToContentScript()` 改委派給 `DSVMessaging`。
- **單元測試**：改寫 `popup.spec.js`（以鉛筆停用狀態與編輯器網址測試取代欄位版面測試組）；新增 spec `content-script.global-prompt-gating.spec.js`（9）、`storage-manager.global-prompt-enabled.spec.js`（6）、`messaging.spec.js`（7）、`editor.spec.js`（約 25）、`popup-editor-window.spec.js`（10）；為新的 `DEFAULTS` 鍵更新 `storage-manager.migration-push.spec.js` 輔助函式。測試套件：47 個檔案共 887 個測試，全數通過。
