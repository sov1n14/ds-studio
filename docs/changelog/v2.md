# v2.x 版本變更記錄

> 📂 [DS studio 文件](../) › [版本記錄](../CHANGELOG.md) › v2.x

## [2.9.0] - 2026-06-07

### 新增

- **審查回覆還原開始監看 `edit_message` API** (`content/censor-xhr-hook.js`)：編輯先前送出的使用者訊息時，回覆會透過 POST `/api/v0/chat/edit_message` 而非 `/api/v0/chat/completion` 重新生成，但 XHR 攔截器的網址篩選只比對後者，因此編輯所產生的審查回覆從未被攔截：DOM 元素被判定為已審查，卻始終沒有片段抵達，內容也一直未還原（實地確認：編輯後的回覆記錄了「Detected censored message」，卻沒有對應的「Fragment complete!」，儲存區也沒有比對結果）。實地擷取驗證了 `edit_message` 是 SSE，格式與 `completion` 完全相同（同樣以 `event: ready` 攜帶 `response_message_id`、同樣的 `data:` 修補語法、同樣的 `CONTENT_FILTER` 狀態路徑），且其請求本體使用相同的 `chat_session_id` 與 `prompt` 欄位名稱（額外的 `message_id` 欄位是被編輯的「使用者」訊息 ID，刻意忽略；回覆 ID 仍取自 SSE 串流）。攔截器現在透過純函式 `getMatchedEndpoint(url)`，以新的 `INTERCEPTED_ENDPOINTS` 清單（`/api/v0/chat/completion`、`/api/v0/chat/edit_message`）比對網址，攔截日誌也會註明比對到哪個端點。請求本體解析、`sse-parser.js`、`censor-reply-restore.js` 與 `DVOY_FRAGMENT_COMPLETE` payload 皆維持原樣，下游流程與 API 無關。

### 變更

- **單元測試** (`test/unit/censor-xhr-hook-edit-message.spec.js`，新檔案)：新增 24 個測試，涵蓋端點比對（兩個端點皆接受；`/api/v0/chat/history`、`/api/v0/file/upload` 與空網址不經攔截器直接放行）、標註端點的攔截日誌、依實地擷取建模的端到端 `edit_message` SSE 解析（`messageId` 取自串流的 `response.message_id`，而非請求的 `message_id`；`censored`／`finished` 旗標、排除 `TEMPLATE_RESPONSE`、累積 `THINK`、`thinking_elapsed_secs`）、兩個端點的請求本體擷取（含本體缺失、非字串、非 JSON 的情況），以及雙端點並存（一次 `completion` + 一次 `edit_message` → 兩次 `DVOY_FRAGMENT_COMPLETE` 派送）。測試套件共 829 個測試，全數通過。

## [2.8.12] - 2026-06-07

### 修正

- **審查回覆還原在同一對話內注入錯誤內容（待處理佇列殘留過期項目）** (`content/censor-reply-restore.js`)：`_pendingQueue` 的項目只會被 `_getMessageIdFromElement()` 中佇列備援的 `.shift()` 移除。元素若改經由對應表或儲存區路徑解析，對應的佇列項目就會默默留下。實地觀察到的失敗（經主控台／DOM 證據確認）：某個審查元素在其片段完成前就出現並維持未還原；接著片段抵達（佇列 `[2]`，記錄已儲存），重新掃描時經由儲存區路徑解析了該元素，卻讓過期的 `2` 留在佇列中；之後該對話的下一個審查元素又在自己的片段抵達前出現時，對應表與儲存區都查無結果（其記錄尚不存在），佇列備援便盲目取出過期的 `2`，將第一則回覆的內容注入第三則回覆的元素。等到其真正的片段抵達時，元素早已標記為已還原，錯誤內容便一直保留到重新整理頁面、記憶體狀態重設為止。修正分兩部分：(1) 經由對應表或儲存區路徑解析出 `messageId` 時，現在會將該 ID 從 `_pendingQueue` 中清除（所有出現處，並記錄日誌）；(2) 佇列備援在取用前會先驗證：若元素可透過 `_getPrecedingUserPromptKey()` 取得提示鍵，而佇列開頭候選項目的儲存記錄帶有不相符的 `prompt_key`，備援就會拒絕（並記錄日誌）、不動佇列並回傳 `null`，讓該元素在自己的片段抵達後由重新掃描正確還原；只有在取不到提示鍵、或候選項目尚無儲存記錄時，才保留盲目取用。

### 變更

- **單元測試** (`test/unit/censor-reply-restore.spec.js`)：新增 9 個測試，涵蓋對應表路徑與儲存區路徑的佇列清除（含 ID 不存在時不做任何事）、提示不相符時拒絕佇列備援（佇列必須維持未取用）、三種接受備援的路徑（提示相符、尚無儲存記錄、元素取不到提示鍵），以及完整的過期佇列實地情境端到端測試。測試套件共 805 個測試，全數通過。

## [2.8.11] - 2026-06-07

### 修正

- **審查回覆還原在即時對話中注入錯誤內容（跨對話汙染）** (`content/censor-reply-restore.js`)：DeepSeek 網頁版是 SPA，切換對話從不重新載入頁面，但 CensorRestore 有三項執行期狀態既未依對話區隔，也未在導覽時清除。(1) `_restoredMessages` 以單純的 `message_id` 為鍵，但訊息 ID 是各對話內的流水號（2、4、6、…），因此新對話的審查記錄會默默覆寫前一個對話相同鍵下的記錄，而注入查詢從未驗證 session。(2) `_keyToMessageId` 與 `_pendingQueue` 在切換對話後仍然保留，而 `data-virtual-list-item-key` 的值是各對話內的索引、會跨對話重複使用，因此前一個對話的過期對應項目會劫持新對話中相同虛擬索引的元素。觀察到的結果（經主控台／DOM 證據確認）：新對話的第一則審查訊息顯示了前一個對話的還原內容，之後的審查訊息則顯示目前對話的第一則回覆；只有重新整理頁面、記憶體狀態重設後才會自行恢復。修正方式：所有 `_restoredMessages` 的讀寫現在都透過新的 `_recordKey(sessionId, messageId)` 輔助函式使用依 session 區隔的鍵（`"<session>::<id>"`，session 為假值時為 `nosession`）；舊的單純鍵記錄會在載入時依其內含的 `chat_session_id` 遷移一次；`chat_session_id` 為假值的記錄（或目前網址沒有 session ID 時）永遠不會比對到任何元素；新的 `_checkSessionChange()` 在 `_tryRestoreMessage()`、`_onFragmentComplete()` 與 `_tryRestoreFromStoredRecords()` 的入口呼叫，只要網址的 session 改變，就會清除 `_keyToMessageId` + `_pendingQueue` 並重設 `_storedRecordsApplied`（`null` → 非 `null` 的轉換會保留佇列，因為全新對話的第一個片段可能在網址穩定前就抵達）。

### 變更

- **診斷日誌** (`content/censor-reply-restore.js`)：`_getMessageIdFromElement()` 現在會記錄每個訊息 ID 是經由哪條路徑解析（`map` | `storage` | `queue`）；先前單一的 `Found messageId:` 日誌無法區分三者，是這次調查中的盲點。`_checkSessionChange()` 會記錄每一次清除執行期狀態的 session 轉換。
- **單元測試** (`test/unit/censor-reply-restore.spec.js`)：新增 23 個測試，涵蓋 `_recordKey()` 格式、跨對話記錄並存（兩個對話都持有 `message_id=2`）、舊鍵遷移（含 `null` session 記錄變成永遠無法比對的 `nosession::` 項目）、`null` session 比對的嚴格性、`_checkSessionChange()` 全部四條清除規則、SPA 汙染回歸情境（過期的虛擬清單鍵不得注入前一個對話的內容），以及依 session 區隔鍵下的即時 XHR 與重新整理還原正常路徑；6 個既有測試由單純鍵斷言更新為依 session 區隔的斷言。測試套件共 796 個測試，全數通過。

## [2.8.10] - 2026-06-07

### 修正

- **重新整理頁面後審查回覆還原未重新套用** (`content/censor-reply-restore.js`)：啟動時儲存記錄都有正確載入，但唯一將儲存記錄與 DOM 比對的程式路徑 `_tryRestoreFromStoredRecords()`，只會從 `enable()` → `applyToExisting()` 呼叫一次；它在 React 渲染對話記錄之前就執行（啟動期間被頁面本身的 WASM／React 初始化占據），找到零個 `.ds-message._63c77b1` 元素後默默返回，且從未重試。之後 `MutationObserver` 偵測到審查訊息時，`_getMessageIdFromElement()` 只查詢執行期的 `_keyToMessageId` 對應表（重新整理後為空）與 `_pendingQueue`（只由即時 XHR 填入），因此舊訊息記錄了「No `messageId` available (pendingQueue empty, no storage match)」並維持未還原。修正方式是在 observer 路徑加入儲存區備援：新的 `_resolveMessageIdFromStorage()` 依網址 session ID + 正規化後的前一則提示鍵，將單一元素與儲存記錄比對（命中時寫入 `_keyToMessageId`，絕不動到佇列）；`_getMessageIdFromElement()` 的查詢順序現在是 `_keyToMessageId` → 儲存區 → `_pendingQueue.shift()`（真正的最後手段），也一併修正新生成訊息的佇列 ID 可能被較舊的未還原元素搶走的錯配風險；當所有逐元素查詢都未命中時，`_tryRestoreMessage()` 會觸發完整的 `_tryRestoreFromStoredRecords()` 掃描，並由新的 `_storedRecordsApplied` 旗標把關（每次 `_onFragmentComplete` 時重設），避免 observer 重複變動時不必要地重新掃描。即時 XHR 正常路徑維持不變。

### 變更

- **診斷日誌** (`content/censor-reply-restore.js`)：先前完全無聲的 `_tryRestoreFromStoredRecords()` 現在會記錄擷取到的 session ID、未還原審查元素數量、逐元素提示鍵、儲存記錄數與 session 相符記錄數、逐提示鍵的比對結果，以及每一次注入，全部使用 `[DV:CensorRestore]` 前綴。
- **單元測試** (`test/unit/censor-reply-restore.spec.js`、`test/unit/censor-xhr-hook.spec.js`)：新增 16 個測試，涵蓋 `_getMessageIdFromElement()` 查詢順序（儲存區優先於非空佇列、保證不取用佇列）、`_resolveMessageIdFromStorage()`（session／提示比對、略過已被認領的 ID、佇列不變）、重新整理後由 observer 觸發的還原情境、重複注入的冪等性、`applyToExisting()` 冷啟動、`_storedRecordsApplied` 把關語意，以及 `_tryRestoreFromStoredRecords()` 的邊界返回；兩個讀取 `to-fix/` 下已刪除 YAML fixture 的 `censor-xhr-hook` 測試改用內嵌 SSE 字串。測試套件共 773 個測試，全數通過。

- **原生按鈕偵測**：選擇器依新結構改寫：主要選擇器為 `._0706cde:not(.dsw-gotop)`，結構備援限定在 `.aaff8b8f` 包裹容器內（`.ds-button--floating.ds-button--circle`、`[role="button"].ds-button--floating`、`[role="button"][class*="ds-button--circle"]`），且全部排除擴充功能自己的按鈕。

## [2.8.6] - 2026-06-06

### 修正
