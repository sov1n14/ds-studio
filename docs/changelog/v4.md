## [4.11.6] - 2026-07-26

修復「回到頂部」按鈕在對話串中反覆上捲又彈回、始終到不了頂的缺陷。

### Fixed

- **⚠️ 使用者可見：點擊「回到頂部」後畫面上捲一小段隨即彈回原位，反覆震盪直到靜默失敗。** `scrollToTopAndWait()`（`content/go-top.scroll.js`）完全未與 `PreventAutoScroll` 協調——`content/go-top.js`、`go-top.scroll.js`、`go-top.locate.js`、`go-top.render.js` 四檔對該模組零參照。頁面自身發起的向下捲動因此不受抑制，每輪都把 `scrollTop` 拉回。
  - **為何會空轉到超時**：收斂判定的外層條件是 `if (currentScrollTop <= 0)`（`content/go-top.scroll.js:104`）。容器被拉回後該條件恆為偽，每輪都走 else 分支將 `_stableTopCount` 歸零（`:111-114`），永遠到不了 `STABLE_REQUIRED = 3`，`_isAtTop()` 因此一次都沒被呼叫。唯一出口是 30 秒硬超時（`:93-97`），且 `content/go-top.render.js:98-100` 的點擊處理器直接丟棄回傳值，`{ success: false, reason: 'timeout' }` 無人接收——所以失敗是靜默的，使用者只會看到震盪，並傾向再點一次，每次重跑一輪 30 秒。
  - **診斷依據**：`content/harvest.js` 呼叫的是**同一個** `scrollToTopAndWait`、同一組 30000 毫秒上限（`harvest.js:196` 明示的值與 `content/go-top.js:24` 的預設值相同），且未傳入自己解析的容器——`scrollToTopAndWait` 一律使用自身的容器解析（`content/go-top.scroll.js:58-66`）。兩條路徑的唯一差異是 harvest 先啟用了 `PreventAutoScroll`（`harvest.js:284-286`）。匯出功能能捲到頂而按鈕不能，構成單一變因的對照組。
  - **修法**：於 `scrollToTopAndWait()` 進入點以 `isEnabled()` 記錄啟用前狀態，未啟用才 `enable()`；還原邏輯置於 `cleanup()`（`content/go-top.scroll.js:75-88`），且僅在「本次呼叫是啟用者」時才 `disable()`。
  - **為何必須是保存還原而非直接開關**：`PreventAutoScroll` 沒有引用計數，`disable()` 是無條件的全域關閉（`content/prevent-auto-scroll-bridge.js:74-77`）。`harvest.js` 在自己已啟用的狀態下呼叫 `scrollToTopAndWait`（`harvest.js:290`），若此處盲目 `disable()`，會在匯出仍在向下掃描時關掉保護傘。
  - **退出路徑稽核**：`cleanup()` 已涵蓋成功、30 秒超時（`:93-97`）與使用者中止（`:155-159`）三條路徑，無需在各站點重複還原邏輯。唯一繞過 `cleanup()` 的 `no_container` 提早返回發生在啟用邏輯之前，該路徑不曾啟用任何東西。函式頂端的重入鎖分支同樣在建立 Promise 前返回，不觸及 `PreventAutoScroll` 狀態。
- **未納入本次範圍**：GoToTop 全檔沒有任何 no-progress／反彈偵測，`content/harvest.js:306-318` 的 `scroll_interrupted` 安全網在此無對應物。根因修復後該情境不應再發生，故刻意不加——待日後確有需要再議，避免引入需要調校的門檻值。

### Tests

- `test/unit/go-top.prevent-auto-scroll.spec.js`（新檔，5 測試）：依既有 go-top spec 拆檔慣例獨立成一個關注點，重用 `test/helpers/go-top-fixtures.js` 的 `resetGoToTopState`。作者未讀 `content/go-top.scroll.js`，斷言僅由需求描述、`prevent-auto-scroll-bridge.js` 的公開介面與 `harvest.js` 既有的協調模式推導。
  - 測試以一個由真實布林值支撐的假 `PreventAutoScroll`（`enable`／`disable`／`isEnabled` 皆操作真實狀態）為基礎，斷言的是**可觀察狀態**而非呼叫序列。捲動進行中的狀態以包裝 `container.scrollBy`、於第一次捲動步驟取樣 `isEnabled()` 的方式擷取，觀察的是真實的執行中狀態。
  - 5 個測試中 3 個觀察到紅燈（happy path、超時、二次呼叫中止），失敗訊息均為 `expected false to be true`——修復前的取樣值恆為 false。
  - 另 2 個測試（harvest 巢狀、模組不存在）在修復前即通過，因為「呼叫前後狀態相同」對一個完全不碰該模組的實作是恆真的。已另以兩個合成的錯誤實作驗證其非空洞：盲目 `enable()` + 無條件 `disable()` 會被巢狀測試抓到，未加存在性守衛的 `pas.enable()` 會拋錯而被抓到。
- 修復後驗證：新 spec 5/5 綠、7 個既有 go-top spec 164 測試全綠、`harvest.spec.js` 51 測試全綠（此為關鍵回歸項——它涵蓋 harvest 在已啟用狀態下呼叫本函式的情境）、`prevent-auto-scroll-bridge.spec.js` 16 測試全綠。合計 **11 檔 / 236 測試 / 0 失敗 / 0 跳過**。

### Documentation

- `docs/architecture/content-interaction.md`：於 PreventAutoScroll 段落補記「無引用計數、`disable()` 為全域關閉」這項先前未載明的關鍵限制，新增「Consumers」小節說明 `harvest.js` 與 `go-top.js` 兩者的巢狀關係與保存還原契約，並澄清 Design Decisions 中「`harvest.js` and `go-top.js` can scroll freely」一句——該句描述的是**不受 patch 誤傷**，而非「已與 patch 協調」，先前易被誤讀為 go-top 已完成整合。

## [4.11.5] - 2026-07-26

修復 GoToTop 停用後的計時器殘留缺陷。稽核來源為 `to-do/go-top-route-change-timer-leak.md`，該報告的每項指控皆經獨立 read-only 覆核後確認成立。

### Fixed

- **⚠️ 使用者可見：關閉「回到頂部」後按鈕仍可能重新出現。** `content/go-top.js` 的 `_onRouteChange()` 所排下的 100 毫秒 `setTimeout` 未將 handle 存入任何欄位，`disable()` 因此無從 `clearTimeout`；`_onRouteChange()`（全文無 `this.enabled` 參照）與 `_tryConnectDom()`（進入點無守衛）也都沒有攔阻。若 SPA 路由切換發生在使用者停用功能前的 100 毫秒內，該計時器仍會在停用後觸發 `_tryConnectDom()`，無條件執行 `_injectButton()` 與 `_startScrollListener()`——按鈕被重新注入 DOM，包裝容器的 `MutationObserver` 與 scroll 監聽器在功能已關閉的狀態下重新啟動。
  - **殘留的 observer 無法自行收拾。** `_startWrapperObserver()` 的重複防護是 `if (this._wrapperObserver) return;`（`content/go-top.render.js:291`）；停用時 `_stopWrapperObserver()` 已將該欄位設為 null 並執行完畢，因此停用**之後**才建立的新 observer 會成功掛上且不會再被拆除，而其回呼會在按鈕被移除時自動補回（`content/go-top.render.js:289-336`）。使用者除重新整理外無法擺脫。
  - **修法**：新增 `_routeChangeTimer` 欄位保存 handle 並於 `disable()` 清除，同時在 `_tryConnectDom()` 進入點加入 `if (!this.enabled) return;`。守衛置於進入點而非各呼叫點，一次涵蓋三個呼叫點（路由計時器、自身重試、`enable()` 的同步呼叫）；`_enableRetryTimer` 回呼內原有的 `if (this.enabled)` 因此成為冗餘並一併移除。
  - **按鈕不會被設為可見。** `_evaluateVisibility()` 自帶 `if (!this.enabled || !this._masterEnabled) return;` 守衛（`content/go-top.locate.js:230-233`），但它在序列中最後執行，故只擋得住可見性更新，無法撤銷已經發生的注入。稽核報告原先將此列為「按鈕可能被設為可見」，實測不成立。
- **`disable()` 未中止進行中的捲動。** 原本僅將 `this._scrollReject` 設為 null 而從未呼叫它，然而該 reject 函式是捲動模組唯一的外部取消介面——呼叫它才會執行閉包內的 `cleanup()`（`content/go-top.scroll.js:75-88`），清掉閉包區域變數 `mutationTimer`。缺此呼叫時 anchor 輪詢迴圈會持續呼叫 `scrollContainer.scrollBy`，直到自身的 timeout 或 `MAX_ANCHOR_RETRIES` 上限才停止（影響有界，非無限）。改為比照 `_onRouteChange()` 的既有寫法傳入 `{ success: false, reason: 'aborted' }` 後再設 null，未改動 `content/go-top.scroll.js`。

### Tests

- `test/unit/go-top.enable.spec.js`：新增 `disable — teardown correctness (regression)` 區塊與 2 個測試（10 → 12）。兩者皆先觀察到紅燈——第一個因 `.dsw-gotop` 仍存在於 document 而失敗，第二個因停用後 `scrollBy` 多被呼叫 5 次（3 → 8）而失敗。新區塊刻意與既有 `enable / disable` 區塊平行而非嵌套：後者的 `beforeEach` 將 `container.addEventListener` 換成 `vi.fn()` 空殼，會使「停用後 scroll 監聽器是否仍會觸發」根本無法被觀察。
  - 紅燈階段另有一項診斷值得留存：「promise 即時結算」那條斷言在修復前就已通過，證明 promise 結算路徑與捲動迴圈取消路徑是脫鉤的——這正是修法必須走 `_scrollReject` 而非另設旗標的理由。
- 修復後驗證：7 個 go-top spec 檔 / 164 測試 / 0 失敗 / 0 跳過。完整套件跨模組回歸驗證：**92 檔 / 1736 測試 / 0 失敗 / 0 跳過**。
  - 4.11.4 記載的 `86 檔 / 1731 測試` 基準線在本次動工前即已過時，差額全數可歸因於前兩次提交：go-top 測試拆檔（`4327741`，1 spec 檔 → 7 spec 檔加 1 個 fixture helper，helper 不計入 spec 檔數，淨 +6 檔）與 go-top 調和 no-op 分支補測（`ab0066d`，+3 測試）。`1731 + 3 + 2 = 1736`，逐位吻合，無來源不明的測試。

### Rejected

- **`popup/custom-select.js` 改用 `AbortController`（D3）已否決。** 原計畫以 `open()` 建立、`close()` 中止的 `AbortController` 取代手動追蹤的 `_outsideClickHandler` 與 `_registerOutsideClick`／`_unregisterOutsideClick`（省 13 行）。否決理由：**happy-dom 16.8.1 會靜默忽略 `addEventListener` 的 `signal` 選項**（已以探針實證，非查閱文件）。改寫後，`close()` 呼叫 `abort()` 並不會真正卸載監聽器，而 `close()` 是冪等的，因此驗證卸載行為的測試會**空洞通過**——真實 Chrome 90+ 行為正確，但測試從此無法證明卸載有發生。以 13 行換掉一個真實的守門測試不划算。此模式在 `content/sidebar-auto-hide.js`、`content/go-top.js`、`content/quote-reply.js`、`content/preset-dropdown.component.js` 另有四處，同樣不改。
- **`popup/popup.modal.js` 改用原生 `<dialog>` 已否決。** happy-dom 16.8.1 的 `HTMLDialogElement` 是純屬性切換的空殼：`showModal()` 與 `show()` 實作完全相同（皆只 `setAttribute('open','')`）、`cancel` 事件從未被派發（`oncancel` 屬性宣告了卻未接線）、`::backdrop` 在整個 CSSOM 實作中無任何處理。Escape 關閉這條最需要保護的路徑會變成無法測試。波及面：`test/unit/popup-modal.spec.js` 6 處與 `test/unit/popup-custom-select.spec.js:407,416,421,430` 2 處直接斷言 `Modal.overlay.hidden`，共 8 個測試需**重寫**（非微調，因 `<dialog>` 暴露的是 `.open`），加上 `popup/popup-modal.css` 的遮罩規則需為 `::backdrop` 重新編寫。另有一項行為差異需獨立簽核而非夾帶在瘦身中：原生 `<dialog>` 會捕獲 Tab 焦點，現行實作不會——那是無障礙**改善**，不是等價替換。

## [4.11.3] - 2026-07-26

稽核瘦身批次 C（結構性合併）。`utils/` 由 13 檔併為 10 檔；三項合併皆為機械式搬移，公開方法名稱、簽章與行為一律不變。所有跨檔呼叫原本就透過組裝後物件的 `this.<method>()` 進行，故無任何呼叫端需要修改。

### Fixed

- **⚠️ 使用者可見：背景同步重試一直靜默失效。** `background/service-worker.js` 的 `importScripts` 從未載入 `utils/storage-manager.tombstones.js`，但 `retryParkedSync()` → `retrySync()` → `resolveSyncConflict()` 會呼叫僅定義於該檔的 `this._pruneTombstones(this._mergeTombstones(...))`。因此該路徑一律拋出 `TypeError: this._mergeTombstones is not a function`，而錯誤被一個標註「best-effort，全部吞掉」的空 `catch` 吃掉——`onStartup`、`onInstalled` 與 alarm 觸發的背景同步重試，在衝突可自動解決時從未真正完成過，且無錯誤、無 console 警告。本次合併後墓碑函式隨 `presets.js` 抵達（service worker 本就已載入該檔），缺口自然消失，未新增任何 import。
  - **二階效應**：修復後的 service worker 會在啟動時真正完成 `resolveSyncConflict()` 並寫入 `chrome.storage.sync`——這是先前不會發生的寫入。
  - 根因是方法包的 `|| {}` 合併語意：入口檔以 `root.__DS_StorageManager_X || {}` 混入各包，未載入的包會以空物件併入，其所有方法在該 context 的生命週期中全部缺席，無錯誤亦無警告。

## [4.9.0] - 2026-07-11

### Changed

- **Two-layer temporary-conversation deletion architecture**: Real-time deletion and crash/shutdown remediation are now fully separated.
  - **Layer 1 (real-time, content script)**: `beforeunload` (tab/browser close) now calls `fetch(..., { keepalive: true })` directly instead of relaying through the Service Worker via `chrome.runtime.sendMessage` — removing the unreliable IPC hop that could fail to arrive during tab teardown.
