Three separate happy-dom 16.8.1 gaps discovered while testing this project, all environment limitations rather than production bugs — do not chase these as regressions, and do not write a test asserting the missing behavior actually works.

**1. `AbortController`-based listener teardown is unverifiable.** happy-dom 16.8.1 ignores the `signal` option on `addEventListener` — a listener registered with `{ signal }` and later aborted via `controller.abort()` is never actually removed in this environment. Any test that tries to prove "the listener was torn down because the signal fired" will pass or fail independent of the real implementation; don't rely on this to validate `AbortController`-based cleanup code.

**2. `HTMLDialogElement` is a bare attribute-toggle shell.** In happy-dom 16.8.1, `showModal()` and `show()` behave identically (no true modal semantics), no `cancel` event is ever dispatched (so Escape-to-close cannot be simulated/verified), and `::backdrop` is not representable at all. Any `<dialog>`-based rewrite of existing overlay/modal UI is therefore untestable in this environment — such a change would need manual/DOM-adapter-layer verification against the real page, not a happy-dom unit test asserting dialog behavior.

**3. `MutationObserver` under `vi.useFakeTimers()` (RESOLVED 2026-07-26 by empirical probe).** Confirmed via a 5-case throwaway probe (real MutationObserver on a real happy-dom node, mutated then flushed 5 different ways) that the earlier suspicion was correct and now has a precise rule: with fake timers active, a bare microtask flush (`await Promise.resolve()`, even twice) or `await vi.advanceTimersByTimeAsync(0)` does **NOT** deliver pending mutation records — fireCount stayed 0 in both cases, and stayed 0 even with `vi.useFakeTimers({ toFake: [...] })` explicitly excluding microtask/nextTick from the fake list. **The one workaround that DOES work: `await vi.runAllTimersAsync()`** — this flushed the observer and fireCount went to 1, matching real-timer behavior. Any fake-timer test that mutates the DOM and expects a `MutationObserver` callback to have run before its assertions MUST flush with `vi.runAllTimersAsync()` (or drop to real timers + `setTimeout(fn, 0)`), never a bare `vi.advanceTimersByTime()`/`advanceTimersByTimeAsync()`/`Promise.resolve()`.
**Caveat (measured empirically, treat as verified): `runAllTimersAsync()` coalesces multiple mutations into ONE callback.** When several mutations are pre-scheduled (e.g. queued via multiple `setTimeout` calls) and then flushed with a single `runAllTimersAsync()` call, happy-dom batches them into exactly one observer callback delivery instead of one-per-mutation — measured 19 scheduled mutations producing exactly 1 callback (instrumented with `console.log` in the observer). Consequence: any test whose correctness depends on counting mutations, or on each individual mutation resetting a counter/timer (debounce reset, stability-tick reset, throttle reset), MUST use real timers instead — fake timers make such a test insensitive to the very defect it's meant to catch, since coalescing means only one reset ever happens regardless of how many are supposed to occur. Use `performance.now()` for elapsed-time assertions under real timers. Working precedent: `test/unit/harvest.spec.js`'s `_waitForDomStability` describe block has two real-timer tests relying on per-mutation resets, converted from a fake-timer + single-flush attempt that was proven insensitive to sabotaged reset logic.

**Confirmed casualties of the wrong flush pattern:**
- `test/unit/go-top.spec.js` ("re-injects as solo when button removed and no native button") — FIXED 2026-07-26: switched to real timers + `await new Promise(r => setTimeout(r, WRAPPER_OBSERVER_DEBOUNCE + 40))`, assertions strengthened to `_button !== oldBtn` + `isConnected` + correct parent (was only checking non-null, which passed trivially). Sabotage-proved by blanking the re-injection branch body in `content/go-top.render.js` — test failed with `expected null not to be null`, then production file restored via `git checkout --`. Two new regression tests added alongside it for the reconciler's no-op branch (mode already matches DOM reality → no transition/offset/visibility work), same real-timer pattern, sabotage-proved by removing the mode guard so it always transitions.
- `test/unit/harvest.spec.js:272-286` ("resolves on step-timeout when mutations keep resetting stable count") — interleaves `container.appendChild(...)` with bare sync `vi.advanceTimersByTime(...)`, no flush, and **contains zero `expect()` calls**. `content/harvest.js:150-163`'s `_waitForDomStability` MutationObserver (which sets `isMutated`/resets `stableTicks`) never gets a chance to fire; the promise resolves purely because cumulative fake-time (400ms) exceeds the 300ms stepTimeout, which would happen with or without any mutation ever occurring. FIXED 2026-07-26: replaced with two real-timer tests in the `_waitForDomStability` describe block — "resolves via the stability window (not the timeout) when mutations stop early" and "resolves via step-timeout when mutations keep arriving right up to the deadline". Sabotage-proved by breaking the mutation-reset logic in `content/harvest.js` — the step-timeout test failed with `expected 469.1947 to be greater than or equal to 550` (resolved via the stability window early instead of waiting the full 600ms stepTimeout), then production file restored via `git checkout --`.
