# Layout Measurement Needs a Layout Model

**Cause**: v4.11.4 → v4.35.3 — `#dss-preset-overlay` grew a few px wider on every in-chat preset switch, capped at 200px. `measure()` in `content/preset-dropdown.width.js` wrote each option name into the live `span.dss-preset-label` (`flex: 1 1 auto; overflow: hidden`) and read `scrollWidth`. In a real browser, `scrollWidth` of an overflow-hidden element is max(content width, own box width), so short names returned the flex-stretched box width, which derives from the overlay width the controller wrote back from the previous measurement — each re-measure returned the previous width plus a constant. The tests stayed green because happy-dom performs no layout (`scrollWidth`, `offsetWidth`, `getBoundingClientRect` return 0), the component spec only asserted a finite number, the idempotency test called `reposition()` twice without `setOptions()` in between so the width cache never invalidated, and `createWidthMeasurer` had no spec.

**Solution**: `measure()` sets `flex: none` on the label while measuring and restores it afterwards, so `scrollWidth` reflects the text width alone. `test/unit/preset-dropdown.width.spec.js` adds a boundary layout model (flex-grow, `scrollWidth` = max(content, box), fixed per-character width) and drives measure → write back → `setOptions()` → measure. On pre-fix code, repeated `setOptions()` + re-measure gave natural widths [263, 270, 277, 284, 291, 298] instead of a constant 263, and measuring at overlay inline widths 120 / 300 / 600px gave [263, 307, 607] instead of [263, 263, 263].

**Prevention**: Code whose output depends on browser layout — `scrollWidth`, `offsetWidth`, `clientWidth`, `getBoundingClientRect` — MUST be tested with a boundary layout stub that implements the relevant browser rule (flex-grow filling free space, `scrollWidth` = max(content, box), a fixed per-character text width), with the real CSS loaded; happy-dom's zeros make every measurement independent of its container and hide the defect. When a measured size is written back into the layout it measures, the test MUST drive the full feedback loop through the real invalidation trigger (for the dropdown: measure → write back → `setOptions()` → measure) and assert a fixed point.

**Check**: Measure at several container inline widths (for example 120 / 300 / 600px) and confirm the result responds only as the requirement says — for content-width sizing, not at all. Then revert the fix and confirm the test goes red with a width that drifts across loop iterations or follows the container width.
