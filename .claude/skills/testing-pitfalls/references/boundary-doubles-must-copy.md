# Boundary Test Doubles Must Copy

**Cause**: `remediatePendingDeletes` lost-update bug in `background/service-worker.js`. The sweep read the pending-delete list, a lease refresh or concurrent add wrote fresh data, then the sweep wrote its stale snapshot back. The scenario test passed 5/5 because `test/fixtures/chrome-storage-mock.js` returned stored objects by reference on `get` and kept the caller's objects by reference on `set` — the "stale snapshot" was the same object the concurrent write had mutated. Real `chrome.storage` structured-clones values on both `set` and `get`, so every caller holds an independent copy.

**Cause** (error-signal lifetime): the same fixture's quota-error mode set `chrome.runtime.lastError` whenever `set()` failed, in promise form too, and never cleared it there. Every later callback-form read in the same test then saw a stale `lastError`, so code that checks `lastError` treated a healthy read as failed and returned `{}` — a spec could pass or fail on the fixture's leftover state, not on the code under test. Real Chrome exposes `lastError` only while the failing call's own callback runs, and a promise-form call rejects without touching it.

**Cause** (missing failure shape): v4.35.3 failed-bind race, see [overlapping-async-writes.md](overlapping-async-writes.md). The `sendMessage` double in `test/helpers/chat-map-writer-harness.js` rejected with PORT_CLOSED whenever listeners existed but none responded. Real promise-form `chrome.runtime.sendMessage` can instead resolve `undefined` in that case, which the client turns into "DSS_CHAT_MAP_BIND 失敗：未收到回應" — the live trigger of the bug. That shape was never modelled, so no test took the path that exposed the race.

**Solution**: `transports` in `test/helpers/overlay-consistency-harness.js` gained `'no response (resolves undefined)'` and `'rejection (port closed, not retried)'`, and `test/unit/content-script.overlay-failed-bind-consistency.spec.js` runs every failure mode against both bound and unbound chats.

**Prevention**: A test double for any storage or message boundary MUST reproduce the boundary's copy semantics — deep-copy (`structuredClone`) on the way in and on the way out. A read-modify-write test against a by-reference double proves nothing. The double MUST also reproduce how the boundary signals errors: `chrome.runtime.lastError` is set only for the duration of the failing call's callback and cleared afterwards, never set for a promise-form call (which rejects instead). The double MUST offer every real failure shape of the API — rejection, synchronous throw, never settling, and resolving with `undefined` or an empty response — not only rejections. Applies to fakes of `chrome.storage`, IndexedDB, `postMessage` / `chrome.runtime.sendMessage` payloads, and any in-memory store.

**Check**: Before trusting a concurrency or lost-update test, run it against a deliberately broken implementation (or the known-buggy version) and confirm it fails. If it passes, suspect aliasing in the double before trusting the test. For an error-signaling knob, assert in a fixture-fidelity spec (`test/unit/chrome-storage-mock.copy-semantics.spec.js`) that the error state is absent between the call and its callback and after the call settles. For a failure-mode matrix, list how the real API reports each failure (Chrome docs plus observed live behavior) and confirm the double has a knob for each shape, including a resolved `undefined`.
