# Boundary Test Doubles Must Copy

**Cause**: `remediatePendingDeletes` lost-update bug in `background/service-worker.js`. The sweep read the pending-delete list, a lease refresh or concurrent add wrote fresh data, then the sweep wrote its stale snapshot back. The scenario test passed 5/5 because `test/fixtures/chrome-storage-mock.js` returned stored objects by reference on `get` and kept the caller's objects by reference on `set` — the "stale snapshot" was the same object the concurrent write had mutated. Real `chrome.storage` structured-clones values on both `set` and `get`, so every caller holds an independent copy.

**Cause** (error-signal lifetime): the same fixture's quota-error mode set `chrome.runtime.lastError` whenever `set()` failed, in promise form too, and never cleared it there. Every later callback-form read in the same test then saw a stale `lastError`, so code that checks `lastError` treated a healthy read as failed and returned `{}` — a spec could pass or fail on the fixture's leftover state, not on the code under test. Real Chrome exposes `lastError` only while the failing call's own callback runs, and a promise-form call rejects without touching it.

**Cause** (missing failure shape): v4.35.3 failed-bind race, see [overlapping-async-writes.md](overlapping-async-writes.md). The `sendMessage` double in `test/helpers/chat-map-writer-harness.js` rejected with PORT_CLOSED whenever listeners existed but none responded. Real promise-form `chrome.runtime.sendMessage` can instead resolve `undefined` in that case, which the client turns into "DSS_CHAT_MAP_BIND 失敗：未收到回應" — the live trigger of the bug. That shape was never modelled, so no test took the path that exposed the race.

**Cause** (prompt closes the caller): the 4.39.0 "on" path of `#autoCopyReplyToggle`, `#autoCopyCodeToggle` and the `replyNotificationToggle` radio awaited `chrome.permissions.request()` before saving the setting, and Chrome closes the popup when its prompt appears, so the save never ran after Allow and the setting stayed off. `test/unit/popup-auto-copy-toggles.spec.js:273` and `test/unit/popup-reply-notification-toggle.spec.js:263` resolved the `request` double with `async () => true` while the caller was still alive, and `fireChangeAndSettle` drained all async work before the assertions, so the teardown path never ran. Nothing modelled a `request` that never settles, so no test asserted the saved setting from a context that outlives the popup.

**Cause** (event semantics): through v4.39.7, a re-pick in the in-page overlay of a new conversation of the group that is already the stored `activePresetId` sent the group content without the global prompt. The overlay relied on the `DSS_SETTINGS_CHANGED` broadcast, driven by `chrome.storage.onChanged`, to refresh `isGlobalPromptEnabled`, and real Chrome fires no `onChanged` for a write that stores the value already held (verified in Chrome 156.0.8078.80, local and sync; a mixed write reports only the changed keys). The `chrome.storage` fake in `test/fixtures/chrome-storage-mock.js` reports every set as a change, so a same-value re-pick still delivered the broadcast and hid the missing refresh.

**Cause** (failure the boundary cannot produce): through v4.39.9, fixed in v4.39.10 — on a new conversation, the overlay pick (`onSelectChange` in `content/preset-overlay.controller.js`) and the `ACTIVE_PRESET_CHANGED` handler in `content/content-script.js` called `ChatBinding.updatePromptPrefixFromBinding()` without awaiting or catching it, while the sibling steps of the same event (`saveActivePresetId`, the global-prompt refresh) each had a `.catch` that logs on the `[DSS]` boundary. A rejected `StorageManager.getSettings()` read inside the recompute became an unhandled rejection and `promptPrefix` kept its previous value. The existing failure matrices (storage write failures, `sendMessage` shapes) failed the boundary and so never rejected that read: `getSettings()` resolves `{}` on storage errors, so no `chrome.storage` double can make it reject, and no test rejected one step while its siblings succeeded.

**Cause** (failure shape the caller branches on): through 4.39.21, fixed in 4.39.22 — on Kiwi Browser (Android), `chrome.permissions.request` rejects with `Error: Could not find an active window.` because no native window can host the prompt. `popup/popup.toggles.js`, through `utils/clipboard-permission.js` and `utils/notification-permission.js`, treated every rejection as a user refusal, reverted the toggle and never saved, so auto-copy and the reply-complete notification could never be enabled on Kiwi. `test/unit/clipboard-permission.spec.js`, `test/unit/notification-permission.spec.js`, `test/unit/popup-auto-copy-toggles.spec.js` and `test/unit/popup-reply-notification-toggle.spec.js` rejected `request` only with generic text ('request failed', 'permissions API error') and asserted "reject, then revert". `test/helpers/permission-intent-harness.js` offered no rejecting answer (`answerRequestWith` resolves a value, `closePopupOnPrompt` never settles). No double carried the platform's own failure message, so a rejection that is not a refusal stayed invisible.

**Solution**: `transports` in `test/helpers/overlay-consistency-harness.js` gained `'no response (resolves undefined)'` and `'rejection (port closed, not retried)'`, and `test/unit/content-script.overlay-failed-bind-consistency.spec.js` runs every failure mode against both bound and unbound chats.

**Solution** (prompt closes the caller): the popup writes the pending intent to `chrome.storage.local` before `chrome.permissions.request()`, and `background/permission-intent-routes.js` completes it on `chrome.permissions.onAdded` in the service worker. `test/unit/permission-intent.scenario.spec.js` (R1 to R5) and `test/unit/service-worker.permission-intent-wiring.spec.js` share one in-memory `chrome.storage` across the real popup toggle manager, `StorageManager` and routes module; the `request` double from `test/helpers/permission-intent-harness.js` never settles by default, and the assertions read the setting through `StorageManager.getSettings()` after Allow. Observed red on pre-fix code (HEAD `popup/popup.toggles.js` and `utils/*-permission.js`, with the new routes module): 16 of 21 tests failed, R1 among them with "after Allow, StorageManager reports autoCopyReply on and the other gated settings off: expected autoCopyReply false to deeply equal true"; R5 (permission already granted, no prompt) passed.

**Solution** (event semantics): `test/helpers/overlay-consistency-harness.js` gained the opt-in mode `isUnchangedWriteSilent`, which drops unchanged keys from `onChanged` events and emits no event when nothing changed, as real Chrome does, verified against Chrome 156. The overlay now calls `ChatBinding.refreshGlobalPromptEnabled()` explicitly on a pick in a new conversation. `test/unit/content-script.overlay-repick-global-flag.scenario.spec.js` (6 tests) runs with the mode on; observed red on 4.39.7 code: 5 of 6 failed (the success case `expected '<system-reminder>\nPREFIX-G…' to contain 'GLOBAL-INSTRUCTION'`, the three write-failure cases the same, the `getSettings()` rejection guard `expected 0 to be greater than 0`) and the blank-option companion passed.

**Solution** (failure the boundary cannot produce): both call sites now catch the rejection and log it with `console.error('[DSS] … 前綴重算失敗:', err)`, and `pendingPresetId` is still set. `test/unit/content-script.overlay-pick-prefix-rejection.scenario.spec.js` (5 tests) shares one in-memory `chrome.storage` across the real overlay, chat-binding controller and `StorageManager`, delivers the popup message through the content script's real `chrome.runtime.onMessage` listener, and stubs `StorageManager.getSettings` with `vi.spyOn(...).mockImplementation` that rejects only when `new Error().stack` contains `updatePromptPrefixFromBinding`, so every other read and the sibling steps succeed. It collects unhandled rejections with `process` `unhandledRejection` and `rejectionHandled` listeners and asserts the `[DSS]` `console.error` call carries each error. Observed red on 4.39.9 code: 4 of 5 tests failed (the no-escape and the logging case of each entry path) and the pending-group case passed.

**Solution** (failure shape the caller branches on): a rejection whose message is "Could not find an active window." now saves the setting as a grant does; every other rejection and a `false` answer still revert. `test/unit/popup-permission-window-unavailable.spec.js` makes the harness's `request` fake reject with the exact Kiwi error, drives the real popup toggle manager for both the clipboard and the notification permission paths, asserts the control state and the saved setting through `StorageManager.getSettings()`, and keeps control cases where a generic rejection and `false` still revert. Observed red on 4.39.21 code: 3 of 9 tests failed and the 6 control cases passed.

**Prevention**: A test double for any storage or message boundary MUST reproduce the boundary's copy semantics — deep-copy (`structuredClone`) on the way in and on the way out. A read-modify-write test against a by-reference double proves nothing. The double MUST also reproduce how the boundary signals errors: `chrome.runtime.lastError` is set only for the duration of the failing call's callback and cleared afterwards, never set for a promise-form call (which rejects instead). The double MUST offer every real failure shape of the API — rejection, synchronous throw, never settling, and resolving with `undefined` or an empty response — not only rejections. Applies to fakes of `chrome.storage`, IndexedDB, `postMessage` / `chrome.runtime.sendMessage` payloads, and any in-memory store. When the API's prompt can close the calling page, the teardown path MUST run with the `request` double never settling, and the state the caller wrote before the await MUST be asserted from a context that outlives the caller, never from the caller itself. A fake that emits change events (`chrome.storage.onChanged`) MUST emit them as the real API does: no event for a write that stores the value already held, and only the changed keys for a mixed write. Verify that semantics against the real API before a scenario test relies on events. Production code SHOULD refresh state explicitly rather than rely on a storage broadcast after a write that may be a no-op. When one event starts several async steps and each step has its own error handling, a failure matrix over the boundary is not enough: a step that swallows the boundary's errors (a reader that resolves a default) never rejects through the double. The test MUST reject each step's own call on its own while its siblings succeed, stub that call at the module seam (scoped to the step's call stack, restored after the event), and assert two outcomes: no unhandled rejection (collected with `process` listeners) and one logged error per rejection, plus that the state the step would have written before it failed is still set. A fake of a platform prompt such as `chrome.permissions.request` MUST also reject with each platform-specific error the real API raises where the caller reads the message (a prompt that cannot open, as in the Kiwi Cause above, versus a user refusal), not only a generic `Error`. The test MUST assert that the caller treats each distinct failure as the requirement says, never that "any rejection means refusal".

**Check**: Before trusting a concurrency or lost-update test, run it against a deliberately broken implementation (or the known-buggy version) and confirm it fails. If it passes, suspect aliasing in the double before trusting the test. For an error-signaling knob, assert in a fixture-fidelity spec (`test/unit/chrome-storage-mock.copy-semantics.spec.js`) that the error state is absent between the call and its callback and after the call settles. For a failure-mode matrix, list how the real API reports each failure (Chrome docs plus observed live behavior) and confirm the double has a knob for each shape, including a resolved `undefined`. For a teardown scenario, run it against the pre-fix caller with the `request` double never settling and confirm the outcome assertion fails; a pass there means the double still resolves, or the assertion reads the caller. For an event-driven refresh, run the scenario with the fake in the real-Chrome mode (`isUnchangedWriteSilent`) and a same-value write, and confirm the refreshed state is still correct; a pass only in the default mode means the test relies on an event the real API never fires. For a multi-step event, list its async steps and confirm one test rejects each step alone; then remove that step's `.catch` and confirm the no-escape and logging assertions go red. A guard that the stub was actually hit (the rejected read count is above zero) MUST precede those assertions, so a stub that never matches cannot pass them. For a caller that branches on a rejection, list the error messages the real API raises on each supported platform and confirm one test rejects with each exact message.
