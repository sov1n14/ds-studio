# Init Window: Deliver Events Before the Listener Exists

**Cause**: through v4.39.24, fixed in v4.39.25 — the content script registered its `DSS_SETTINGS_CHANGED` listener as the last step of init, so a settings write committed after init read its settings snapshot but before the listener existed was never applied. A popup write of the local-only `isEnabled: false` in that window left the content script state enabled and the overlay visible. Every existing spec used "the second `chrome.runtime.onMessage` listener is registered" as its init-done signal and seeded storage or acted only after it, so no test ever wrote storage while init was running.

**Solution**: the content script registers the listener early, buffers the messages that arrive during init, and replays them after init. `test/unit/content-script.init-settings-window.scenario.spec.js` injects a storage write on the next tick after init's snapshot read (case 1) and during the read in `handleChatChange` (case 2), then asserts the state and the overlay after init completes. On pre-fix code 2 of 3 cases failed with "... expected true to be false". After the fix, the listener-count signal fired before init ended, and 4 specs failed intermittently. `test/helpers/content-script-init-probe.js` replaces that signal with a sentinel broadcast probe applied only after the replay.

**Cause** (init failing partway): the content script marked init done and replayed the buffer only as the last step of a successful init, so an init step that threw before it, such as a rejected `chrome.storage.local.set` during the settings write-back or a synchronous throw from `chrome.storage.onChanged.addListener`, left every later `DSS_SETTINGS_CHANGED` broadcast buffered forever; a global prompt edit never reached the open page. The init-window specs covered only an init that completed, so no test released the buffer after a failed init.

**Solution** (init failing partway): `initSettings()` runs the init steps in a `try` and marks init done and replays the buffer in a `finally`, and the original error still reaches the caller. `test/unit/content-script.init-settings-window.scenario.spec.js` (describe "content-script: a settings broadcast after init failed partway takes effect") fails init once by rejection through `lastError` and once by synchronous throw, then broadcasts a global prompt edit. On pre-fix code both cases failed with "a global prompt edit broadcast after init settled replaces the page global prompt instead of being buffered forever: expected '' to be 'GLOBAL-EDITED-AFTER-INIT'".

**Prevention**: A module that reads a snapshot at init and later follows change events MUST have a scenario test that writes the watched store at each await of init. Assert the state after init completes against the final stored value. A test MUST NOT use a registration count as its init-done signal; it MUST wait for an observable effect of init completion. Test that the buffer is released with init failing at each trust boundary, once by promise rejection and once by synchronous throw. See host-request-sequence-needs-live-model.md for one-shot messages.

**Check**: List the awaits between init start and listener registration and confirm a test writes storage at each. Move the registration back to the end of init and confirm a test goes red. Search specs and helpers for listener-count waits and confirm none gates seeding or acting. Confirm a case makes init reject and a case makes init throw synchronously, each followed by a broadcast asserted to take effect.
