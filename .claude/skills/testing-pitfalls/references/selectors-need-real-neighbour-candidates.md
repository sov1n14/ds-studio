# Collection Selectors: Seed the Real Neighbours

**Cause**: `selectNewestHar` in `test/e2e/helpers/har-recording.js` picked the `*.har` file with the latest modification time under `tools/recordings/`. When purpose recordings with a name suffix (`deepseek-YYYY-MM-DD-scroll-chat-list.har`, `deepseek-YYYY-MM-DD-single-long-chat.har`) were saved next to the main `deepseek-YYYY-MM-DD.har`, the picker chose a purpose recording, and every offline E2E spec would have replayed a recording that lacked the conversations those specs choose. The unit tests in `test/unit/e2e-har-recording.spec.js` passed because every fixture folder held only generic names that differed by modification time (`a.har`, `b.har`, `c.har`; `older.har`, `newer.har`), so no fixture ever put a same-kind file that the rule must skip next to the intended one.

**Solution**: only names matching `deepseek-YYYY-MM-DD.har` qualify; the latest name date wins, and a date tie goes to the latest modification time. The spec puts a newer purpose recording next to the main recording for both `selectNewestHar` and `locateNewestHar`, includes a case where an older name date has the newer modification time, includes a date tie, and includes a folder holding only purpose recordings (the selector returns null and the locator throws, naming the directory and the re-record procedure). On the pre-fix code six of these cases failed; the main-recording case received the newer purpose recording.

**Prevention**: A test of code that picks one item from a set of candidates (a file in a folder, a key in storage, a record in a list) MUST seed the set as the real environment fills it: the intended item plus every same-kind neighbour the rule must skip (suffixed or purpose copies, backups, drafts, older versions). The neighbour MUST win on the naive criterion (newer, first in order, broader pattern match), so that only the real selection rule separates them. Fixtures whose candidates differ only in the attribute the code sorts by are not evidence, because they pass any selector that sorts by that attribute. A test MUST also cover a set that holds only neighbours and assert the documented no-match outcome.

**Check**: List the item kinds that really live in the candidate set (read the directory, storage area or list the code scans in a real or recorded environment), confirm the fixture holds at least one neighbour of each kind that beats the intended item on the naive criterion, and confirm the test is red when the selection rule is replaced by the naive one (sort by modification time, take the first match).
