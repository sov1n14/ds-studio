# Visibility Guards Need a Live Capture

**Cause**: v4.36.2, `content/auto-open-sidebar.js`. Clicking DeepSeek's collapsed-rail open button in the narrow hamburger layout opens the sidebar as a drawer, so the fix assumed the rail button is CSS-hidden in that layout and gated activation on the rail button's own `checkVisibility()`. On the live page the rail button is rendered and visible (34×34) in BOTH the narrow and the desktop layout, so the guard never blocked and the extension kept clicking. The only discriminating signal is the header hamburger (`SIDEBAR_HAMBURGER_BUTTON_SELECTOR`): its `checkVisibility()` is true in the narrow layout and false on desktop, where it stays mounted but hidden. The unit test missed the bug because it stubbed `checkVisibility` to `false` on the rail button: it encoded an unverified assumption about which element is hidden instead of a live-page fact, so the stub made the guard pass by construction, a tautology.

**Solution**: v4.36.3 gates the rail-button activation on the visibility of `SIDEBAR_HAMBURGER_BUTTON_SELECTOR`, chosen from a `[DSS-DBG]` capture on the live page that logged `checkVisibility()` and `getBoundingClientRect()` of both elements in each layout. `test/unit/auto-open-sidebar.spec.js:183-220` stubs `checkVisibility` only on the hamburger, per the capture: while the hamburger is visible the rail button is not activated and the episode is not consumed; once the hamburger is hidden the rail button is activated once; a hamburger without a `checkVisibility` method (happy-dom 16.8.1) does not block. Observed red of the hamburger case on pre-fix (4.36.2) code: `AssertionError: [open, search, new-chat] while the header hamburger is visible (narrow layout): expected [ 1, +0, +0 ] to deeply equal [ +0, +0, +0 ]` at `test/unit/auto-open-sidebar.spec.js:196` (line number after the v4.36.4 deletion of the rail-button case). The v4.36.4 change removes the rail-button `_isVisible` gate and its spec case that stubbed `checkVisibility` to `false` on the rail button, because the live capture showed the rail button visible in both layouts.

**Cause**: through v4.39.4, fixed in v4.39.5 — `GoToTop._evaluateVisibility()` in `content/go-top.locate.js` showed the Go Top button only when the first mounted message's `getBoundingClientRect().bottom < 0`. After the native Go Down jump in a long conversation the list sits at the bottom, `[data-virtual-list-item-key="1"]` is unmounted, and the first mounted message can be one very tall message: the live capture read `scrollTop` 62438, `clientHeight` 740, first mounted message rect top -3440 and bottom +45, so the guard stayed hidden. The existing visibility specs stubbed `_getFirstMessage` and `_isAtTop` and gave the first message a small rect, so they never modelled a tall first mounted message at the bottom of a long thread, and the stubs made the guard follow the test author's assumption that "scrolled far" implies "first message above the viewport".

**Solution**: `_evaluateVisibility()` also shows the button when `scrollTop >= clientHeight`, with the hide rule evaluated first. `test/unit/go-top.long-thread-visibility.spec.js` stubs nothing in the module: it mounts the captured live list, gives the scroller the captured geometry (`scrollTop` 62438, `clientHeight` 740, `scrollHeight` 63178), gives the mounted messages the captured rects, and drives the real scroll listener and the real first-message and at-top lookups; four guard cases cover the top, the keep-current band in both directions, and the existing show rule. On pre-fix code 1 of the 5 tests failed (the long-thread bottom state stayed hidden) and 4 passed.

**Prevention**: Before writing a guard that decides by visibility or layout, capture on the live page the values of every candidate element in each layout the guard must tell apart: `checkVisibility()`, `getBoundingClientRect()`, and computed `display`. Build the guard on the element whose captured values actually differ between layouts. The test MUST record those captured facts in a comment above the case, and MUST stub visibility only to reproduce a captured value; when the guard decides by the rect of a mounted host element, the fixture MUST also model the captured extreme (a very tall element, an unmounted anchor, a large scroll offset) and MUST NOT limit rects to small ones that make "far from the top" and "first element above the viewport" coincide; it MUST NOT stub visibility on an element merely assumed to be hidden, because such a stub proves only that the code reads the stub.

**Check**: Before trusting a visibility-guard test, confirm its comment cites a live capture (element, layout, `checkVisibility()`, rect, computed `display`) and that every stubbed value matches that capture for the layout the case models. Then confirm the fixture gives every candidate element its captured value, including elements that look the same in both layouts (here, the rail button visible in both), so a guard reading the wrong element would go red. For a guard that reads a mounted element's rect, confirm the fixture holds at least one state captured from a long page in which that rect still overlaps the viewport although the page is far from the top.
