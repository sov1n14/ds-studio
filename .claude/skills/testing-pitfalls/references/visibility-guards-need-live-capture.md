# Visibility Guards Need a Live Capture

**Cause**: v4.36.2, `content/auto-open-sidebar.js`. Clicking DeepSeek's collapsed-rail open button in the narrow hamburger layout opens the sidebar as a drawer, so the fix assumed the rail button is CSS-hidden in that layout and gated activation on the rail button's own `checkVisibility()`. On the live page the rail button is rendered and visible (34×34) in BOTH the narrow and the desktop layout, so the guard never blocked and the extension kept clicking. The only discriminating signal is the header hamburger (`SIDEBAR_HAMBURGER_BUTTON_SELECTOR`): its `checkVisibility()` is true in the narrow layout and false on desktop, where it stays mounted but hidden. The unit test missed the bug because it stubbed `checkVisibility` to `false` on the rail button: it encoded an unverified assumption about which element is hidden instead of a live-page fact, so the stub made the guard pass by construction, a tautology.

**Solution**: v4.36.3 gates the rail-button activation on the visibility of `SIDEBAR_HAMBURGER_BUTTON_SELECTOR`, chosen from a `[DSS-DBG]` capture on the live page that logged `checkVisibility()` and `getBoundingClientRect()` of both elements in each layout. `test/unit/auto-open-sidebar.spec.js:183-220` stubs `checkVisibility` only on the hamburger, per the capture: while the hamburger is visible the rail button is not activated and the episode is not consumed; once the hamburger is hidden the rail button is activated once; a hamburger without a `checkVisibility` method (happy-dom 16.8.1) does not block. Observed red of the hamburger case on pre-fix (4.36.2) code: `AssertionError: [open, search, new-chat] while the header hamburger is visible (narrow layout): expected [ 1, +0, +0 ] to deeply equal [ +0, +0, +0 ]` at `test/unit/auto-open-sidebar.spec.js:196` (line number after the v4.36.4 deletion of the rail-button case). The v4.36.4 change removes the rail-button `_isVisible` gate and its spec case that stubbed `checkVisibility` to `false` on the rail button, because the live capture showed the rail button visible in both layouts.

**Prevention**: Before writing a guard that decides by visibility or layout, capture on the live page the values of every candidate element in each layout the guard must tell apart: `checkVisibility()`, `getBoundingClientRect()`, and computed `display`. Build the guard on the element whose captured values actually differ between layouts. The test MUST record those captured facts in a comment above the case, and MUST stub visibility only to reproduce a captured value; it MUST NOT stub visibility on an element merely assumed to be hidden, because such a stub proves only that the code reads the stub.

**Check**: Before trusting a visibility-guard test, confirm its comment cites a live capture (element, layout, `checkVisibility()`, rect, computed `display`) and that every stubbed value matches that capture for the layout the case models. Then confirm the fixture gives every candidate element its captured value, including elements that look the same in both layouts (here, the rail button visible in both), so a guard reading the wrong element would go red.
