# Close and Unload Paths: Assert What Is Persisted at the Instant of Close

**Cause**: through v4.39.6, fixed in v4.39.7 — pressing `Esc` in the prompt group editor window (`popup/editor/editor.js`, shipped in v4.15.0) called `window.close()` at once. The save is an async multi-step storage chain, and the `pagehide` / `visibilitychange` backstops are fire-and-forget, so they cannot finish during unload; the typed name and content were lost. `test/unit/editor.spec.js` missed it three ways: it asserted source strings (`toContain('window.close()')`, `debouncedSave()`) that pinned the buggy wiring, the `DOMContentLoaded` closure that holds the handlers was never executed, and every save assertion waited for the save to settle, so nothing checked the persisted state at the moment the window closed.

**Solution**: `popup/editor/editor.autosave.js` adds a controller whose `flush()` the `Esc` handler awaits (bounded by `ESC_SAVE_WAIT_MS`) before calling `window.close()`. `test/unit/editor.escape-save.scenario.spec.js` drives the real editor through `test/helpers/editor-window-harness.js` (real `editor.js`, real `StorageManager`, an in-memory `chrome.storage`; only `chrome.storage` and `window.close` are doubles), and the `window.close` spy snapshots storage at the call. On the 4.39.6 code 2 of the 6 tests failed (dirty `Esc`: `expected 'poc original' to be 'poc renamed'`; duplicate name: `expected 1 to be +0`) and 4 passed; all 6 pass now. The 4 source-text cases in `test/unit/editor.spec.js` were deleted.

**Cause (teardown started from outside the page)**: through v4.39.11 — the same editor window still lost its last edits when another context tore it down. `background/editor-window-routes.js` closed the tracked editor windows when DeepSeek got focus, and `utils/window-control.js` `openSingletonWindow` navigated the same window when the popup "Edit" of another group was clicked; neither waited for the pending save. Autosave fires 500 ms after the last input, and a preset save awaits about 9 storage reads before its first write, so a typed edit is still unsaved for a noticeable time. `test/unit/editor-window-routes.spec.js` and the window-control specs missed it because they stubbed `chrome.windows.remove` and `chrome.tabs.update` and never opened the real editor page, so no save was ever pending or in flight when the teardown call ran. The Esc fix above covered only the teardown the page itself starts.

**Solution (flush handshake)**: before `chrome.windows.remove` or `chrome.tabs.update`, the caller awaits `requestEditorFlush(slot)` from `utils/editor-flush-channel.js`, a `chrome.runtime.sendMessage` race bounded at 1000 ms that returns `undefined` on rejection, synchronous throw, missing reply, or timeout. The editor page registers `listenForFlushRequests(slot, answerFlush)`, answers only for its own slot, and waits at most 800 ms for the save, so a timeout reply still arrives before the caller gives up. A `duplicate` status keeps the window open and cancels the navigation. `test/unit/editor-window-routes.flush-before-close.scenario.spec.js` and `test/unit/window-control.flush-before-navigate.scenario.spec.js` open the real editor page through `test/helpers/editor-window-harness.js`, type without blurring, trigger the teardown, and snapshot storage inside the `windows.remove` / `tabs.update` double (`test/helpers/editor-window-flush-doubles.js`). Both specs were red on the pre-fix code and pass now.

**Prevention**: A test for any path that closes, unloads, or navigates away from a page that holds unsaved state (`Esc`, a close button, `pagehide`, a route change) MUST execute the real handler and assert what is persisted at the instant the close is requested, by snapshotting storage inside the `window.close` (or equivalent) spy. This covers every initiator of the teardown, not only the page's own handlers: a background route that closes the window, or a popup call that navigates it, MUST be tested with the real page open and an edit typed but not yet saved (debounce not fired, no blur), with only the trust boundary (`chrome.windows`, `chrome.tabs`, `chrome.runtime`) doubled. A fire-and-forget async flush inside `pagehide` or `visibilitychange` is not a save guarantee and MUST NOT be accepted as the reason a close path is lossless. A test of a teardown caller that stubs the remove or navigate call and has no page behind it proves nothing about data loss. A test MUST NOT assert source text of the file under test.

**Check**: Before trusting a close-path spec, confirm that the close spy reads storage at call time and that the expectation does not run after the save settles. For a teardown started outside the page, confirm that the spec types into the real page and that the teardown call lands before the 500 ms debounce could have saved on its own. Revert the wait in the handler or the flush request and confirm the spec goes red with the stored value still the original. Search the spec for `readFileSync` of the production file and for `toContain` on its text, and replace each hit with a behavior assertion.
