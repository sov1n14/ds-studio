# DOM Fixture Completeness

**Cause**: v4.33.18 → v4.33.26 — `findSendButtonForTextarea` regression. `querySelector` returns the first DOM-order match. The attachment button matched the same selector as the send button and appeared first in the real DOM. Tests passed because the fixture only contained the send button — no attachment button to expose the ordering conflict.

**Cause** (same slot, other UI state): v4.35.3 — clicking DeepSeek's Stop Generating button injected the prompt prefix and re-dispatched a click. `isSendButtonCandidate` in `content/prompt-injector.send-button.js` had a structural fallback that accepted any `div.ds-button[role=button]` with an svg and the `ds-button--primary` + `ds-button--filled` classes. The Stop button replaces the send button while a reply streams and is byte-identical except the SVG path (`M2 4.88…` vs `M8.3125…`). Fixtures modelled only the idle composer (send and attachment buttons), and the case "accepts send button via structural fallback when SVG path changes" used `makeSendButtonWithChangedIcon` — structurally a Stop button — so a test asserted the bug as desired behavior. The tolerant matcher was tested only for what it should accept, never for what it must reject.

**Cause** (fallback matchers, real markup): both fallbacks passed their tests while returning the wrong element, because their fixtures were hand-written trees the page never renders. The new-chat structural fallback in `content/preset-overlay.resolvers.js` returned the first `div[role=button]` after the title in document order, which on DeepSeek's mobile-UA home header is the download-app pill, not the new-chat button. The toolbar fallback in `content/censor-reply-restore.detection.js` counted descendant icon buttons, so on the real markup it returned the outer `.ds-flex` wrapper instead of the toolbar group whose icon buttons are its direct children. The synthetic trees in `test/unit/preset-overlay.dom-resolvers.spec.js` (structural-fallback group) and `test/unit/censor-reply-restore.detection.spec.js` put the new-chat button first after the title and omitted the wrapper, so each fallback was checked only against a shape the page never renders.

**Cause** (nested host element): the extension cloned the positioning wrapper instead of the control it holds, and the defect was present at HEAD 0872dfe. On the live page the go-bottom class `_0706cde` sits on a wrapper div whose only child is the real `div[role=button].ds-button--floating.ds-button--circle`. `content/go-top.render.combined.js` cloned that wrapper, so the `.dsw-gotop` button held a nested copy of the real button. After the native wrapper unmounted, the fallback in `content/go-top.locate.js` matched that nested copy, so stacked-to-solo never fired and the button sat 42px too high. The tests missed it because `createNativeButton()` in `test/helpers/go-top-fixtures.js` hand-built a flat `role=button` carrying `_0706cde`, one DOM level shallower than the page. Every clone, locate and observer test used that fixture, and mutation testing could not expose it because the fixture shape itself was wrong.

**Cause** (happy-dom selector semantics): happy-dom 16.8.1 drops the leading `>` of a multi-level relative `:has()` argument, so `:has(> div > .x > .y)` behaves like `:has(div > .x > .y)`, while `:has(> .x > .y)` is evaluated correctly. Its scoped `el.querySelector(sel)` also ignores ancestors outside `el` that `sel` references, while Chrome matches them as the spec requires. Checked against Chrome 156 on 28 real DeepSeek snapshots with 58 selectors (1624 element pairs), happy-dom 16.8.1 disagreed on 317 pairs and happy-dom 21.0.4 on 324 (both fail the same 18 selectors; 21.0.4 also throws on `:has(~ .x)`), while jsdom 31.0.0 disagreed on none. On real pages happy-dom matched `SIDEBAR_WRAPPER` and `FLOATING_BUTTON_BAR` 6253 times where Chrome matched them 28 times. A code comment at `content/go-top.locate.js:183` reports the same class of failure for `:not(.dsw-gotop *)`. A test built on these selectors can pass or fail for a reason unrelated to the code under test.

**Solution**: the fallback was removed. `makeStopButton()` and `makeActionsRowWithStopButton()` in `test/helpers/send-button-fixtures.js` are built verbatim from `to-do/samples/stop-button.html`; `test/unit/prompt-injector.send-button.spec.js` asserts the Stop button is rejected alone and inside the real actions row, and `test/unit/prompt-injector.controller.spec.js` asserts a Stop click leaves the textarea unchanged and the event not prevented. On pre-fix code, `isSendButtonCandidate(stopButton)` and its actions-row and unknown-icon variants failed with "expected true to be false", `findSendButtonForTextarea` returned the Stop button instead of `null`, and the controller test failed because clicking Stop wrote the injected prefix wrapper around the global prompt into an empty textarea (expected `''`).

**Solution** (fallback matchers, real markup): the fallback fixtures are copies of live snapshots under `test/fixtures/ds-snapshots/` (`mobile-ua-home-header.html`, `conv2-finished-visible-items.html`) with personal text replaced by placeholders. The new `test/unit/preset-overlay.resolvers.real-markup.spec.js` and `test/unit/censor-reply-restore.detection.real-markup.spec.js` reach each fallback by minimal mutation: the new-chat button loses its inline `min-width` style (case at `:50`), and the toolbar group's hashed classes become a bare `ds-flex` (case at `:47`). On pre-fix code both cases failed red (observed): the resolver returned the download-app pill, and the toolbar lookup returned the outer wrapper. The synthetic-markup cases stayed green, which is why the earlier suites passed.

**Solution** (nested host element): the render clones the inner `[role=button]` instead of the wrapper, and the fallback in `content/go-top.locate.js` skips any match inside `.dsw-gotop` with a JS `closest()` filter. Built from the real message-list markup in `test/fixtures/ds-snapshots/conv2-finished-message-list.html`, the tests `test/unit/go-top.locate.spec.js:225`, `test/unit/go-top.render-combined.mutant-killers.spec.js:199` and `:223` failed red on pre-fix code (observed), where the flat fixture had kept them green.

**Solution** (happy-dom selector semantics): a spec that asserts selector or DOM-structure behavior opts into jsdom with the `// @vitest-environment jsdom` docblock, which works per file; upgrading happy-dom does not fix the disagreement. A jsdom spec may need `scrollIntoView` and `location` stubs, because `test/helpers/set-pathname.js` is specific to happy-dom.

**Prevention**: Test fixtures for a UI region MUST include all interactive sibling elements present in the real page, not just the element under test. When code uses `querySelector` or any first-match API, omitting siblings that match the same selector hides ordering-dependent bugs. Fixtures MUST also cover every real element that occupies the same slot or shares the same classes in another UI state (generating vs idle, mobile vs desktop). Any tolerant or fallback matcher over host-page elements MUST have negative tests against each such element, built from captured live markup; a test asserting "accepts unknown variant X" MUST name the real non-target elements checked and confirm none looks like X. A fallback path MUST be exercised on a fixture copied from a captured live snapshot, never a hand-written tree, and the test MUST reach the fallback by minimal mutation of that markup (strip only the class or inline style the primary path relies on), keeping the real nesting and sibling order. A fixture for a host element MUST keep every real wrapper level around that element, copied from a captured snapshot, because a flat hand-built element passes every clone and lookup test that the page would fail.

**Prevention** (happy-dom selector semantics): a spec that asserts selector or DOM-structure behavior MUST opt into jsdom with the `// @vitest-environment jsdom` docblock. A test asserting a negative match through `:has()` or an ancestor-referencing selector MUST confirm the result against headless Chrome on a copy of a captured snapshot under `test/fixtures/ds-snapshots/` before trusting it.

**Check**: Before finalizing a DOM fixture, compare against real page structure (`to-do/samples/` or `test/fixtures/ds-snapshots/` for HTML snapshots). Every element matching the selector under test must appear in the fixture, in real DOM order. For a tolerant matcher, list every UI state that reuses its slot or classes, confirm a captured sample exists for each, and confirm each non-target element in those samples has a rejection test. For a fallback test, confirm the fixture is a copy of one of those captured snapshots with only personal text replaced, and that the mutation changes only the class or style the primary path reads. For a clone-and-query fixture, compare the ancestor chain of the target in the fixture with the same chain in the captured snapshot, and confirm the test is red on pre-fix code when that snapshot markup replaces the fixture.

**Check** (happy-dom selector semantics): compare the selector's match list in headless Chrome (Playwright, a one-off check outside the committed tests) with the list the spec's environment returns on the same markup; a difference means that environment is not evidence.
