# Transient UI State: Sample Every Step, Not Only the Settled Result

**Cause**: through v4.39.24, fixed in v4.39.25 — on a fresh load of a chat bound to prompt group B, the overlay rendered the stored global `activePresetId` A synchronously at overlay start and showed B only after an async settings read. On SPA navigation from a chat bound to A to a chat bound to B, the overlay kept showing A until the async reads finished. Every existing test asserted only the shown value after settling, so a wrong group shown for a moment never failed a test.

**Solution**: the overlay starts with the group resolved for the chat in the URL, and navigation updates the overlay at once, except while a new chat is waiting for its uuid. `test/unit/content-script.overlay-flash.scenario.spec.js` wraps `chrome.storage.*.get` with a 5 ms delay and samples the shown group at every storage delivery. On pre-fix code 2 of 3 cases failed with "chat X is bound to B, so the overlay must never show A ... expected [ …(21) ] to deeply equal []".

**Cause**: through v4.39.26, fixed in v4.39.27 — after a prompt group was picked on the new-chat page and the message was sent, the overlay showed the blank option until the service worker wrote the bind for the created chat. The overlay resolved a chat with a uuid only from the chat-to-group map, and the created chat is absent from the map until the bind lands. When the pick's settings broadcast resumed after the page had switched to the created chat, it resolved `''`. The overlay-flash spec's new-chat case sampled only after a wall-clock delay and allowed `''`, so the blank window between the pick's broadcast and the bind was never sampled.

**Solution**: a chat awaiting its bind resolves like the new-chat page (pending pick, then pinned group) until the bind flow ends. `test/unit/content-script.new-chat-blank-flash.scenario.spec.js` times the send by counting storage deliveries after the pick (cases 33, 37, 41, 45, 47), with an in-flight precondition, and samples the shown group at every step. On pre-fix code 5 cases failed with "G was picked and sent, so from the send until the created chat settles the overlay must never show the blank option; samples: ... expected [ …(63) ] to deeply equal []".

**Cause**: a defect in the in-progress v4.39.27 fix, caught by tests before commit, never shipped — returning to a created chat that still awaited its bind showed the blank option at the navigation render and for several storage deliveries, then the pending group G. The earlier assertion of the return-navigation case in `test/unit/chat-binding-controller.blank-flash-mutant-killers.failed-bind-flow.spec.js` started checking at the first G sample, so the blank prefix passed unnoticed.

**Solution**: the navigation render resolves with the controller's last-read settings snapshot, so it shows the pending pick at once. The return-navigation case samples from the navigation render itself. On the in-progress code it recorded 17 blank samples, then `preset-G`.

**Prevention**: UI that resolves its value through async reads (prompt group label, toggle state, width) MUST have a test that records the shown value at every async step, from first render through settling, and asserts that the record holds no wrong value. A final-state assertion alone is not enough. Delay the boundary reads so intermediate renders become observable, and cover each entry path: fresh load and SPA navigation. Time a race by counting boundary deliveries, not wall clock, and never let an allow-list (such as `''`) absorb the transient state under test. Start sampling at the triggering render itself, never at the first correct value. A storage write that triggers a render MUST differ from the stored value, because Chrome fires no `onChanged` for an unchanged write.

**Check**: For each async-resolved UI value, confirm a test samples it at each storage delivery or render and asserts on the whole sample list. Then make the first render use the stored global default and confirm that test goes red. For each race the test sets up, confirm it counts deliveries to place the event and that its assertion does not accept the transient value. Confirm the sample list starts at the triggering render (navigation, load, send) itself, never at the first correct value.
