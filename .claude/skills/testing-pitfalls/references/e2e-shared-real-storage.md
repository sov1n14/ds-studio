# E2E Specs Share One Real Storage

**Cause**: every E2E spec runs in the same persistent profile, so all specs share one real `chrome.storage.sync` and its per-minute write quota (Chrome rejects a write once 120 writes fall inside a sliding 60 s). Popup specs that toggle synced settings had written 119 sync writes in the 60 s before the prompt-group spec ran, so its next sync write failed with `This request exceeds the MAX_WRITE_OPERATIONS_PER_MINUTE quota.` and the full suite failed while every spec passed when run alone. Each spec was only ever checked by itself or in a quieter order, and no helper treated the quota as a shared resource, so the failure depended on which specs ran in the minute before.

**Solution**: `test/e2e/helpers/extension.js` `evaluateInWorker`, the single path for every test-side storage write, retries the whole worker call once a second while the error names `MAX_WRITE_OPERATIONS_PER_MINUTE`, until the budget in `QUOTA_RETRY_BUDGET_MS` runs out, then rethrows; any other error, the hourly quota included, is thrown at once. Observed red on pre-fix code: the full suite ran twice and finished 90 of 93 both times, with `e2e/prompt-groups.e2e.js:53` failing on that quota error from `helpers/settings.js` `setBothAreas`.

**Cause**: `test/e2e/websearch-toggle.e2e.js` turned the master switch on and set the web-search start mode in one write, `settings.set({ isEnabled: true, dsWebSearchToggle: 'on' })`. The extension never writes those two keys together: each user action writes one key. While the profile still held a stored mode of `'off'` from an earlier run, the combined write hit an ordering race in the extension's change handling that no user action can produce, and the Search toggle stayed released. The spec's precondition therefore depended on what the profile happened to hold before the spec ran.

**Solution**: both tests write the mode first and `isEnabled: true` second, one key per write, as the extension does. Observed red on pre-fix code with the profile holding `dsWebSearchToggle: 'off'` in both areas and `isEnabled: false` in local: both tests timed out on the Search-pressed precondition (Expected: true, Received: false); after the change both pass from the same profile state.

**Cause**: `test/e2e/prompt-groups.e2e.js` adds a prompt group through the popup's + button, and the new group carries its own `globalPromptEnabled: true`. So, by the resolution rule in [STORAGE](../../../../docs/architecture/STORAGE.md#state-management), the device-level `globalPromptEnabled: false` that the spec's `beforeEach` sets did not stop injection. The spec never set `globalDefaultPrompt`, so whatever the profile held went into the sent prompt and the exact assertion failed. A `global-prompt.e2e.js` run killed mid-test skipped its `finally` restore and left a non-empty value in the profile; the settings fixture snapshots each key on first touch and restores that snapshot, so later runs took the leftover as the original value and kept it. The existing tests missed it because the spec was correct only on a profile whose global prompt was empty, and this spec did not pin that key.

**Solution**: `test/e2e/prompt-groups.e2e.js` pins `settings.setInBothAreas({ globalDefaultPrompt: '' })` before the page reload, the same pattern as `test/e2e/global-prompt.e2e.js`, and the exact assertion stays. Observed red on pre-fix code: three consecutive runs failed with an extra line carrying the leftover global prompt ahead of the group content.

**Cause**: `test/e2e/backup-restore.e2e.js` Import Settings read its "keeps the device-local toggles" expectation from the values the profile already held. The persistent `.browser-profile/` always held the three device-local toggles, because an earlier popup open had filled their defaults (`utils/storage-manager.init.js` fills a local-only key only while it is `undefined`). On the fresh temporary profile of the offline lane those keys were absent when the test read them, so the expected value was `undefined`. The existing tests missed it because they only ever ran on a profile that earlier runs had already filled.

**Solution**: the test pins the three toggles with `setLocal(context, localToggles)` before it reads the before state, so the precondition holds on any profile.

**Cause**: `test/e2e/temp-chat.e2e.js` `openKeptFromSidebar` clicked a kept chat in the native sidebar and assumed the sidebar was expanded. The "home page on a phone" test in `test/e2e/selector-health.e2e.js` emulated a 412px phone, and DeepSeek collapsed its sidebar there and stored `"siderCollapsed":true` in `localStorage['__appKit_@deepseek/chat_lastSessionValue']`. That host-page value persisted in the worker's shared browser profile, so the next spec in the same worker loaded the page with the sidebar collapsed and the click timed out on a 0x0, invisible link. The spec passed alone (17 passed, twice) and failed only in the full offline lane (190 tests, 2 workers), where `selector-health` sorts before `temp-chat` in one worker. The existing tests missed it because the spec was only checked alone, and the phone test had been certified with only the new spec pair, not the full lane. `test/e2e/mobile-sidebar-swipe.e2e.js` leaked the same value; its last test reopens the sidebar, which hid the leak.

**Solution**: `openKeptFromSidebar` first sets the sidebar expanded with `setNativeSidebar(page, false)` from `test/e2e/helpers/sidebar.js`, and the phone test in `test/e2e/selector-health.e2e.js` restores the stored session value in a `finally`. Observed red on pre-fix code: `npx playwright test -c playwright.offline.config.js e2e/selector-health.e2e.js e2e/temp-chat.e2e.js --workers=1` reported 19 passed and 1 failed.

**Prevention**: Route every test-side write to shared real storage through the one helper that retries on the per-minute quota error, and add no write path that bypasses it. **MUST** write settings in an E2E spec with the same key grouping and order the extension uses, one key per write wherever one user action writes one key. **MUST** set every key a spec's precondition depends on, including each key an enabled per-item flag injects, so the outcome is the same whatever value the profile held before the spec ran. When a test creates data through the UI, **MUST** check which per-item flags the UI defaults to on and pin every key those flags pull in. **MUST** pin such keys inside the spec itself; a killed run leaves them behind and no later run clears them. **MUST** pin every key a precondition reads, including keys the extension fills with defaults on first open, so the spec passes on an empty profile as well as one an earlier run filled. **MUST** treat host-page `localStorage` in the shared profile as shared storage too: a spec that changes host layout state (sidebar collapse, viewport emulation) restores it in a `finally`, and a spec whose step depends on a host layout state sets that state itself before the step.

**Check**: Before trusting an E2E spec, confirm each of its storage writes goes through `evaluateInWorker` and run it inside the full suite in its normal order, not only alone. For each `settings.set` holding more than one key, confirm the extension writes those keys together, or split the call. Then store the opposite of each target value in the profile, and a non-empty value for each key that an enabled per-item flag injects. Run the spec once and confirm it still passes. For each item the spec creates through the UI, list the per-item flags it defaults on and confirm the spec pins every key those flags read. Run the spec once on a fresh empty profile (the offline lane's temporary user-data directory). Confirm it passes without relying on defaults the extension fills later. For each spec that emulates a viewport or toggles a host-page layout control, run it followed by every later spec in the same worker with `--workers=1`, then run the full offline lane, and confirm no spec depends on a host layout state an earlier spec left in `localStorage`.
