# Stale In-Memory Copy: Test the Save After Another Context Wrote

**Cause**: through 4.39.22, fixed in 4.39.23 — `content/censor-reply-restore.storage.js` loaded `restored_messages` from `chrome.storage.local` into memory once when the tab started, and each later save wrote the whole in-memory map back without reading storage first. A record written by another context after the tab loaded — a popup import through `StorageManager.mergeRestoredMessages`, or another open tab's save — was erased by the next save in this tab. The existing `test/unit/censor-reply-restore.*.spec.js` tests drove a single tab and asserted only that tab's in-memory map, so no test ever wrote storage from a second context between load and save, or read what storage held afterwards.

**Solution**: the save reads `restored_messages` from storage, merges the cleaned stored records with the tab's records, and writes the merged map (read-merge-write). `test/unit/censor-reply-restore.stale-tab-save.scenario.spec.js` loads the real `StorageManager` and two real module instances (`vi.resetModules()`) over one shared `chrome.storage` double, and asserts the keys persisted in storage after a popup import then a tab save, after two tabs each save, after three saves fired without awaiting, and that an imported record lacking `censored: true` does not enter the tab's records. Observed red on pre-fix code: 2 of 4 failed, first: "the tab save must keep the imported record and add its own: expected [ 'sessLIVE::9' ] to deeply equal [ 'sessIMP::5', 'sessLIVE::9' ]".

**Cause**: the read-merge-write fix in 4.39.23 opened a second hole before release — a save that read the snapshot, then wrote after a "clear all" committed by another context, wrote back the pre-clear records it had read and undid the clear. A storage-only clear (the tab message lost) and two saves in one tab straddling a clear also lost or resurrected records, and a save after a clear overwrote a record another tab wrote after the clear. The new scenario tests only ever added records from the second writer; no test interleaved a destructive write by the second writer between the save's read and its write. A failed storage read was reported as generation 0, because the shared safe read turns a failure into `{}`, so after one clear a save with failing reads dropped the tab's post-clear records; the read-failure tests ran only at generation 0.

**Solution**: the clear bumps a local-only clear generation (`dsRestoredMessagesClearGeneration`) in the same `set` as the cleared key; each save tags its in-memory records with the generation they belong to, drops records of an older generation, and re-reads the snapshot (a bounded number of times) to merge records written after the clear. `test/unit/censor-reply-restore.stale-tab-save.scenario.spec.js` holds the save's read behind a gate, commits a clear, then releases it; observed red before the guard: "a record that existed before the clear must not be written back by the save: expected [ 'sessIMP::5', 'sessLIVE::9' ] to not include 'sessIMP::5'". `test/unit/censor-reply-restore.clear-generation.scenario.spec.js` covers the storage-only clear, two saves in one tab straddling a clear, and a post-clear record from another tab; observed reds: "expected [ 'sNEW::2' ] to deeply equal [ 'sNEW::1', 'sNEW::2' ]", "expected [ 'sNEW::1', 'sOLD::1' ] to deeply equal [ 'sNEW::1' ]", "expected [ 'sNEW::1' ] to deeply equal [ 'sB::1', 'sNEW::1' ]". The restored-message reads report a failure distinctly from an empty result; `test/unit/censor-reply-restore.clear-generation.scenario.spec.js` runs the failing-read save after a clear; observed red: "expected [ 'sB::2' ] to deeply equal [ 'sA::1', 'sB::2' ]".

**Cause**: the save path of the same module never had its write failure tested: `_onFragmentComplete` called `_saveFragment` without awaiting it and without a `catch`, and `_safeSet` swallowed a synchronous `set` throw silently, so a failed save write escaped as an unhandled rejection or vanished without a log. Every save test seeded a working storage double, so the write always succeeded.

**Solution**: `_onFragmentComplete` catches the rejection of the save and logs it with `console.error('[DSS] censor-reply-restore: save restored message failed:', err)`, and `_safeSet` logs a `[DSS]` warning for a synchronous throw and still resolves. `test/unit/censor-reply-restore.save-write-failure.scenario.spec.js` fails the write of `restored_messages` as an asynchronous rejection and as a synchronous throw of `set`; observed reds on pre-fix code: "the failed save write must not escape as an unhandled rejection: expected [ Array(1) ] to deeply equal []" and "a [DSS] console.error or console.warn call must carry the write failure: expected 0 to be greater than 0".

**Prevention**: A test of any module that caches a storage key in memory and later writes that key MUST include a second writer — another real module instance or the real `StorageManager` path the popup uses — that writes the same key after the cached load and before the save under test. The test MUST assert what storage holds after the save, never the saving module's in-memory copy. Use real module instances over one shared storage double, never a mocked sibling module. Include concurrent saves from one context fired without awaiting. When the writer merges a read snapshot, the test MUST also commit each destructive write by another writer (clear, delete) between that read and the write, once with the notification message delivered and once with storage changed alone, and run two overlapping saves in the same context across that destructive write. Run each failure-path test also in a non-initial state (after a clear, generation 1 or higher), and check that the failure value of a safe-read wrapper cannot pass as a valid value. For each write path, test the write failing, as an asynchronous rejection and as a synchronous throw, and assert that the failure is logged and not left unhandled.

**Check**: Restore the pre-fix save and confirm the persisted-key assertion fails; a pass means the second writer never wrote between load and save, or the assertion reads memory instead of storage. For a merging writer, hold the save's read, commit a clear from another context, release the read, and assert that no pre-clear record survives and that post-clear records from other contexts do.
