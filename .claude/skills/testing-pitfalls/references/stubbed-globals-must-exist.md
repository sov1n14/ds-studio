# Cross-Script Globals: Load the Real Scripts

**Cause**: in v4.39.18 every incomplete Markdown export (cancelled, stalled, scroll-interrupted) downloaded nothing and showed no warning toast. `content/content-script.export.js:185` called `showHarvestToastIncomplete(...)` as a bare global, but no content script defines that name: `content/harvest.toast.js` publishes it only inside the `globalThis.__DS_Harvest_toast` bundle, and `content/harvest.js:24-27` binds only `showHarvestToastScrolling`, `showHarvestToastCapturing` and `hideHarvestToast` from it. The ReferenceError skipped `downloadMarkdown`, and the `.catch` in `content/content-script.js:231-233` swallowed it. `test/unit/content-script.export.spec.js:312` and `test/unit/export-collapsed-thinking.scenario.spec.js:92` called `vi.stubGlobal('showHarvestToastIncomplete', ...)`, so the specs themselves supplied the global the browser lacks, and every incomplete-export test passed. Vitest also imports each script as its own module, so no import-based spec can observe what one classic script can or cannot see of another.

**Solution**: `test/unit/export-incomplete-cancel.scenario.spec.js` runs the export-path scripts as classic scripts in one fresh `vm` context that acts as the isolated-world global, in `manifest.json` `content_scripts` order, stubs only Blob, `URL.createObjectURL`, `alert` and the download navigation, presses the real progress toast's cancel button, and asserts the downloaded file, its last line `> ⚠️ Export may be incomplete (2 messages captured): the export was cancelled.` and a visible `.dss-harvest-toast--incomplete`. On the 4.39.18 code, `npx vitest run unit/export-incomplete-cancel.scenario.spec.js` gave `Tests  1 failed | 1 passed (2)` with "the cancelled export downloaded no Markdown file; the export rejected with ReferenceError: showHarvestToastIncomplete is not defined: expected [] to have a length of 1 but got +0". The bare-global stubs are gone: the collapsed-thinking spec never reaches the toast, and `content-script.export.spec.js` now imports the real `content/harvest.toast.js` and asserts the toast on the page, so its seven incomplete-export tests also fail on the 4.39.18 code with "showHarvestToastIncomplete is not defined". After the fix resolves the toast from `globalThis.__DS_Harvest_toast` at call time, the scenario spec and `content-script.export.spec.js` pass, and a cancelled export still downloads its file when the toast bundle is absent.

**Cause**: in v4.39.42 `content/censor-xhr-hook.js`, `content/temporary-chat-history-hook.js` and `content/temporary-chat-fiber-delete.js` read `globalThis.DSS_TEMP_CHAT_MESSAGE_TYPES` while they load and throw when it is missing, but `content/main-world-injector.js` created each MAIN-world `<script src>` without `async = false`. A dynamically created script runs in the order its fetch finishes, so on a page load where `utils/temporary-chat-message-types.js` arrived after a hook, the hook threw on its first line and never patched XMLHttpRequest or history, and no `DSS_CHAT_CREATE_DETECTED`, `DSS_AUTH_CAPTURED` or `DSS_FRAGMENT_COMPLETE` message was posted. `test/unit/main-world-injector.spec.js` asserted only the order of the appended `src` values, and happy-dom does not model script execution order (its script element reports `async` as false whatever the browser would do), so the append order passed for the very ordering that breaks in Chrome.

**Solution**: `test/unit/main-world-injector.execution-order.spec.js` drives the real injector against a document stand-in that follows the HTML script rules (created scripts are force-async until `async = false`; an async script runs when its fetch finishes; a non-async script waits in an ordered queue), runs the five real source files in a vm context that acts as the MAIN world, lets the test choose which fetch finishes first, and asserts the execution log, the load errors and the answers of the patched history, XHR and fiber-delete hooks. On the 4.39.42 code `npx vitest run main-world-injector` gave `Tests  9 failed | 10 passed (19)`: the three cases where fetches finish in declared order passed, and every reordered case failed with "[DSS] censor-xhr-hook needs utils/temporary-chat-message-types.js injected first" (and the same text for the other two hooks) or with an execution log that was not the declared order. Setting `script.async = false` in `injectScript` turned all 19 green; a local Chromium probe against a local HTTP server confirmed that two scripts inserted with `async = false` and removed at once still run in insertion order, and in fetch-completion order without it.

**Cause**: in v4.39.42 `manifest.json` listed `content/react-click-bridge.shared.js` in both the isolated `content_scripts` entry and the `"world": "MAIN"` entry. Chromium runs a script path once per page, in the first entry that lists it (inferred from three real-Chromium probes, not from the Chromium source), so the isolated entry won, the MAIN world never received `globalThis.DSSReactClickBridgeShared`, and `content/react-click-bridge.main.js` threw its load-order error on every page load. Auto retry, auto continue, auto open sidebar and auto copy did nothing in v4.39.42 and v4.39.43. Three blind spots hid it: `test/unit/react-click-bridge.shared.spec.js` asserted only the order inside each entry and even expected the isolated file in the MAIN entry; the happy-dom harnesses of the auto-click and auto-copy specs give both worlds one shared global, so the missing MAIN-world global never showed; and the offline E2E lane, which loads the real extension and does catch it, was not run for those two versions.

**Solution**: the MAIN entry lists `content/react-click-bridge.shared.main.js`, a byte-identical copy of the shared file. `test/unit/react-click-bridge.shared.spec.js` gained a cross-world manifest test that fails when a file path appears in entries of two different worlds (a missing `world` counts as ISOLATED), and the MAIN-entry test now rejects the isolated file. `test/unit/react-click-bridge.shared-main-copy.spec.js` compares the two files byte for byte. On the v4.39.42 and v4.39.43 code the cross-world test received `["content/react-click-bridge.shared.js"]` as the shared path, the MAIN-entry test failed with "MAIN entry lists the isolated shared file", the byte-identity test failed with "content/react-click-bridge.shared.main.js does not exist", and the load-error test expected `shared.main.js` in the message and received `shared.js`. The offline E2E specs `auto-click.e2e.js` and `auto-copy.e2e.js` gave 6 failed and 2 passed on that code and 8 passed with the fix.

**Prevention**: A test of scripts that a loader injects or appends at run time MUST assert the order they EXECUTE in, not the order they were appended: run the real files in a vm context behind a loader model that finishes the fetches in a chosen order (the dependency last), and assert what the page ends up with. A DOM implementation that does not model script loading (happy-dom) cannot stand in for that model. A test MUST NOT stub, define or assign a global that no production script defines in the same world; supply a collaborator by loading its real script or by replacing the member of the global object that production publishes, such as `globalThis.__DS_Harvest_toast`. A behavior that crosses content scripts through globals MUST have at least one scenario test that runs the real scripts in `manifest.json` order in one shared `vm` context, the way `test/unit/service-worker.*-wiring.spec.js` runs the service worker. An assertion on a collaborator's effect reads the page (the toast element, the downloaded file), not a spy standing in for the collaborator. A manifest wiring test MUST assert which world runs each file path, not only the list order inside one entry: no path may appear in `content_scripts` entries of two different worlds, and a file both worlds need MUST exist as a separate MAIN-world copy that a test compares byte for byte. A harness that gives the isolated and the MAIN world one shared global (happy-dom, a single `vm` context) cannot observe a missing MAIN-world global; a change to `content_scripts` MUST run the offline E2E lane (`npm run test:e2e:offline`) before release.

**Check**: For every `vi.stubGlobal(<name>, ...)` or `globalThis.<name> =` in a test, run `timeout 120 grep -rnw "<name>" content utils background` and confirm one hit defines the name in the world the code under test runs in, as a global property or a top-level declaration (destructuring included); a member of a bundle object or a name declared inside an IIFE does not count. Then run the scenario test with the stub removed and confirm it fails with the ReferenceError the browser would raise whenever production does not define the name. For a dynamically injected script set, also reorder the stand-in's fetch completions so the dependency finishes last, and confirm the test fails on code that leaves `async` at its default. For a `manifest.json` `content_scripts` change, build the map of file path to world over every entry and confirm no path has two worlds; then run `cd test && npx playwright test -c playwright.offline.config.js auto-click.e2e.js auto-copy.e2e.js`, which loads the real extension, and confirm it passes.
