# Host Request Sequence: Model What the Live Page Sends

**Cause**: through v4.39.5, fixed in v4.39.6 — with the temporary conversation switch on, opening an existing conversation and sending a message within about 1 s of page load marked that conversation as temporary, and leaving it deleted it (confirmed live: a kept test conversation was deleted). DeepSeek sends `chat_session/create` on every page load, including the pages of existing conversations, but the extension treated a create request plus a completion request within 1000 ms as proof of a new chat and marked the uuid in the current URL; a pending flag could also mark whatever conversation the next SPA navigation landed on. Every existing spec faked the hook's window messages (`DSS_CHAT_CREATE_DETECTED`, `DSS_CHAT_COMPLETION_DETECTED`) and set state flags such as `createDetected` and `isCompletionDetected` directly, so none of them modelled the request sequence DeepSeek really sends (a create on every page load, a completion body carrying `chat_session_id`). Cases H5 and H6 in `test/unit/temporary-chat-delete.spec.js` (at HEAD 13b74f2) asserted the dangerous behaviour as correct: with both flags set and the URL already on a conversation, that conversation is tracked and sent for deletion. The hook's create-detection spec ran an inline copy of the hook, so a change to the real hook could not turn it red.

**Solution**: a conversation is temporary only when a create response in this page load returned its id and the first send in it (completion request body `chat_session_id`) went out while the switch was on; the hook posts both ids and the content side matches them (`content/temporary-chat-delete.tracking.js`). `test/helpers/deepseek-page-harness.js` runs the real main-world hook and the real history hook in one sandbox whose only fakes are the network boundary, a fake XHR that answers with live-captured request and response bodies (create answers `{code:0,data:{biz_data:{chat_session:{id}}}}`, completion carries `chat_session_id`), and a cross-world `postMessage` bridge that delivers structured-cloned messages asynchronously with `source: window`. The page side is driven as DeepSeek drives it: `createSession()`, `sendCompletion()`, `pushState()`. `test/unit/temporary-chat-delete.existing-chat.scenario.spec.js` asserts the user-visible outcome (which uuid is tracked, which delete requests go out on leaving by tab close, SPA navigation home and SPA navigation to another conversation). On the 4.39.5 code 12 of its 33 tests failed, for example "existing conversation X must never be sent as DSS_TRACK_FOR_DELETION: expected [ Array(1) ] to not include 'da794fe0-243a-4ba5-817a-b88ff327e634'" and "leaving existing conversation X must not delete it: expected [ { channel: 'fetch', …(1) } ] to deeply equal []"; the new-conversation controls and the switch-off case passed there. The hook create-detection spec now loads the real hook.

**Cause**: through v4.39.8, fixed in v4.39.9 — turning the temporary conversation switch on after the DeepSeek page loaded left the temporary conversation undeleted when the tab was closed or the page navigated away (confirmed live; in-site SPA navigation still deleted through the service worker hand-off). The content script attached the window-message listener that captures `DSS_AUTH_CAPTURED` only while the switch was on or a conversation was tracked, and the main-world hook posts the token only when its value changes, so the single token post of the page-load create request reached no listener when the switch was off at load; `beforeunload` then had no token for the keepalive delete. The existing specs missed it because none turned the switch on after the page-load token post: `test/unit/temporary-chat-delete.existing-chat.scenario.spec.js` carried a comment acknowledging the gap. Two specs (P8 in `test/unit/temporary-chat-delete.spec.js`, the detached case in `test/unit/temporary-chat-delete.mutant-killers-2.spec.js`) asserted the missing capture as correct behaviour.

**Solution**: a resident listener, `handleResidentAuthMessage` in `content/temporary-chat-delete.js`, is attached in `init()` on every page load and captures the token while the deletion listeners are detached. `test/unit/temporary-chat-delete.late-toggle.scenario.spec.js` replays the page-load token post through the real hook and `test/helpers/deepseek-page-harness.js`, turns the switch on afterwards, and asserts the delete requests when leaving by tab close and by a full-page navigation away, each paired with the same leave after an early switch-on. On the 4.39.8 code 3 of the 17 tests failed (the 2 late-switch deleting cases and the late-switch token relay) and the other 14 passed; the two obsolete specs now assert that the token is captured and that leaving deletes nothing for a conversation that was never marked.

**Prevention**: A test of code that reacts to the host page's network requests MUST drive the real request sequence of the live page through the real hook: every request the page sends on load and on a user action, in the live order and timing, with request and response bodies copied from a live capture, and only the network and cross-world boundaries faked. The sequence MUST include the requests that fire in the case the feature must ignore (an existing conversation's page load sends a create too), and the test MUST assert the outcome the user sees (what is tracked, what is deleted), never a flag or a message the test itself set. A host message that the page posts once (a value posted only when it changes, such as the captured token) MUST be posted at the live moment, before the user changes the setting under test, and the test MUST vary the order of that post and the setting change: a listener attached only after the setting changes never sees a one-shot message posted earlier. A test MUST NOT post the hook's window messages or write state flags directly to stand in for the page, and MUST NOT run an inline copy of the hook; it loads the real file. A test that asserts a destructive behaviour as correct (a conversation tracked for deletion, a delete request sent) MUST name the live scenario in which that behaviour is right, and a spec with no such scenario is a tautology to remove.
