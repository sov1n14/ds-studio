# Environment Detection: Test With Real Device Profiles

**Cause**: through v4.35.4, fixed in v4.35.5 — `isMobileDevice()` in `content/mobile-device.js` returned true for `navigator.maxTouchPoints > 0`, so any desktop reporting touch points counted as mobile: Enter-to-send skipped the prompt prefix and the selected preset was reset to none on new-chat creation, while DeepSeek itself treats Enter as send on that machine. The bug-report machine is a Windows desktop with no touch hardware (non-touch monitor), yet Windows reports `SM_MAXIMUMTOUCHES = 10` and `SM_DIGITIZER = 0xC1`, so Chromium reports `navigator.maxTouchPoints === 10`; the most likely source (unconfirmed) is software touch injection, e.g. an Android emulator's touch-injection service using `InitializeTouchInjection`/`InjectTouchInput`. Touch points on a desktop therefore come from touchscreen laptops, pen devices, and touch-injecting software alike, and installed software can change the value on a machine whose hardware never changed. The suite encoded the bug as correct: `test/unit/mobile-device.spec.js` asserted "maxTouchPoints 2 + desktop UA → mobile", `test/unit/content-script.mobile-enter.spec.js` TC-2 asserted "5 touch points + Windows UA → Enter not intercepted", and the mobile-feature specs (`mobile-sidebar-swipe*.spec.js`, `mobile-homepage-cleanup.spec.js`) used `{ maxTouchPoints: 2, userAgent: 'Chrome Desktop' }` as their "mobile" fixture. The tests transcribed the implementation's predicate instead of the real-world fact that a desktop reporting touch points is still a desktop.

**Solution**: `isMobileDevice()` decides by form factor: the UA matches `/Mobi|Android|iPhone|iPad/i`, or iPadOS desktop mode (`navigator.platform === 'MacIntel' && navigator.maxTouchPoints > 1`). `test/unit/mobile-device.spec.js`, TC-2 in `test/unit/content-script.mobile-enter.spec.js`, `test/unit/prompt-injector.controller.spec.js`, and the new `test/unit/content-script.desktop-touch-points-enter.scenario.spec.js` use the exact UA, platform, and touch points from the bug-report machine (Edge on `Win32`, `maxTouchPoints: 10`), and the mobile-feature fixtures use a real Android phone profile. On pre-fix code, 7 tests in 4 files failed, including "a Windows desktop that reports touch points is a desktop form factor: expected true to be false", TC-2 "the native send must be swallowed so the prefixed text is sent instead: expected false to be true", and the scenario's "the overlay must still show preset A for the newly created chat, not reset to none: expected '' to be 'preset-A'".

**Prevention**: Environment-detection tests (device, platform, browser, input capability) MUST use realistic device profiles: the full tuple a real device reports (real UA + `platform` + `maxTouchPoints`), covering at least a desktop UA with touch points > 0 (touchscreen laptops, pen devices, and touch-injecting software such as Android emulators), a non-touch desktop, an Android phone, an iPhone, and an iPad in desktop mode. A fixture labeled "mobile" (or any device class) MUST be a real profile of that class, never a desktop UA with a capability flag flipped. The expected value comes from how the device behaves in the real world and on the host page, not from the predicate under test.

**Check**: Before trusting a detection test, confirm each fixture's UA string is one a real device of the labeled class sends, and that the expected result matches that device's real-world form factor. Then mutate the predicate to a single-signal version (touch only, or UA only) and confirm at least one profile goes red.
