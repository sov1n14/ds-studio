# Overlapping Async Writes: Older Resolves Last

**Cause**: v4.35.3 — in an existing chat with no stored binding, picking preset B while the chat→preset bind to the service worker failed rolled the dropdown label back to the placeholder, but the injected prefix kept B's content. The overlay's optimistic `updatePromptPrefixFromBinding()` awaited `getSettings()`; the rollback's call on the unbound chat set the prefix synchronously, so the older optimistic call resolved last and overwrote it — the stale async result won. The failed-bind consistency spec covered only a chat already bound to preset A, where the rollback also awaits and finishes last, so the unbound branch that writes synchronously never lost the race in a test. Some failure modes (NO_RECEIVER with retry, timeout) delay the rollback enough to avoid the race, so covering "a failure mode" was not enough, and the `sendMessage` double lacked the resolve-`undefined` shape that triggered it live (see [boundary-doubles-must-copy.md](boundary-doubles-must-copy.md)).

**Solution**: a generation counter makes the latest `updatePromptPrefixFromBinding()` call win. `test/unit/content-script.overlay-failed-bind-consistency.spec.js` runs every failure mode against an unbound chat and asserts the displayed label and the injected prefix agree. On pre-fix code, 4 failure modes on an unbound chat (rejection / port closed, resolves `undefined`, synchronous throw, `{ok:false}`) failed with "overlay shows no preset, so B's content must not be injected: expected '…GLOBAL-INSTRUCTION… PREFIX-B…' not to contain 'PREFIX-B'"; NO_RECEIVER with retry and timeout passed because their delayed rollback naturally avoids the race.

**Cause** (rollback crossing a navigation): the v4.34.3 bind-failure rollback in `onSelectChange` (`content/preset-overlay.controller.js`) restored the overlay and `activePresetId` from the stored binding of the chat UUID captured at dispatch time, without checking that the user was still on that chat. The rejection can land up to about 20 s after the click (10 s send timeout, one no-receiver retry, 10 s again), so after the user opened a new chat the rollback persisted the old chat's preset as `activePresetId`. Every failed-bind spec settled the rejection before navigating, so the rollback always ran while the original chat was still current; the "navigate after a rejected bind" cases tested the order that cannot go wrong.

**Solution** (rollback crossing a navigation): the rollback returns early unless `ctx.getCurrentChatUuid()` still equals the captured UUID, leaving only the map refresh. `test/unit/content-script.overlay-failed-bind-consistency.spec.js` holds the bind open with a deferred `sendMessage`, starts `handleChatChange()` for the new page, then rejects. On pre-fix code "bind rejected only after opening a new chat" failed with "chat X's stored binding must not become the new chat's activePresetId: expected 'preset-A' not to be 'preset-A'". Its bound-chat sibling passed on pre-fix code because the content-side chat-map queue is FIFO: chat Y's map read is queued behind the in-flight bind and resumes ahead of the rollback's read, so in the in-memory fake the navigation writes last; live storage latency can still reorder them. The settings relay also re-renders the overlay from the current chat within one settle, so the overlay label alone did not expose the stale repaint; the persisted `activePresetId` did.

**Prevention**: State written by overlapping async calls MUST have a scenario test in which the older call resolves last, once per branch that writes synchronously and once per branch that writes after an await. Run the scenario for every failure mode of the trust boundary, since each mode shifts timing differently. Assert that the consumers of the state agree with each other (displayed label vs injected prefix), not each in isolation. A late callback that writes state keyed by a value captured before an await (chat UUID, tab, page) MUST have a scenario test in which the context changes between dispatch and settlement, for each kind of context change (another existing chat, a new chat), with the boundary held open by a deferred promise rather than a fixed-delay transport; assert persisted state, not only a UI label that a relay may repaint.

**Check**: For each async writer of shared state, list its callers and mark which write before and which after an await; confirm a test orders the older call to resolve last for each pair. Then remove the latest-wins guard and confirm at least one of those tests goes red. For each async callback that reads a captured context value, confirm a test settles it after the context changed, then remove the context guard and confirm that test goes red.
