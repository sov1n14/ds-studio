# Overlapping Async Writes: Older Resolves Last

**Cause**: v4.35.3 — in an existing chat with no stored binding, picking preset B while the chat→preset bind to the service worker failed rolled the dropdown label back to the placeholder, but the injected prefix kept B's content. The overlay's optimistic `updatePromptPrefixFromBinding()` awaited `getSettings()`; the rollback's call on the unbound chat set the prefix synchronously, so the older optimistic call resolved last and overwrote it — the stale async result won. The failed-bind consistency spec covered only a chat already bound to preset A, where the rollback also awaits and finishes last, so the unbound branch that writes synchronously never lost the race in a test. Some failure modes (NO_RECEIVER with retry, timeout) delay the rollback enough to avoid the race, so covering "a failure mode" was not enough, and the `sendMessage` double lacked the resolve-`undefined` shape that triggered it live (see [boundary-doubles-must-copy.md](boundary-doubles-must-copy.md)).

**Solution**: a generation counter makes the latest `updatePromptPrefixFromBinding()` call win. `test/unit/content-script.overlay-failed-bind-consistency.spec.js` runs every failure mode against an unbound chat and asserts the displayed label and the injected prefix agree. On pre-fix code, 4 failure modes on an unbound chat (rejection / port closed, resolves `undefined`, synchronous throw, `{ok:false}`) failed with "overlay shows no preset, so B's content must not be injected: expected '…GLOBAL-INSTRUCTION… PREFIX-B…' not to contain 'PREFIX-B'"; NO_RECEIVER with retry and timeout passed because their delayed rollback naturally avoids the race.

**Cause** (rollback crossing a navigation): the v4.34.3 bind-failure rollback in `onSelectChange` (`content/preset-overlay.controller.js`) restored the overlay and `activePresetId` from the stored binding of the chat UUID captured at dispatch time, without checking that the user was still on that chat. The rejection can land up to about 20 s after the click (10 s send timeout, one no-receiver retry, 10 s again), so after the user opened a new chat the rollback persisted the old chat's preset as `activePresetId`. Every failed-bind spec settled the rejection before navigating, so the rollback always ran while the original chat was still current; the "navigate after a rejected bind" cases tested the order that cannot go wrong.

**Solution** (rollback crossing a navigation): the rollback returns early unless `ctx.getCurrentChatUuid()` still equals the captured UUID, leaving only the map refresh. `test/unit/content-script.overlay-failed-bind-consistency.spec.js` holds the bind open with a deferred `sendMessage`, starts `handleChatChange()` for the new page, then rejects. On pre-fix code "bind rejected only after opening a new chat" failed with "chat X's stored binding must not become the new chat's activePresetId: expected 'preset-A' not to be 'preset-A'". Its bound-chat sibling passed on pre-fix code because the content-side chat-map queue is FIFO: chat Y's map read is queued behind the in-flight bind and resumes ahead of the rollback's read, so in the in-memory fake the navigation writes last; live storage latency can still reorder them. The settings relay also re-renders the overlay from the current chat within one settle, so the overlay label alone did not expose the stale repaint; the persisted `activePresetId` did.

**Cause** (auto-bind flow resuming after the user left): `bindChatFromStorage()` in `content/chat-binding-controller.js` wrote `promptPrefix` and cleared `awaitingNewChatUuid`, `pendingPresetId` and the auto-bind marker after its awaits without checking that the user was still on the chat it bound, so a late auto-bind flow for a created chat wrote that chat's group as the injected prefix of the unbound chat the user had moved to. The existing controller tests released a held BIND only while the user stayed on the created chat, so a late flow writing view state for a chat the user had left went unseen. A leftover prefix from the created chat's own send also masked the late write until another tab's edit of the group cleared it.

**Solution** (auto-bind flow resuming after the user left): the flow always runs its storage writes and map refreshes, and writes view state only while `state.currentChatUuid` still equals its chat after the awaits; `handleChatChange()` likewise returns after the flow when the user has left. `test/unit/chat-binding-controller.late-auto-bind-scope.scenario.spec.js` holds the created chat's BIND, moves the user to an unbound chat, edits the group from another tab to clear the leftover prefix, releases the BIND, and checks the next send on the moved-to chat. On pre-fix code (v4.39.27) the spec failed in 4 consecutive runs with "the late flow of X must not write its group G as the prefix of unbound chat Y: a send on Y right after the flow of X resumes carries no group: expected … not to contain 'PREFIX-G'", and a revert-and-rerun by the verifier reproduced the same failure.

**Cause** (settings re-read queued behind a held bind): through v4.39.32, fixed in v4.39.33 — when the device-level `globalPromptEnabled` key changed, `refreshGlobalPromptEnabled()` in `content/content-script.js` re-read settings through `StorageManager.getSettings()`, whose `getChatPresetMap()` waits in the FIFO chat-map write queue of `utils/storage-manager.chatmap.js`. While another chat's auto-bind BIND write was held, an unbound chat kept the stale global-prompt flag from the new-chat page until the BIND released. No test toggled a setting while a chat-map write was held: the specs that hold a BIND exercised only preset edits and the prefix (such as `chat-binding-controller.late-auto-bind-scope.scenario.spec.js`). The state before the toggle also matched the expected state by chance, so a send could not tell a stale flag from a fresh one.

**Solution** (settings re-read queued behind a held bind): the change handler applies the changed key at once from the last-read settings snapshot before any await, then runs the corrective re-read. `test/unit/chat-binding-controller.held-bind-global-prompt.scenario.spec.js` holds another chat's BIND, toggles `globalPromptEnabled` on an unbound chat, and checks the next send before releasing the BIND, once for each toggle direction, so a fix that forces one value cannot pass. On pre-fix code it failed with "the device-level global prompt was turned off and unbound Y shows no group, so a send on Y must follow the new flag at once, even while the BIND of another chat is held: … not to contain 'GLOBAL-INSTRUCTION'".

**Cause** (nested job joining inside a closing broadcast): the closing step of `runExclusiveQueueJob` in `background/service-worker.js` re-broadcast only when a nested job was still pending after the broadcast. A nested unload-grace delete that joined and finished inside the broadcast left the last broadcast stale, so a tab kept hiding an already-deleted chat. No test let a nested job join and finish inside a held broadcast; the existing cases let it join before the broadcast or stay pending past it.

**Solution** (nested job joining inside a closing broadcast): the worker counts nested joins with a counter that only increases and repeats the closing round, wait then broadcast, while the count grew during the round. `test/unit/service-worker.nested-grace-job.scenario.spec.js` holds the broadcast's `tabs.query({})`, lets the grace delete join and finish inside it, releases it, and checks the last broadcast against the stored queue. On pre-fix code it failed with "the last broadcast must match the stored queue, which no longer lists the deleted S: expected { tabId: 1, …(1) } to deeply equal { tabId: 1, uuids: [] }".

**Prevention**: State written by overlapping async calls MUST have a scenario test in which the older call resolves last, once per branch that writes synchronously and once per branch that writes after an await. Run the scenario for every failure mode of the trust boundary, since each mode shifts timing differently. Assert that the consumers of the state agree with each other (displayed label vs injected prefix), not each in isolation. A late callback that writes state keyed by a value captured before an await (chat UUID, tab, page) MUST have a scenario test in which the context changes between dispatch and settlement, for each kind of context change (another existing chat, a new chat), with the boundary held open by a deferred promise rather than a fixed-delay transport; assert persisted state, not only a UI label that a relay may repaint. For any async flow keyed to a chat or page, write one case where the user navigates away before the flow resumes; assert what the moved-to view sends or shows, and clear any leftover state (such as a prefix from the earlier send) that could mask the late write. When a closing step must cover work that can join during it, test both a joiner still pending at the end of the step and a joiner that finishes inside the step. A settings-change handler whose read path shares a queue with a write that can be held (such as the FIFO chat-map queue behind a BIND) MUST have a scenario test that changes the setting while that write is held and asserts the effect before the write is released; test both directions of a toggle whenever the state before the change can equal the expected state after it.

**Check**: For each async writer of shared state, list its callers and mark which write before and which after an await; confirm a test orders the older call to resolve last for each pair. Then remove the latest-wins guard and confirm at least one of those tests goes red. For each async callback that reads a captured context value, confirm a test settles it after the context changed, then remove the context guard and confirm that test goes red. For each async flow keyed to a chat or page, confirm a case navigates away before it resumes, clears leftover state first, and asserts the moved-to view's send or display. For each closing step that covers joining work, confirm one case holds the step open with a deferred boundary call while a joiner joins and finishes, and asserts the last output against the stored state. For each settings-change handler, trace its read path to any write queue it waits in; confirm a case holds that queue's write with a deferred boundary call, changes the setting, and asserts the effect before release in both toggle directions, then make the handler await the re-read before applying the key and confirm that case goes red.
