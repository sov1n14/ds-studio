# Global Interceptors: Drive the User's Own Action Through Them

**Cause**: through v4.39.1, fixed in v4.39.2 — with "Prevent auto-scroll" on, the user's click on DeepSeek's native scroll-to-bottom button did nothing. `content/prevent-auto-scroll.js` patches `Element.prototype.scrollTo`, `scrollBy`, `scrollIntoView` and the `scrollTop` setter and blocks every downward call while the bridge flag is on, so the site's own click handler (one `Element.scrollTo`, then about 5 re-measure `scrollTo` calls within 25 ms as the virtual list grows) was blocked as well. The existing specs only drove programmatic scrolls into the patch and asserted that they are blocked, so they confirmed the block and never exercised the legitimate path through the same interceptor: a trusted user click on a host control whose handler then calls the intercepted API. Each spec saw the patch in isolation, and none put the user's action, the patch, and the host handler's multi-call burst in one document.

**Solution**: `content/prevent-auto-scroll-bridge.js` listens for `pointerdown` and `click` in the capture phase and, for a trusted press inside the native control (the extension's cloned `.dsw-gotop` button excluded), writes `Date.now() + 500` to `dataset.allowScrollUntil` on the bridge element; `content/prevent-auto-scroll.js` lets every scroll through until that time. `test/helpers/prevent-auto-scroll-harness.js` loads the real patch and the real bridge into one happy-dom document, models only the native scroll engine, `isTrusted` and `chrome.runtime`, and replays the site's click handler as the first `scrollTo` plus five re-measure calls with a growing `scrollHeight`. `test/unit/prevent-auto-scroll.user-scroll.scenario.spec.js` asserts the list's final scroll position after a trusted click, that streaming auto-scroll is blocked again once the window passes, and that a scripted `click()` opens nothing. On pre-fix code, 10 of the 60 tests across the five prevent-auto-scroll specs failed, all in the three new specs, including "the user-initiated jump must move the list off the reading position: expected 1000 to be 4200" and "every re-measure jump inside the window must land, ending at the grown bottom: expected 1000 to be 4800"; the two existing prevent-auto-scroll specs stayed green.

**Prevention**: When a test covers code that intercepts or blocks a host-page API (a monkey-patch on `Element.prototype`, a capture-phase `preventDefault`, a message filter), it MUST include the path where the user triggers the same API through a host control: the user's trusted action, the host handler's complete call sequence (every call it makes in that one gesture, not only the first), and the interceptor, all real and in one document. The assertion MUST target the outcome the user sees (the final scroll position), never that the interceptor was or was not called. Alongside it, a test MUST show that an untrusted, programmatic trigger of the same control stays blocked.

**Check**: Before trusting an interceptor spec, list the user gestures that reach the intercepted API on the live page and confirm one test drives each. Replay the host handler's real call sequence from a live probe (count, timing, geometry changes) instead of a single call. Then revert the interceptor's allow path and confirm the user-path test goes red.
