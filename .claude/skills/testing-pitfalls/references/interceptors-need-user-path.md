# Global Interceptors: Drive the User's Own Action Through Them

**Cause**: through v4.39.1, fixed in v4.39.2 — with "Prevent auto-scroll" on, the user's click on DeepSeek's native scroll-to-bottom button did nothing. `content/prevent-auto-scroll.js` patches `Element.prototype.scrollTo`, `scrollBy`, `scrollIntoView` and the `scrollTop` setter and blocks every downward call while the bridge flag is on, so the site's own click handler (one `Element.scrollTo`, then about 5 re-measure `scrollTo` calls within 25 ms as the virtual list grows) was blocked as well. The existing specs only drove programmatic scrolls into the patch and asserted that they are blocked, so they confirmed the block and never exercised the legitimate path through the same interceptor: a trusted user click on a host control whose handler then calls the intercepted API. Each spec saw the patch in isolation, and none put the user's action, the patch, and the host handler's multi-call burst in one document.

**Solution**: `content/prevent-auto-scroll-bridge.js` listens for `pointerdown` and `click` in the capture phase and, for a trusted press inside the native control (the extension's cloned `.dsw-gotop` button excluded), writes `Date.now() + 500` to `dataset.allowScrollUntil` on the bridge element; `content/prevent-auto-scroll.js` lets every scroll through until that time. `test/helpers/prevent-auto-scroll-harness.js` loads the real patch and the real bridge into one happy-dom document, models only the native scroll engine, `isTrusted` and `chrome.runtime`, and replays the site's click handler as the first `scrollTo` plus five re-measure calls with a growing `scrollHeight`. `test/unit/prevent-auto-scroll.user-scroll.scenario.spec.js` asserts the list's final scroll position after a trusted click, that streaming auto-scroll is blocked again once the window passes, and that a scripted `click()` opens nothing. On pre-fix code, 10 of the 60 tests across the five prevent-auto-scroll specs failed, all in the three new specs, including "the user-initiated jump must move the list off the reading position: expected 1000 to be 4200" and "every re-measure jump inside the window must land, ending at the grown bottom: expected 1000 to be 4800"; the two existing prevent-auto-scroll specs stayed green.

**Cause**: through v4.39.4, fixed in v4.39.5 — the same blind spot in the other direction. `scrollToTopAndWait()` in `content/go-top.scroll.js` jumps the list to the top on every poll and settles only after three stable polls. In a long conversation, code block syntax highlighting keeps mutating the DOM, so the loop ran for seconds (live: the page locked about 0.8 s from the bottom). A user click on the native scroll-to-bottom button in that window landed at the bottom (the v4.39.2 allow window let it through), and the loop then rewrote `scrollTop = 0` and pulled the page back to the top. The existing Go Top specs drove the loop alone, with a quiet DOM and no host control in the document, and the prevent-auto-scroll specs drove the native press without the Go Top loop running, so no spec put the user's trusted press, the host handler, and the running extension loop in one document.

**Solution**: `content/go-top.scroll.js` listens for capture-phase `pointerdown` and `click` on `document` while the loop runs, treats a trusted press inside `._0706cde` (not the `.dsw-gotop` clone) as the existing `stopped-by-user` abort, and does not touch the event, so the host handler still runs. `test/helpers/go-top-native-press-harness.js` loads the real GoToTop module, the captured live floating bar, a tracked scroller, `isTrusted`, the host go-bottom handler (one `scrollTo`, then five re-measure calls) and a busy-DOM driver into one happy-dom document. `test/unit/go-top.native-bottom-cancel.scenario.spec.js` records every scroll position the list took and asserts that the list never returns to the top after a trusted press, with a quiet DOM and with a busy DOM, that scripted clicks and the clone do not cancel, and that the next Go Top click still reaches the top. The original 7-test version of this spec failed 3 tests on pre-fix code, and its 4 guard tests passed.

**Cause**: through v4.39.4, fixed in v4.39.5 — the two Go Top button handlers in `content/go-top.render.combined.js` (click and Enter/Space keydown) called `this.scrollToTopAndWait()` and discarded the returned promise. A second button click or a trusted native press during a Go Top rejects that promise with `{ success: false, reason: 'stopped-by-user' }` (`content/go-top.scroll.js`), so the page logged an unhandled rejection although the user's stop worked. The existing native-press specs never saw it, because their harness installed a pass-through `vi.spyOn(GoToTop, 'scrollToTopAndWait')`, and a vitest spy attaches its own then-handlers to every promise it returns, which marks the rejection as handled.

**Solution**: both button handlers now pass the promise to `_startGoTopFromButton()` in `content/go-top.render.combined.js`, which attaches a `catch` and stays silent for `stopped-by-user`. S2 and S3 of `test/unit/go-top.native-press-scope.scenario.spec.js` (a Go Top stopped by a trusted native press, and by a second button click) call `mockRestore()` on `GoToTop.scrollToTopAndWait` before the user path, so only the button's own handler holds the promise. They collect rejections with `watchUnhandledRejections()` from `test/helpers/go-top-native-press-harness.js`, a `process` `unhandledRejection` listener, because the `setTimeout` wait in `captureUncaught` never fires under fake timers. On pre-fix code S1 to S3 failed, and removing the `catch` turned S2 to S5 red; on the fixed code all 5 tests pass.

**Prevention**: When a test covers code that intercepts or blocks a host-page API (a monkey-patch on `Element.prototype`, a capture-phase `preventDefault`, a message filter), it MUST include the path where the user triggers the same API through a host control: the user's trusted action, the host handler's complete call sequence (every call it makes in that one gesture, not only the first), and the interceptor, all real and in one document. The assertion MUST target the outcome the user sees (the final scroll position), never that the interceptor was or was not called. Alongside it, a test MUST show that an untrusted, programmatic trigger of the same control stays blocked. When the code under test is a long-running extension loop that writes host state (a scroll-to-top, retry, or polling loop), the test MUST also fire the user's trusted press on a host control while the loop runs, with the host handler's real call sequence, and assert the position the user sees after the DOM goes quiet; the loop's settle time, not its first write, decides who wins. The busy DOM that keeps such a loop running MUST be delivered through MutationObserver records that the test controls: under fake timers happy-dom delivered only 1 to 2 callback batches for 12 appends 50 ms apart, so a busy DOM looked quiet to the code under test and the race never reproduced. A test that asserts on unhandled rejections MUST first restore the real promise-returning method with `mockRestore()`, and MUST collect rejections with a `process` `unhandledRejection` listener, because a pass-through spy marks each rejection as handled.

**Check**: Before trusting an interceptor spec, list the user gestures that reach the intercepted API on the live page and confirm one test drives each. Replay the host handler's real call sequence from a live probe (count, timing, geometry changes) instead of a single call. Then revert the interceptor's allow path and confirm the user-path test goes red. For a loop that races the user, count the observer callbacks the fixture delivers against the appends it makes, and confirm the number of batches matches what the loop would see in Chrome before trusting a "quiet DOM" or "busy DOM" case; then remove the loop's press listener and confirm the busy-DOM test goes red. For a rejection assertion, confirm the spec's precondition that the method is no longer a mock (`vi.isMockFunction` returns false), then revert the button handler to call the method without a `catch` and confirm the test goes red.
