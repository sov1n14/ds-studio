# Red For the Right Reason

**Lesson from** the chat-map single-writer work (v4.34.x): `test/unit/storage-manager.chatmap.ops.spec.js` and `test/helpers/chat-map-writer-harness.js` loaded their not-yet-written targets through a runtime `import(/* @vite-ignore */ path)` so a missing file would fail each test instead of crashing collection. Under this repo's Vitest config (`environment: happy-dom`, Vite root `test/`) that call fails with "Cannot find module" for every file outside `test/`, including files that have existed for a long time — so the tests were red because the loader could never load anything, not because the code was missing. The "Cannot find module" text read like "not implemented yet", nobody pointed the loader at a file that exists, and once `utils/storage-manager.chatmap.ops.js` landed the ops spec stayed red and could never go green. 16 scenario reds were accepted on the same false signal.

**Rule** — a red test MUST be red for the reason it claims. Any dynamic or indirect loading mechanism (runtime `import()`, `require`, glob loader, fixture reader) MUST be shown to load an existing file before a failure through it is accepted as "target missing". Where a test deliberately targets a file that does not exist yet, check existence explicitly (`fs.existsSync`) and fail with a message that names the missing file, kept separate from the "exists but failed to load" error, so a broken loader cannot pass for an unimplemented feature. Prefer a static import once the target exists.

**Check** — before reporting a red phase, point the loading mechanism at a file that already exists (for the chat-map harness, `background/pending-store-routes.js` via `createRequire(import.meta.url)`) and confirm it loads, then restore the path. Then read the actual failure text of every red test (the JSON reporter shows per-test messages; the default reporter dedupes identical errors) and confirm each one states the claimed reason — for example "background/chat-map-routes.js does not exist" — not a generic resolution error.
